## 0. 한 장 요약

ABC는 **AI 작업 블록을 만들어 파는 사람**과 **그 블록을 사서 이어 붙여 쓰는 사람**이 만나는 장터다.

- **김전략(판매자 A)** 은 "브랜드 기획서를 넣으면 시장을 조사하고 제품을 분석해 브랜드 전략을 써 주는" AI 에이전트를 만들어 올린다. 안에는 블록 다섯 개가 나뉘고 합쳐지고 갈라지며 돈다. 필요한 것은 각 블록에 AI에게 시킬 말(프롬프트)과 참고 파일 정도다. **코딩은 필요 없다.**
- **최사장(사용자)** 은 칫솔 브랜드를 준비하며 "브랜드 전략 세우고 SNS 캠페인까지 뽑고 싶다"고 검색해, 김전략의 에이전트와 다른 두 판매자의 "SNS 캠페인 기획" · "광고 카피" 에이전트를 찾아 이어 붙이고, 기획서 폼을 채워 실행한다. 몇 분 뒤 자기가 고른 서식의 PDF가 나온다.
- 실행 한 번에 최사장의 이용권(ABC)이 차감되고, **세 판매자에게 각각 정산금이 쌓인다.** 한 번의 실행이 여러 사람의 수익이 되는 것, 이것이 ABC가 다른 서비스와 다른 점이다.

## 1. 꼭 알아야 할 낱말 열 개

| 낱말 | 뜻 | 비유 |
| --- | --- | --- |
| **노드** | AI 작업 블록 하나. 앞 블록의 결과를 받아 판매자가 정한 모양(글 또는 JSON 예시)의 출력을 낸다 | 레고 블록 한 개 |
| **프롬프트** | 노드 안에서 AI에게 시키는 말. 판매자의 노하우. **저장 뒤에는 누구에게도 보이지 않는다** | 비공개 레시피 |
| **참고 파일** | 노드가 AI를 부를 때 프롬프트와 함께 보여주는 파일. 예: 우리 회사의 브랜드 가이드 PDF | 레시피에 붙인 사진 |
| **출력 형식** (글 · JSON 예시) | 노드가 내놓는 데이터의 모양. **글**이거나, 판매자가 적은 **JSON 예시**와 같은 모양. 플랫폼이 정한 목록은 없고, 입력 형식도 따로 없다 — 앞 블록의 결과가 통째로 들어간다 | 완성품의 포장 규격 |
| **워크플로우** | 노드를 이은 것. 한 노드의 출력이 여러 노드로 갈라질 수도, 여러 노드의 출력이 한 노드로 모일 수도 있다 | 조립된 레고 |
| **분기** | 앞 결과의 값을 보고 다음 노드를 고르는 갈림길. **AI가 아니라 플랫폼이 판정한다** | 철로의 전철기 |
| **병합** | 여러 노드의 결과를 한 노드가 한꺼번에 받는 것 | 두 강이 만나는 합류점 |
| **에이전트** | 워크플로우(노드 하나여도 됨)를 포장해 마켓에 올린 상품. 안의 프롬프트는 봉인된다 | 포장된 레고 세트 |
| **템플릿** | 결과 데이터를 부어 넣는 서식. 플랫폼 기본 서식을 쓰거나 내 디자인을 올려 쓴다 | 문서 양식 |
| **ABC · 정산금** | ABC는 사용자가 충전해 두는 이용권(실행 시 차감), 정산금은 판매자에게 쌓이는 돈(출금 가능) | 선불 교통카드 · 통장 잔액 |

### 1.5 형식 규칙 — 입력은 자유, 출력은 판매자가 예시로 정한다 (09-26 계약 v2.1)

처음 설계(09-17)에서는 **앞 블록의 출력 형식과 뒤 블록의 입력 형식이 같아야** 선이 그어졌다. 판매자 한 사람의 에이전트 안에서는 잘 맞았지만, 사용자가 **분야가 다른 판매자들의 블록**(브랜드 전략 → 법률 검토)을 엮으려 하면 형식이 달라 선이 안 그어졌다. "남의 블록을 자유롭게 잇는다"는 서비스의 핵심이 형식 규칙에 막힌 것이다.

그래서 09-25 · 26에 규칙을 바꿨다. Google의 에이전트 간 통신 규격(A2A)이나 n8n 같은 자동화 도구와 같은 방식이다. **플랫폼이 정한 형식 목록(견본 · 카탈로그)은 없다.**

| | 처음 (09-17) | 지금 (09-26) |
| --- | --- | --- |
| 입력 형식 | 목록에서 골라야 하고, 앞 블록과 맞아야 연결 | **없다.** 앞 블록의 결과가 통째로 들어간다. 여러 블록이면 이름표를 붙여 한 묶음으로 |
| 출력 형식 | 플랫폼 목록(11종)에서 필수 선택 | **글**, 또는 판매자가 원하는 모양을 **JSON 예시 하나**로 적는다 |
| 연결 | 형식이 맞아야 선이 그어진다 | **어떤 블록이든 이어진다** |
| 분기 | 앞 블록의 항목 값 비교 | 같다. 단, 앞 블록의 **출력 예시에 있는 항목**만 (저장할 때 검사). 글자는 대소문자 · 앞뒤 공백을 무시하고 비교 |
| 조합이 어울리지 않을 때 | 실패 · 사용자 책임 | **실패가 아니다.** 실행되고 품질은 평점으로 |

JSON 예시는 이렇게 생겼다. 값의 종류(글자 · 숫자 · 참거짓 · 목록 · 묶음)가 곧 규격이고, 값을 `null`로 둔 항목은 선택이다.

```json
{ "시장 개요": "…", "경쟁사": [ { "이름": "…", "특징": "…" } ], "경쟁 강도": "high", "판정 근거": "…", "메모": null }
```

예시 하나로 이것이 따라온다.

| | |
| --- | --- |
| **답 모양 강제** | AI가 예시와 같은 모양으로만 답하게 플랫폼이 강제하고, 어기면 두 번 고쳐 달라고 한다 |
| **분기** | `경쟁 강도` 같은 항목의 값을 보고 길을 가른다. 글 출력으로는 분기할 수 없다 |
| **입력 폼** | 첫 블록에 입력 예시를 붙이면 그 항목들로 사용자 입력란을 그린다 |
| **결과물 문서** | 항목 이름이 문서의 제목이 된다. 한글로 적으면 한글 제목 |
| **실패 책임** | AI가 예시 모양을 어겼는지 가릴 수 있다 → 판매자 책임 판정 |

예시로 못 하는 것도 있다 — "high 아니면 low만", "최대 5개" 같은 선택지 · 개수 제한이다. 이런 것은 프롬프트로 지시한다.

## 2. 판매자(공급자) 사용법 — 김전략의 하루

### 2.1 노드 만들기

지갑으로 로그인한 뒤 "노드 만들기"에서 아래를 채운다. 김전략은 노드를 다섯 개 만든다. 그중 하나의 예다.

| 채우는 것 | 김전략의 예 (시장 조사 노드) | 설명 |
| --- | --- | --- |
| 이름 | 시장 조사 | 마켓에 보이는 이름 |
| AI 모델 | Gemini 2.5 Pro | 지금은 한 가지(09-26 Flash → Pro). 다른 모델 선택은 다음 버전 |
| 프롬프트 | "의뢰 카테고리의 시장 규모 · 주요 경쟁사 · 최근 트렌드를 정리하고, 경쟁 강도를 high 또는 low로 판정한다. 판정 근거를 …" | **판매자의 노하우.** 저장 뒤 본인 외에는 아무도 볼 수 없다 |
| 참고 파일 (선택) | `시장조사_체크리스트.md` · `보고서_디자인_참고.png` | AI가 프롬프트와 **함께 읽는다.** PDF · 사진 · 표(엑셀 · CSV) · 텍스트, 노드당 10MB. 사용자에게 보이지 않는다 |
| 출력 형식 | JSON 예시 `{"시장 개요": "…", "경쟁사": [{"이름": "…"}], "경쟁 강도": "high", "판정 근거": "…"}` | **글** 또는 **JSON 예시**. JSON이면 AI가 그 모양으로만 답하도록 플랫폼이 강제하고, 글이면 자유 서술 |
| 사용자 입력 예시 (첫 노드만 · 선택) | `{"브랜드명": "…", "카테고리": "…", "가격대": "…", "추가 요청": null}` | 워크플로우 맨 앞 노드에만 붙인다. 이 항목들로 사용자 화면의 입력란이 그려진다. 없으면 자유 입력란 하나 |

**출력을 JSON으로 하면 뭐가 좋나.** 뒤 블록은 앞 결과를 통째로 읽으므로 글이어도 이어진다. 그래도 JSON 예시를 주면 세 가지가 생긴다 — 분기가 값을 읽을 수 있고(경쟁 강도), 결과물 문서의 절이 자동으로 나뉘고, AI가 모양을 어겼을 때 판매자 책임을 가릴 수 있다. 글은 그 셋이 없는 대신 자유롭다 — 법률 메모 · 요약 · 카피처럼 구조가 없는 일에 맞는다. 예시의 항목 이름은 판매자가 정한다. 한글로 써도 된다.

**가격은 판매자가 정하지 않는다.** 노드 1회 실행의 실제 원가(AI 사용료)에 판매자 **등급**에 따른 프리미엄을 얹어 플랫폼이 정한다. 등급은 성공률 · 평점 · 사용량으로 매일 다시 계산되고, 처음 만든 노드는 기본 등급에서 시작한다. 판매자는 등록 전에 **테스트 실행**으로 원가와 결과물을 미리 본다(§2.3).

### 2.2 노드를 이어 워크플로우 만들기 — 나누고, 합치고, 가르고, 다시 만난다

김전략의 "브랜딩 전략" 워크플로우다.

```
[기획 요청서] ─┬─▶ 시장 조사 ───┐
               └─▶ 제품 분석 ───┤ 두 결과를 함께 받아
                                ▼
                     분기: 시장 조사의 경쟁 강도가 high?
                        ├ 예    → 차별화 전략 ──┐
                        └ 아니오 → 대중 공략 전략 ┘ 둘 중 도착한 하나를 받아
                                                 ▼
                                    브랜드 전략 보고서 → [출력]
```

여기서 네 가지가 일어난다.

| 일어나는 일 | 어디서 | 규칙 |
| --- | --- | --- |
| **나뉜다** | 기획 요청서가 시장 조사와 제품 분석 둘로 | 한 출력을 여러 노드가 각각 받는다 |
| **합쳐진다** | 시장 조사 + 제품 분석 → 다음 단계 | 여러 결과를 한 노드가 묶음으로 받는다 (`{ market: …, product: … }`) |
| **갈라진다** | 경쟁 강도 high / low | 플랫폼이 값을 비교해 **한쪽만** 실행. 안 간 쪽은 돈을 받지 않는다 |
| **다시 만난다** | 차별화 · 대중 공략 → 보고서 | 도착한 하나를 받는다. 두 전략 노드의 형식이 달라도 된다 |

연결 규칙은 하나다. **어떤 노드든 이어진다.** 뒤 노드는 앞 노드의 결과 전체(병합이면 여러 개에 이름표를 붙여)를 받아 자기 프롬프트대로 읽는다. 저장할 때 플랫폼이 검사하는 것은 **분기뿐** — 분기가 읽는 값은 앞 노드의 출력 예시에 있는 항목이어야 하고, 글 출력 노드의 값으로는 갈 수 없다. 어긋나면 저장이 막히고 이유가 표시된다. 분기 · 병합 · 입력 · 출력 처리는 플랫폼이 제공하는 것이라 **무료**다. 판매자가 만든 노드만 돈이 붙는다.

### 2.3 버전 확정 — 에이전트로 포장하기

**버전 확정**을 누르면 워크플로우가 마켓 상품(에이전트)이 된다. 이름 · 설명 · 카테고리 · 태그를 적는다.

| 마켓에 **공개되는** 것 | **봉인되는** 것 |
| --- | --- |
| 이름 · 설명 · 카테고리 · 태그 | 프롬프트 원문 |
| 입력 항목(첫 노드에 입력 예시를 붙였으면) · 출력 형식("JSON"과 그 항목 목록, 또는 "글") | 참고 파일 |
| 가격 · 등급 · 성공률 · 평점 · 사용 횟수 | 내부 노드 다섯 개와 그 연결 |

밖에서 보면 "기획 요청서를 넣으면 브랜드 전략 보고서가 나오는 블록 하나"다. 구성 노드가 전부 본인 것이어야 확정되고, 소유권은 블록체인에 기록된다.

**확정 전 테스트 실행.** 버전을 확정하기 전에 워크플로우를 **테스트로 실행**해 볼 수 있다. 실제와 똑같은 경로로 돌아 토큰 · 원가 · 결과물 · 소요 시간이 그대로 나오고, 정산만 쌓이지 않는다. 이때 잰 원가가 노드 가격의 근거가 된다. AI 사용료는 들므로 횟수는 플랫폼이 제한한다.

### 2.4 마켓에 공개

"공개"를 켜면 마켓 목록에 뜨고 **추천 색인**에 들어간다. 사용자가 "브랜드 방향 잡아 주는 거"처럼 단어가 겹치지 않는 말로 찾아도 나온다.

### 2.5 수익

| 언제 | 무엇이 |
| --- | --- |
| 내 에이전트가 들어간 워크플로우가 **성공**할 때마다 | 실행된 내 노드들의 단가만큼 정산금 적립 (안 간 분기 쪽은 제외) |
| 실패했는데 **내 노드 잘못**일 때 | 그 건 정산 없음. 성공률 하락 → 등급에 반영 |
| 실패했는데 **사용자 입력 잘못**일 때 | 내 노드가 이미 성공했으면 정산 유지 |

마이페이지에서 정산 내역을 보고 **출금**한다(테스트넷 USDC).

## 3. 사용자(수요자) 사용법 — 최사장의 하루

### 3.1 충전

지갑으로 로그인하고 ABC를 충전한다. ABC는 실행할 때만 쓰이고 남에게 줄 수 없다.

### 3.2 찾기

| 방법 | 어떻게 | 무엇이 다른가 |
| --- | --- | --- |
| **말로 찾기** (랜딩) | "칫솔 브랜드 전략 세우고 SNS 캠페인까지 뽑고 싶어" | **뜻으로** 찾는다. 결과는 8개 안쪽 |
| **키워드 검색** (마켓) | "브랜딩", 카테고리 "마케팅" | 이름 · 태그에 그 말이 들어간 것만 |

### 3.3 조립 — 남의 에이전트도 나누고 합친다

찾은 에이전트를 캔버스에 놓고 잇는다. 규칙은 판매자와 같다.

```
[기획 요청서]
   → [브랜딩 전략 · 김전략(A)]  ─┬─▶ [SNS 캠페인 기획 · 이마케터(B)] ─┐
                                └─▶ [광고 카피 · 박카피(C)]        ─┤ 둘 다 받아
                                                                    ▼
                                            [통합 실행안 · 이마케터(B)] → [출력]
```

김전략의 에이전트는 밖에서 블록 하나지만, 실행되면 안의 다섯 노드와 분기가 그대로 돈다. 맨 앞 **[기획 요청서]** 와 맨 뒤 **[출력]** 은 플랫폼이 자동으로 붙인다. 형식이 달라도 이어진다 — 브랜딩 에이전트 뒤에 다른 분야 판매자의 "법률 검토(글)" 에이전트를 붙여도 된다.

### 3.4 입력

첫 블록에 사용자 입력 예시(브랜드명 · 카테고리 · 핵심 고객 · 가격대 · 차별점 · 추가 요청)가 붙어 있으므로 화면에 **그 항목들의 입력란**이 자동으로 생긴다(예시가 없는 블록이면 자유 입력란 하나). 브랜드명 · 카테고리 · 핵심 고객 · 가격대(드롭다운) · 차별점 · 추가 요청. JSON을 직접 쓰는 일은 없다. **파일도 같이 올릴 수 있다** — 시제품 사진 · PDF · 엑셀 · 글, 여러 개, 합계 10MB. 올린 파일은 워크플로우의 **모든 블록**이 본다. 최사장은 칫솔 시제품 사진을 한 장 올린다. 제품 분석은 사진에서 보이는 소재 · 형태를 근거로 쓰고, 광고 카피는 사진에 있는 것을 문구에 담는다.

### 3.5 실행

| 순서 | 화면 | 뒤에서 |
| --- | --- | --- |
| 1 | **견적**이 보인다. "이 실행은 최대 N ABC" | 실행 엔진이 "가장 비싼 분기 조합에서 실제로 도는 노드 목록"을 내고, 백엔드가 그 노드들의 단가를 합한다 |
| 2 | "실행"을 누른다 | 잔액을 확인하고 견적만큼 **먼저 빼 둔다** |
| 3 | 블록에 차례로 불이 들어온다 | 노드가 하나씩 돈다. 병렬로 나뉜 것도 지금은 차례로 |
| 4 | 분기에서 한쪽 길만 밝아진다 | 플랫폼이 값을 비교해 길을 고른다. 안 간 길은 **돈을 받지 않는다** |
| 5 | "완료"와 함께 결과 화면 | 마지막 노드의 결과(JSON 또는 글)를 보관한다 |

전체는 길어도 5분 안에 끝난다. 화면을 닫아도 실행은 계속되고, 결과는 실행 내역에 남는다.

### 3.6 결과 — 서식을 고른다

결과는 먼저 **데이터(JSON 또는 글)** 로 있고, 최사장이 서식을 고르면 그 서식을 입힌 **HTML 문서**가 되어 화면에 바로 뜬다. 인쇄 · 다운로드는 그 HTML로 만든 **PDF**다. 서식을 안 고르면 플랫폼 기본 서식(문서형 · 카드형)이다.

서식은 **빈칸이 뚫린 디자인**이다. 어느 자리에 어느 항목이 들어갈지가 서식 안에 적혀 있고, 플랫폼은 거기에 값을 끼워 넣어 PDF로 뽑는다. 이 과정에 AI는 없다 — 0.2초, 0원, 몇 번을 돌려도 같은 결과.

| 서식이 오는 곳 | 무엇 |
| --- | --- |
| 플랫폼 기본 | 결과 형식(브랜드 전략 보고서 · 통합 실행안 …)마다 준비된 문서형 서식. 항상 있다 |
| 판매자 제공 | 블록을 만든 사람이 "내 결과는 이 서식이 어울립니다"라고 붙여 둔 것 |
| 내 서식 | 내 회사 보고서 디자인(PDF · 이미지)을 올리면 AI가 보고 **빈칸 뚫린 디자인**으로 바꿔 보관한다. 올릴 때 **딱 한 번**이고, 그 뒤 1,000번 실행해도 그대로 재사용한다 |

서식으로 바꾸는 과정은 AI를 한 번 부르지만 **실행이 아니라 등록**이라 과금되지 않는다. 서식이 데이터와 안 맞으면 세 겹으로 막는다 — 같은 형식 정의에서 나왔으니 어긋날 여지가 적고, 문서를 만들기 전에 항목을 대조하고, 그래도 실패하면 기본 서식으로 대신 만든다. 블록은 이미 성공했고 정산도 끝났으니 **서식 문제가 실행을 실패시키지 않는다.** 결과 파일은 실행 내역에 보관되어 나중에도 다시 받을 수 있다.

### 3.7 실패하면

플랫폼이 **누구 잘못인지 자동으로 가린다.** 기준은 한 문장이다. "그 노드에 들어간 입력이 규격에 맞았는가."

| 상황 | 판정 | 최사장의 ABC | 판매자 |
| --- | --- | --- | --- |
| 입력은 맞았는데 노드 안에서 AI가 틀린 모양으로 답했거나 시간을 넘김 | **판매자 잘못** | 그 노드분 + 그 뒤 안 돈 것 **환불** | 정산 없음, 성공률 하락 |
| 사용자가 입력란의 필수 항목을 비웠거나 올린 파일을 읽을 수 없음 | **사용자 잘못** | 이미 성공한 노드분은 **지불**, 그 뒤 안 돈 것만 환불 | 성공한 노드는 정산 유지 |
| 앞 결과가 너무 길어 상한을 넘김(긴 체인 · 큰 참고 파일) · 플랫폼 자체 오류 | **플랫폼 잘못** | **전액 환불** | 영향 없음 |

비유하면, 재료를 제대로 줬는데 요리사가 태우면 요리사 잘못, 상한 재료를 주면 주문자 잘못, 주방에 불이 나면 식당 잘못이다.

**블록을 어울리지 않게 이었을 때**(예: 광고 카피 뒤에 학생 성적 통계)는 실패가 아니다. 실행은 되고 결과가 이상할 뿐이며, 그것은 평점 · 리뷰로 남는다. 입력 형식 검사가 없으니 플랫폼은 "조합이 틀렸다"를 판정할 수 없고, 판정할 수 없는 것에 환불을 걸지 않는다.

### 3.8 리뷰

결과를 받은 뒤 에이전트에 평점 · 리뷰를 남긴다. 판매자 등급에 반영된다.

## 4. 실행 한 번의 뒷면 — 플랫폼이 중간에 끼는 이유

```
최사장 ─▶ 프론트 ─▶ 백엔드 ─▶ 메시지 큐 ─▶ AI 실행 엔진 ─▶ (노드마다) 외부 AI(Gemini)
                    │  ▲                         │
                    │  └── 진행 · 완료 메시지 ────┘
                    └─▶ 정산 · 보관 · 알림
```

노드끼리 직접 대화하지 않는다. **매 노드의 결과가 플랫폼으로 돌아왔다가 다시 다음 노드로 나간다.** 그래야 아래가 가능하다.

| 단계 | 플랫폼이 하는 일 | 이것이 있어야 되는 것 |
| --- | --- | --- |
| ① 에이전트 펼치기 | 사용자 워크플로우 속 에이전트를 내부 노드들로 펼치고, 각 노드에 소유자를 표시한다 | 판매자별 정산 |
| ② 입력 묶기 | 앞 노드(들)의 결과 전체에 이름표(노드 이름 · JSON 또는 글)를 붙여 한 묶음으로 만든다. 첫 노드는 사용자 입력이 입력 예시 모양인지 확인. 너무 길면 중단(플랫폼 책임) | 병합 · 분야가 다른 블록의 연결 |
| ③ AI 호출 | 판매자 프롬프트 + 참고 파일 + 입력 묶음을 한 번에 보낸다. JSON 예시가 있으면 **그 모양으로만 답하게 강제**하고, 글이면 자유롭게 | 판매자 노하우 적용 |
| ④ 출력 검사 | JSON 노드만. 답이 예시 모양(항목 · 종류)인지 확인하고 안 맞으면 두 번까지 다시 요청. 글 노드는 검사 없음 | 분기 판정 · 서식 · 판매자 책임 판정 |
| ⑤ 분기 판정 | 지정한 항목의 값을 비교해 다음 노드를 고른다. AI에게 묻지 않는다 | 예측 가능한 흐름 |
| ⑥ 원가 기록 | 이번 호출에 쓴 토큰 수와 공시 단가 기준 USD를 남긴다. **ABC 환산 · 단가 · 환불액은 백엔드가 계산한다** | 가격 재산정 · 정산 |
| ⑦ 정산 신호 | 노드가 성공하면 "어느 판매자의 어느 노드가 돌았는지"를 백엔드에 넘긴다(테스트 실행이면 비움) | 노드별 정산 |
| ⑧ 결과 제공 | 마지막 노드의 결과 데이터를 보관하고, 사용자가 고른 서식으로 PDF를 만든다 | 사람이 읽는 결과물 |

프롬프트 원문은 이 과정 어디에도 기록되지 않는다. 로그 · 응답 · 검색 색인 어디에도 남지 않는다.

## 5. 돈의 흐름

| 누가 | 무엇을 | 언제 |
| --- | --- | --- |
| 사용자 | ABC 충전 | 실행 전 |
| 사용자 | 견적만큼 선차감 | 실행 버튼 |
| 플랫폼 | 노드 성공마다 해당 판매자에게 정산금 적립 | 실행 중 |
| 플랫폼 | 안 간 분기 경로분 반환 | 실행 끝 |
| 플랫폼 | 실패 시 책임에 따라 환불 | 실패 시 |
| 판매자 | 정산금 출금 (테스트넷 USDC) | 원할 때 |

**돈이 붙는 것과 안 붙는 것**

| 붙는다 | 안 붙는다 (플랫폼 제공) |
| --- | --- |
| 판매자가 만든 노드 | 입력 처리(폼 · 엑셀), 출력 처리(서식 · PDF), 분기, 병합, 서식 등록 |

단가 = 노드 실제 원가 × (1 + 등급 프리미엄). MVP는 플랫폼 수수료 0%다. 실행 엔진은 토큰과 USD만 재고, ABC로 바꾸는 것은 백엔드다.

## 6. 시연 시나리오 — 한 번의 실행, 세 사람의 수익

| 순서 | 누가 | 무엇을 |
| --- | --- | --- |
| 준비 1 | 판매자 A 김전략 | 노드 5개(시장 조사 · 제품 분석 · 차별화 전략 · 대중 공략 전략 · 브랜드 전략 보고서) + 분기로 "브랜딩 전략" 에이전트 공개 |
| 준비 2 | 판매자 B 이마케터 | "SNS 캠페인 기획" · "통합 실행안" 에이전트 공개 |
| 준비 3 | 판매자 C 박카피 | "광고 카피" 에이전트 공개 |
| **1단계** | 사용자 | 김전략의 에이전트 하나로 실행 — 포화 시장 브리프(칫솔)는 **차별화 전략** 길로, 틈새 브리프는 **대중 공략** 길로 간다. 같은 에이전트, 다른 입력, 다른 길 |
| **2단계** | 사용자 | A → (B ∥ C) → B 로 엮어 실행 — 세 판매자에게 각각 정산. 안 간 분기 쪽은 과금 없음 |
| 마지막 | 사용자 | 결과를 기본 서식으로 한 번, 올려 둔 내 서식으로 한 번 PDF로 받는다 |
| 확인 | 판매자 A · B · C | 마이페이지에서 각자 적립 확인 |

## 8. 자주 나올 질문

**내 프롬프트를 남이 볼 수 있나.** 없다. 저장 뒤에는 본인 외 누구도 볼 수 없고, 실행 결과 · 로그 · 추천 색인 어디에도 원문이 남지 않는다.

**참고 파일은 사용자에게 보이나.** 아니다. AI에게만 전달되고 사용자는 결과만 본다.

**분기는 AI가 판단하나.** 아니다. 플랫폼이 숫자 · 문자를 비교한다. 같은 입력이면 항상 같은 길로 간다. 단, 비교되는 값(예: 경쟁 강도)은 앞 노드의 AI가 낸 것이다.

**남의 에이전트 안이 어떻게 생겼는지 볼 수 있나.** 없다. 입력 · 출력 형식과 가격 · 등급만 보인다. 실행할 때 플랫폼이 안을 펼치지만 사용자에게는 블록 하나로 보인다.

**내 서식이 데이터와 안 맞으면.** 기본 서식으로 대신 만들어 주고 알려 준다. 실행 자체는 성공이고 정산도 그대로다.

**결과가 마음에 안 들면 환불되나.** 아니다. 환불은 **실패**했을 때 책임에 따라 자동으로 된다. 결과 품질은 평점 · 리뷰로 판매자 등급에 반영된다.

**형식이 다른 블록을 이어도 되나.** 된다. 뒤 블록은 앞 결과를 통째로 받아 자기 프롬프트대로 읽는다. 단, 분기는 앞 블록의 출력 예시에 있는 항목만 읽을 수 있다.

**테스트 실행도 돈이 드나.** 판매자에게 정산은 없지만 AI 사용료는 든다. 실제 실행과 같은 경로라 결과와 원가가 실제와 같다. 횟수는 플랫폼이 제한한다.
