# 1부. 현재 동작 (A2A 없음)

## 1. 등장인물과 한 줄 역할

| | 역할 |
| --- | --- |
| **사용자** | 코멘트를 적고 참고 자료를 올리고 실행을 누른다. 그게 전부다 |
| **프론트** | 화면을 그리고 백엔드를 부른다. AI Runtime을 직접 부르지 않는다 |
| **백엔드** | 워크플로우 정의를 갖고 있고, 돈을 차감·적립하고, AI Runtime을 부르고, 결과를 저장한다 |
| **AI Runtime** | 노드를 순서대로 실행하고 PDF를 만든다. 아무것도 기억하지 않는다 |

## 2. 실행 전에 이미 정해져 있는 것

**워크플로우 정의**는 실행 전에 존재한다. **사용자가 캔버스에서 직접 만든다.** 랜딩에서 자연어로 하고 싶은 일을 적으면 마켓의 에이전트를 추천받고, 그중에서 골라 캔버스에 배치하고 연결한 것이 워크플로우가 된다. 저장은 백엔드가 하고, 실행할 때 그 정의를 AI Runtime에 통째로 보낸다.

**AI Runtime은 그 정의가 어디서 왔는지 알 필요가 없다.** 캔버스에서 왔든 코드에 박혀 있든 노드 배열을 받아 순서대로 실행할 뿐이다. 그래서 아래 형식은 프론트 캔버스의 산출물이자 백엔드 저장 형식이자 실행 요청의 본문이다.

```jsonc
{
  "id": "brand_strategy",
  "name": "브랜딩 전략 보고서",
  "nodes": [
    { "id": "market", "name": "시장 조사",      "prompt": "당신은 시장 조사 분석가입니다 …",
      "context": "user", "owner_id": "u_2001", "unit_price": 3.9 },
    { "id": "strategy",  "name": "브랜드 전략 보고서", "prompt": "당신은 브랜드 전략가입니다 …",
      "context": "prev", "owner_id": "u_3001", "unit_price": 4.0 }
  ],
  "output": { "type": "pdf", "title": "브랜딩 전략 보고서" }
}
```

`nodes` 배열의 **순서가 곧 실행 순서**다. 엣지나 그래프 개념은 없다. 캔버스에서 위에서 아래로 연결한 순서를 그대로 배열에 담으면 된다. **계약 확정본에서 `edges[]`가 들어오면 연결선이 실행 순서를 정한다.**

**그래프 규모 상한은 네 가지다.** 캔버스 노드 **8**(에이전트 1개 = 1) · 에이전트 전개 후 **20** · 가능한 최장 경로 **8** · 에이전트 중첩 **1**. 넷 다 워크플로우 정의만 보면 정해지는 정적인 값이라 저장 시점과 실행 시점의 판정이 갈리지 않는다. 프론트 · 백엔드가 저장 단계에서 막고(`POST /v1/workflows/validate`), Runtime도 요청 시점에 다시 검사한다.

## 4. 단계별 상세

### ① 사용자가 하는 일 — 두 가지뿐

1. **코멘트 텍스트를 적는다.** 예: "이번 달은 전반적으로 시험 난이도가 높았음"
2. **엑셀 파일을 고른다.** `.xlsx` `.xls` `.csv`, 최대 10MB

노드별로 따로 입력하는 것은 없다. 첫 노드에만 사람이 값을 주고, 그다음부터는 앞 노드의 결과가 자동으로 흘러간다.

### ② ~ ③ 백엔드가 실행 전에 하는 일

- 워크플로우 정의를 꺼낸다
- **예상 차감액 = 모든 노드의 `unit_price` 합계.** 위 예시는 3.9 + 4.0 = 7.9 ABC
- 사용자 잔액과 비교해 부족하면 실행을 막는다
- 통과하면 7.9 ABC를 **선차감(예치)** 한다

### ④ 백엔드 → AI Runtime

`POST /v1/runs`에 multipart로 세 가지를 담는다. 워크플로우 정의 JSON 문자열, 코멘트, 참고 자료 파일.

**AI Runtime은 즉시 `202`와 `run_id`를 돌려주고 백그라운드에서 실행을 시작한다.** 실행이 끝날 때까지 기다리지 않는 이유는 노드 하나가 평균 25초라 노드 3개면 nginx와 ALB의 기본 타임아웃 60초를 넘기기 때문이다.

### ⑤ 참고 자료를 텍스트로 바꾼다 (LLM 없음)

pandas로 첫 시트를 읽어 **마크다운 표**로 만든다. 여기에 요약 한 줄을 붙인다. 100행이 넘으면 앞 100행만 쓴다.

이렇게 만들어진 것을 **사용자 입력 덩어리**라고 부르자.

```markdown
## 사용자 코멘트
20대 여성 타깃 비건 스킨케어, 프리미엄 포지션으로 가고 싶음

## 참고 자료 — 경쟁사 가격표
### 표 요약
- 행 20개, 열 6개: 브랜드, 제품, 가격, 용량, 주성분, 점유율
- 가격 평균 38,400원 (최저 12,000원, 최고 89,000원)

### 표
| 브랜드 | 제품 | 가격 | 용량 | … |
|:-------|:-----|-----:|-----:|---|
| A사 | 수분 크림 | 32000 | 50ml | … |
| …
```

### ⑥ 노드 1 실행 — `context: "user"`

LLM 호출은 **시스템 메시지와 사용자 메시지 두 덩어리**로 이루어진다.

| 자리 | 내용 |
| --- | --- |
| system | 노드 1의 프롬프트 원문 ("당신은 시장 조사 분석가입니다 …") |
| user | 위의 **사용자 입력 덩어리 전체** |

Gemini가 답한 마크다운 텍스트가 노드 1의 출력이다. 약 2,500자.

### ⑦ 노드 2 실행 — `context: "prev"` ← **여기가 노드 간 결합 지점**

| 자리 | 내용 |
| --- | --- |
| system | 노드 2의 프롬프트 원문 ("당신은 브랜드 전략가입니다 …") |
| user | `## 이전 단계 결과` + **노드 1의 출력 텍스트 전체** |

실제로 보내는 user 메시지는 이렇게 생겼다.

```markdown
## 이전 단계 결과
## 비건 스킨케어 시장 조사 보고서

### 1. 전체 요약
* 경쟁 브랜드: 20곳
* 가격대 분포:
  * 저가 12,000원 ~ 프리미엄 89,000원 (평균 38,400원)
  …

### 2. 경쟁사 표
| 브랜드 | 가격 | 주 타깃 | 핵심 소구점 | 점유율 |
| A사 | 32000 | 20대 여성 | 저자극 | 24% |
…
```

**중요한 세 가지**

1. **노드 2는 참고 자료 원본을 보지 못한다.** 노드 1이 쓴 텍스트만 본다. 그래서 노드 1이 경쟁사 20곳을 표에 다 넣어야 노드 2도 20곳을 쓸 수 있다. 프롬프트가 사실상 계약 역할을 한다.
2. **가공 없이 통째로 붙인다.** 요약하거나 잘라내지 않는다.
3. **LLM은 앞 호출을 기억하지 않는다.** 노드 1을 불렀다는 사실을 Gemini는 모른다. 우리 코드가 노드 1의 응답을 들고 있다가 노드 2의 메시지에 끼워 넣어 다시 보내는 것이다.

`context` 값에 따라 user 메시지가 달라진다.

| 값 | user 메시지 |
| --- | --- |
| `"user"` | 사용자 입력 덩어리 |
| `"prev"` (기본) | 이전 노드 출력만 |
| `"prev+user"` | 이전 노드 출력 + 사용자 입력 덩어리 |

### ⑧ 백엔드는 그동안 2초마다 조회한다

`GET /v1/runs/{run_id}`가 이런 응답을 준다.

```jsonc
{ "status": "running",
  "progress": { "done": 1, "total": 2, "percent": 50,
                "current_node_name": "브랜드 전략 보고서" },
  "nodes": [ { "id": "market", "status": "succeeded", "owner_id": "u_2001", "unit_price": 3.9 },
             { "id": "strategy",  "status": "running",   "owner_id": "u_3001", "unit_price": 4.0 } ],
  "contribution": [ { "node_id": "market", "owner_id": "u_2001", "charged_abc": 3.9 } ] }
```

백엔드가 하는 일이 둘이다.

- **진행 상황을 프론트에 넘긴다.** `progress.current_node_name`과 `done/total`이 실행 게이지에 그대로 들어간다
- **노드가 `succeeded`로 바뀌는 순간 그 노드 원작자에게 정산금을 적립한다.** 워크플로우가 끝나기를 기다리지 않는다. 폴링은 같은 상태를 여러 번 보므로 이미 적립한 노드를 기억해 두 번 적립하지 않아야 한다

### ⑨ 마지막 노드의 출력을 PDF로 만든다 (LLM 없음)

**PDF는 LLM이 만들지 않는다.** 마지막 노드가 낸 마크다운을 코드가 처리한다.

1. 마크다운 → HTML (`#` 제목은 `<h1>`, `|` 표는 `<table>`)
2. 템플릿에 끼워 넣고 제목·날짜를 채운다
3. A4 크기로 그리면서 한글 폰트를 PDF 안에 심는다
4. `report.pdf` 저장

### ⑩ 결과 전달과 정산 마감

- 백엔드가 `GET /v1/runs/{run_id}/pdf`로 파일을 받아 자체 스토리지에 저장한다
- 프론트에는 백엔드가 발급한 다운로드 URL을 준다
- 선차감한 7.9 ABC 중 실제로 실행된 노드분을 확정하고, 나머지가 있으면 환원한다

### 실패했을 때

응답의 `failure`가 이렇게 온다.

```jsonc
"failure": {
  "node_id": "strategy", "error_code": "MODEL_API_ERROR",
  "fault": "supplier",              // supplier | consumer | platform
  "affects_success_rate": true,
  "refund_scope": { "refund_node_ids": ["strategy"], "settled_node_ids": ["market"] } }
```

백엔드는 `settled_node_ids`의 노드는 정산을 유지하고, `refund_node_ids`만큼 사용자에게 환원한다.

## 5. 지금 방식의 한계

| 한계 | 내용 |
| --- | --- |
| **연결 가부를 판정할 수 없다** | 사용자가 캔버스에서 아무 에이전트나 붙일 수 있고, 맞는지는 실행해 봐야 안다. **사용자가 직접 조립하는 제품에서 가장 큰 구멍이다** |
| 노드 출력에 형식이 없다 | 앞 노드가 무엇을 어떻게 쓸지 프롬프트에 의존한다. 필요한 정보를 빠뜨려도 실패로 잡히지 않는다 |
| **분기를 만들 수 없다** | 조건을 비교하려면 값이 필요한데 자유 텍스트에는 비교할 필드가 없다 |
| 조합 오류를 탐지할 수 없다 | 뒤 노드가 입력을 거부하지 않고 그냥 이상한 결과를 낸다. 수요자 책임 판정이 성립하지 않는다 |
| 입력 폼이 고정이다 | 첫 노드가 무엇을 받는지 선언되어 있지 않아 폼을 자동 생성할 수 없다 |

> 첫 줄이 A2A를 도입하는 가장 강한 이유다. 시드 에이전트 15개 중에서 사용자가 골라 조합하려면 그것들이 서로 붙는지 판정할 수 있어야 하고, 공용 스키마 카탈로그가 그것을 보장한다.

# 2부. A2A를 적용하면 무엇이 달라지나

## 6. 핵심 변화 한 줄

> **노드 사이에 흐르는 것이 "자유 텍스트"에서 "형식이 선언된 JSON"으로 바뀐다.**

전송 방식은 바뀌지 않는다. 202 + 폴링, multipart, `run_id`, PDF 다운로드 전부 그대로다. 바뀌는 것은 노드 안에서 오가는 데이터의 모양과, 그것을 다루는 각 파트의 화면·DB다.

## 7. 노드 간 결합이 어떻게 바뀌나

**지금** — 노드 2가 받는 user 메시지

```markdown
## 이전 단계 결과
## 비건 스킨케어 시장 조사 보고서
### 1. 전체 요약
* 경쟁 브랜드: 20곳
…(자유 텍스트 2,500자)
```

**A2A 이후** — 노드 2가 받는 user 메시지

```jsonc
{
  "schema_id": "biz.market_research@1",
  "payload": {
    "summary": { "competitor_count": 20, "avg_price": 38400, "competition_level": "high" },
    "competitors": [
      { "name": "A사", "price": 32000, "target": "20대 여성", "key_point": "저자극",   "share": 0.24 },
      { "name": "B사", "price": 89000, "target": "30대 여성", "key_point": "프리미엄", "share": 0.18 }
    ]
  }
}
```

그리고 노드 1을 호출할 때 **Gemini에 출력 스키마를 함께 넘겨 이 형태로만 답하게 강제한다.** 프롬프트에 "이런 필드로 답해줘"라고 적는 것이 아니라 API 파라미터로 스키마를 준다. 훨씬 안정적이다.

**마지막 노드는 그대로 마크다운을 낸다.** 출력 스키마를 `common.document@1`(마크다운 문자열 한 필드)로 선언하면 되고, PDF 렌더링 과정은 지금과 같다. JSON을 기계적으로 PDF에 박으면 결과물이 허접해지므로 마지막은 사람이 읽을 글을 그대로 받는다.

## 8. 분기가 가능해지는 이유

시장 조사 노드가 `competition_level` 같은 필드를 내놓으므로 값을 비교할 수 있다.

```jsonc
{ "id": "branch1", "type": "branch",
  "condition": { "field": "$.summary.competition_level", "op": "eq", "value": "high" },
  "branches": { "true": "differentiate", "false": "mass_market" } }
```

**분기 노드는 LLM을 부르지 않는다.** 값 비교 한 줄이다. 판단이 필요한 분기는 앞의 LLM 노드가 `competition_level: "high" | "low"` 같은 열거형 필드로 답하게 하고, 분기는 그 값을 비교만 한다. 판단의 비결정성은 LLM 노드 안에 갇히고, 그 노드는 원작자가 있어 실패 책임도 귀속된다.
