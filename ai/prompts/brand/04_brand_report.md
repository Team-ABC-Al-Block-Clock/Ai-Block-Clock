# ④ 브랜드 전략 보고서 프롬프트 (S15P21A403-276)

| 항목 | 내용 |
| --- | --- |
| 노드 | 브랜딩 전략 에이전트 1단계 · 종단 노드 |
| 입력 → 출력 | `biz.strategy_draft@1` → `biz.brand_strategy@1` |
| 합류 | ③a·③b 어느 쪽이 왔든 같은 형식으로 받는다 |
| 하류 | 2단계 ⑤ SNS 캠페인 · ⑥ 광고 카피가 이 출력을 받는다. **템플릿도 여기서 값을 가져간다** |
| 기준 | 스키마 통과율 ≥ 95% · **배열 4종이 모두 정확히 3개** |

---

## ⚠ 1. A에게 확인이 필요한 것 — `brand_name` 의 출처

`biz.brand_strategy@1` 은 `brand_name` 을 **필수**로 요구한다. 그런데 이 노드의 입력인
`biz.strategy_draft@1` 에는 브랜드명이 없다.

```
strategy_draft@1 의 필드 :  approach · positioning · rationale_md · core_strategies
                            ↑ brand_name 이 없다
```

즉 **지금 명세대로면 ④는 브랜드명을 알 수 없다.** 세 가지 가능성이 있다.

1. Runtime 이 원본 브리프를 함께 넘겨준다
2. `issued_on`·`author_org` 처럼 Runtime 이 `brand_name` 도 채운다
3. `strategy_draft@1` 에 `brand_name` 이 빠진 것이다 (스키마 누락)

**가정하고 진행한다 — 1번.** user 프롬프트에 브리프의 브랜드명을 함께 넣는 것을 전제로
썼다 (로드맵 §7: *"기다릴 수 없으면 가정을 적고 진행한 뒤 알려 준다"*).
A가 다르게 정하면 user 블록의 `{brand_name}` 줄만 고치면 된다.

## 2. 배열이 전부 3개 고정인 이유, 그리고 위험

`purpose` · `positioning` · `reasons` · `core_strategy` 네 배열이 모두 **minItems 3 · maxItems 3**.
템플릿 서식의 칸 수와 맞춘 것이다 (A 결정).

**LLM 이 가장 자주 틀리는 형태가 개수다.** 2개만 쓰거나 5개를 쓴다. 특히 앞선 노드에서
`core_strategies` 를 4~5개 받았을 때 그대로 옮기려다 넘긴다.

그래서 프롬프트에서 **"3개를 고른다"는 행위를 명시**했다. 옮겨 적는 게 아니라 고르는
일이라고 하면 개수를 세게 된다. 4개를 받았을 때 무엇을 버릴지도 기준을 줬다.

## 3. Runtime 이 채우는 필드는 건드리지 않는다

`issued_on`(발행일) · `author_org`(작성 기관)는 **Runtime 이 채운다.** LLM 이 날짜나
기관명을 지어내지 않게 하려는 A의 설계다.

최신 Runtime은 LLM 응답 스키마에서 두 필드를 제외하고 검증 전에 주입한다.
따라서 LLM은 **두 필드를 출력하지 않는다.** 준수율 검사기는 Runtime 주입 전 응답을
검사하며, 이전 초안의 빈 문자열도 허용하되 날짜·기관명을 직접 채우면 실패로 센다.

[이 노드가 하는 일]
새 전략을 만드는 게 아니라 **받은 전략을 보고서 형식에 맞게 다듬는 일**이다.
초안에 없는 전략을 새로 추가하지 않는다. 초안의 방향을 뒤집지 않는다.

[개수 규칙 — 가장 중요하다]
purpose · positioning · reasons · core_strategy 는 **각각 정확히 3개**다.
2개도 4개도 안 된다. 서식의 칸이 3개씩이라 개수가 맞지 않으면 보고서가 깨진다.

초안의 core_strategies 가 4개나 5개로 오는 경우가 있다. 그때는 옮겨 적는 것이 아니라
**3개를 고르는 것**이다. 고르는 기준은 이 순서다.
  1) 초안의 positioning 을 가장 직접적으로 실현하는 것
  2) 읽고 바로 무엇을 할지 그림이 그려지는 것
  3) 나머지 둘과 겹치지 않는 것
3개보다 적게 왔다면, 초안의 rationale_md 에서 근거를 찾아 같은 방향으로 채운다.

[Runtime 이 채우는 필드]
issued_on 과 author_org 는 **출력하지 않는다.**
날짜나 기관명을 절대 지어내지 않는다. 실행 시스템이 나중에 채운다.

[각 항목 작성 지침]
- brand_name: 제공된 브랜드명을 그대로 쓴다. 바꾸거나 다듬지 않는다.

- headline: 표지에 들어갈 한 문장. 20자 내외.
  브랜드가 무엇이 되려는지를 담는다. 회사 슬로건처럼 짧고 단정하게 쓴다.
  느낌표를 쓰지 않는다. 보고서 표지다.

- purpose(브랜드 목적) 3개: 이 브랜드가 왜 존재하는가.
  label 만 있는 한 줄 항목이다. 10~20자 명사구로 쓴다.

- positioning(브랜드 포지셔닝) 3개: 초안의 positioning 한 문장을 세 갈래로 펼친다.
  누구에게 / 무엇으로 / 어떻게 기억될지. 각 10~20자 명사구.

- reasons(선택의 이유) 3개: 고객이 이 브랜드를 고를 이유.
  axis 는 관점의 이름이다 — 서로 다른 세 축을 쓴다 (예: 기능 / 메시지 / 제품).
  detail 은 그 축에서 왜 우리를 고르는지 한 문장.

- core_strategy(핵심 전략) 3개: 초안의 core_strategies 에서 고른다. 위 개수 규칙 참고.
  label 만 있는 한 줄 항목이므로, 초안의 label 을 살리되 길면 줄인다.

- messages(메시지 체계): 세 문장이 한 벌이다. 같은 말을 세 번 쓰지 않는다.
  · core  — 광고에 한 줄만 쓴다면 이것. 20자 내외
  · sub   — core 를 뒷받침하는 설명. 30자 내외
  · daily — 고객이 일상에서 쓸 법한 말투. 20자 내외

- summary_md: 보고서를 덮고 나서 남는 한 문단. 3~5문장. 마크다운 허용.
  전략을 요약하되, 무엇을 하지 않기로 했는지도 한 문장 넣는다.

[하지 않을 것]

- 채널·예산·일정을 정하지 않는다 (2단계 ⑤⑦의 몫이다).

## 5. 채점 기준

| # | 항목 | 실패 조건 |
| --- | --- | --- |
| ① | **개수 고정** | `purpose`·`positioning`·`reasons`·`core_strategy` 중 하나라도 3개가 아님 |
| ② | **지어낸 발행 정보** | Runtime 주입 전 응답의 `issued_on` 또는 `author_org` 에 비어 있지 않은 값이 있음 |
| ③ | 브랜드명 변형 | `brand_name` 이 입력과 다름 |
| ④ | headline 길이 | 30자 초과 또는 느낌표 포함 |
| ⑤ | 메시지 중복 | `messages` 의 `core`·`sub`·`daily` 중 둘 이상이 거의 같은 문장 |
| ⑥ | 축 중복 | `reasons[].axis` 세 개 중 둘 이상이 같은 관점 (사람 확인) |
| ⑦ | 전략 신설 | `core_strategy` 에 초안 `core_strategies` 에 없던 내용이 등장 |
| ⑧ | 월권 | 채널명·예산·일정이 등장 |
| ⑨ | 지어낸 수치 | 초안에 없는 숫자가 등장 |

**①과 ②가 대표 지표다.**

- ①은 **템플릿이 깨지는 문제**다. 09-22~23 에 붙일 서식이 3칸 기준이라,
  개수가 틀리면 시연 화면에서 바로 드러난다
- ②는 **가짜 정보가 보고서에 찍히는 문제**다. 발행일이 지어내진 채로 나가면
  산출물 신뢰도가 통째로 흔들린다. 값이 비어 있는 건 Runtime 이 채우면 되지만,
  틀린 값이 들어 있으면 채울 자리가 이미 없다

### 미달일 때 고치는 순서

1. ①이 걸리면 → system 의 개수 규칙을 user 블록 끝에도 한 번 더 넣는다
   (지시가 멀리 있을수록 잘 잊는다)
2. ②가 걸리면 → Runtime 필드를 출력하지 않는다는 지시를 확인한다
3. ⑦이 걸리면 → "고르는 것이지 만드는 것이 아니다"를 더 강하게 쓴다
