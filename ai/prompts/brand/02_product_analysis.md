# ② 제품 분석 프롬프트 (S15P21A403-276)

| 항목 | 내용 |
| --- | --- |
| 노드 | 브랜딩 전략 에이전트 1단계 · 두 번째 노드 |
| 입력 → 출력 | `biz.brand_brief@1` → `biz.product_analysis@1` |
| 병렬 | ① 시장 조사와 **동시에** 돈다. **①의 결과를 보지 못한다** |
| 기준 | 스키마 통과율 ≥ 95% |

---

## 1. 이 노드의 제약 — 시장을 모른 채 제품만 본다

①과 병렬로 돌기 때문에 **경쟁사도, 트렌드도, `competition_level` 도 모른다.**
브리프 한 장만 보고 쓴다.

그래서 "경쟁사 대비 강점" 같은 말을 쓰면 안 된다. 비교 대상을 모르는데 비교하면
지어내는 것이다. **이 노드는 제품 자체의 성질만 말하고, 시장과 맞붙이는 일은
③a·③b 가 두 결과를 다 받고 나서 한다.**

## 2. 약점을 실제로 쓰게 만드는 것이 관건

LLM 은 약점을 물으면 약점처럼 생긴 칭찬을 쓴다.
"친환경 소재라 원가가 조금 높습니다" 같은 문장이 전형이다 — 읽고 나면 장점만 남는다.

`weaknesses` 가 비어 있으면 ③a·③b 가 쓸 재료가 반쪽이 된다. 차별화 전략은
"우리가 약한 지점을 어떻게 비켜 갈 것인가"가 절반이기 때문이다.

그래서 **약점의 정의를 "고객이 구매를 망설일 이유"로 못박았다.** 우리 사정이 아니라
고객 입장에서 쓰게 하면 칭찬으로 도망가기 어렵다.

## 3. 프롬프트

<!-- prompt:system -->
```
당신은 소비재 제품 기획자다. 브랜드 기획 요청서를 받아 제품 분석 결과를 작성한다.

[이 분석의 범위]
- 요청서에 적힌 제품 하나만 본다. 시장 상황·경쟁사·업계 트렌드는 다루지 않는다.
  (그쪽은 다른 담당자가 동시에 작성하고 있다. 여기서 추측해서 쓰면 서로 어긋난다.)
- "경쟁사 대비", "업계 평균보다" 같은 비교 표현을 쓰지 않는다. 비교 대상을 모른다.
- 숫자를 지어내지 않는다. 요청서에 있는 수치만 쓴다.

[사진이 첨부된 경우]
- 제품 사진이 함께 왔으면 사진에서 확인되는 것(형태 · 소재 · 색 · 패키지 문구)을
  strengths · weaknesses 의 근거로 쓴다. 사진에 없는 것을 본 것처럼 쓰지 않는다.
- 사진이 없으면 요청서만으로 쓴다. 사진이 없다는 말은 하지 않는다.

[각 항목 작성 지침]
- strengths: 제품이 실제로 잘하는 것 2~5개.
  label 은 5~15자 명사구, detail 은 한 문장.
  요청서의 '차별점'을 그대로 옮겨 적지 말고, 그것이 고객에게 무엇을 해 주는지로 바꿔 쓴다.

- weaknesses: 2~5개. **고객이 구매를 망설일 이유**를 쓴다.
  우리 사정(원가·생산 난이도)이 아니라 고객이 느낄 불편·불안·부담으로 쓴다.
  좋게 들리게 다듬지 않는다. "장점의 이면" 형태로 쓰면 약점이 아니다.
  예를 들어 가격이 높다면 "왜 비싼지 설명이 필요하다"가 아니라
  "같은 쓰임의 더 싼 제품이 있는데 굳이 이걸 살 이유를 모른다"로 쓴다.

- opportunities: 2~5개. 약점을 덮거나 강점을 키울 여지.
  label 만 있는 한 줄짜리 항목이다. 짧은 명사구로 쓴다.

[요청서의 '추가 요청']
하지 말라고 적힌 것은 여기서도 지킨다. 표현 방식에 대한 요청이면 문장에 반영한다.
```

<!-- prompt:user -->
```
[브랜드 기획 요청서]
- 브랜드명: {brand_name}
- 제품 카테고리: {category}
- 핵심 고객: {target}
- 가격대: {price_tier}
- 차별점: {differentiator}
- 추가 요청: {comment}

위 요청서로 제품 분석 결과를 작성해 주세요.
```

```
[참고 — weaknesses 를 쓰는 방식]

이렇게 쓰지 않는다 (약점처럼 생긴 칭찬):
  · "친환경 소재를 써서 원가가 다소 높습니다"
  · "기능이 많아 처음에는 익숙해지는 시간이 필요합니다"

이렇게 쓴다 (고객이 망설이는 지점):
  · label: 가격 대비 체감 어려움
    detail: 같은 값에 대용량 제품을 살 수 있는데, 차이를 써 보기 전에는 알 수 없다.
  · label: 교체 시점을 놓침
    detail: 언제 갈아야 하는지 눈으로 표시되지 않아 계속 쓰게 된다.
```

## 4. 채점 기준

| # | 항목 | 실패 조건 |
| --- | --- | --- |
| ① | 항목 수 | `strengths`·`weaknesses`·`opportunities` 중 하나라도 2~5개를 벗어남 |
| ② | **약점 회피** | `weaknesses` 의 `detail` 이 전부 긍정어로 끝남 (아래 판정 참고) |
| ③ | 월권 | 경쟁사명이나 "경쟁사 대비" · "업계 평균" 같은 비교 표현이 등장 |
| ④ | 지어낸 수치 | 요청서에 없는 숫자가 등장 |
| ⑤ | 차별점 복사 | `strengths` 의 `detail` 이 요청서 `differentiator` 와 거의 같은 문장 |
| ⑥ | 요청 위반 | `comment` 에서 하지 말라고 한 것을 함 |

**②의 판정 방법** — 자동으로 완전히 가리기는 어렵다. 측정 스크립트에서는
`weaknesses[].detail` 에 아래 표현이 있으면 걸러 두고 사람이 확인한다.

```
"~하지만", "~라는 장점", "오히려", "덕분에", "대신"
```

완벽한 검사가 아니라 **의심 목록을 만드는 장치**다. 약점 회피는 자동 판정이 어려운
항목이라 사람이 한 번은 봐야 한다.
