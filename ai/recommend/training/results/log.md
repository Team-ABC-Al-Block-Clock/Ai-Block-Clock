### 관찰

1. **단어가 겹치지 않아도 정답이 잡힌다.** "부모님께 보낼 안내문" → "가정통신문 작성기"가 세 모델 모두에서 1등.
   키워드 검색으로는 불가능한 매칭이며, 임베딩 방식의 타당성이 확인됨 (MKT-002 근거)

2. **Recall@3만으로는 모델을 선정할 수 없다.** 세 후보가 전부 1.00으로 동점.
   1등 정답률과 MRR을 추가하자 KURE-v1이, 1·2등 격차를 추가하자 e5-base가 갈렸다.
   → **지표 설계가 곧 선정 근거.** 골든 쿼리와 MRR 도입 필요성이 실측으로 확인됨 (MKT-003 근거)

3. **크고 최신인 모델이 우리 문제에 더 맞지는 않았다.** 한국어 검색 특화 대형 모델(KURE-v1)이
   경량 SBERT보다 1등 정답률·격차·지연 모두에서 밀림. 에이전트 20~30개 규모에서는
   모델 용량보다 **정답/오답 변별력**이 중요하다는 방향

4. **모델 로딩 6~8초 vs 질의 30ms — 약 200배 차이.**
   FastAPI lifespan에서 1회만 로드하는 설계(가이드 §12.7)의 정량 근거

## 2026-09-11 — 추천 API 구현 (`runtime-recommend`)

**산출물.** FastAPI 서비스 · `POST /v1/recommend` · `POST /v1/index/agents` · `GET /health`
명세는 `ai/docs/recommend-api.md` 로 분리해 프론트·백엔드에 공유.

### 실측

| 항목 | 결과 |
| --- | --- |
| 인덱싱 | 에이전트 20개 `rebuild` 성공 |
| 데모 질의 4개 | **4/4 1등 정답** |
| 응답 시간 | **27~36ms** (목표 1초 대비 30배 여유) |

### 설계 판단 3가지

**① 모델은 프로세스 기동 시 1회만 로드한다 (lifespan).**
09-08 실측에서 모델 로딩 6~8초 vs 질의 22ms — 약 300배 차이다. 요청마다 로드하면
사용자가 매번 그 시간을 기다린다. FastAPI `lifespan` 으로 기동 시 한 번만 올린다.

**② 실행 엔진(`runtime-api`)과 프로세스를 분리한다.**
임베딩 모델이 메모리를 약 0.4GB 쓴다. 실행 워커에 같이 올리면 워커 수 × 0.4GB 가
그대로 낭비된다. 별도 컨테이너로 띄워 모델을 한 벌만 유지한다.

**③ 인덱스는 상태가 아니라 파생 캐시다.**
원본은 백엔드 MySQL 이고, 인덱스는 거기서 언제든 다시 만들 수 있다. 그래서
스냅샷(`.npz`)은 커밋하지 않고, `model_version` 이 다르면 복원하지 않고 버린다.
재기동 시 백엔드가 `rebuild` 를 보내는 것이 정상 경로다.

### 보안 — 인덱싱 요청에 프롬프트 원문을 넣지 않는다 (SEC-001)

임베딩 벡터에서 원문이 어느 정도 복원될 수 있다는 연구가 있다. 프롬프트가 인덱스에
들어가면 "어떤 경로로도 노출되지 않아야 한다"를 정면으로 어긴다. 인덱싱 요청 스키마를
**마켓에 공개되는 필드로만** 한정하고, 명세서에 경고를 명시했다.

내부 호출이라도 `X-ABC-Service-Token` 을 요구한다. 인덱스를 누구나 조작할 수 있으면
추천 결과를 조작해 특정 에이전트의 정산금을 늘릴 수 있다.

## 2026-09-14 — 파인튜닝 1차 (`abc-agent-retriever-v1`)

**환경.** SSAFY GPU 개발 서버 (배정 device 1) · conda `abc` · torch 2.11.0+cu128
**학습.** `MultipleNegativesRankingLoss` · 삼중항 680개 · batch 16 · lr 2e-5 · **3 epoch · 19초**
**데이터 분할.** 합성 질의 420개 → 학습 340 / holdout 80 (에이전트당 4개 균등, seed 42)

### 평가 설계 — 왜 지표를 새로 만들었나

09-09 시점에 골든 쿼리 22개는 이미 **1등 정답률 100% · MRR 1.000** 이었다.
천장에 닿은 지표로는 개선도 악화도 보이지 않는다. 두 축으로 나눴다.

| 세트 | 역할 |
| --- | --- |
| **holdout 80개** | 학습에서 한 번도 안 본 질의. 순위 지표가 아직 천장이 아니라 변화가 보인다 |
| **골든 쿼리 22개** | 안전망. 사람이 쓴 구어체에서 **떨어지지 않았는지**만 본다 |
| **1·2등 격차** | 대표 지표. 순위가 이미 맞는 상태에서 "얼마나 확신하고 맞히는가" |

### 하드 네거티브 채굴 — 설계한 함정이 실제로 작동했다

파인튜닝 전 모델의 학습셋 1등 오답률 **76/340 (22.4%)**. 가장 자주 헷갈린 쌍:

| 횟수 | 정답 → 잘못 올라온 것 |
| --- | --- |
| 17 | 학업 성취도 통계 산출기 → 성적 데이터 분석기 |
| 16 | 마감 임박 업무 알림 정리 → 할 일 추출기 |
| 16 | 주간 일정 브리핑 → 마감 임박 업무 알림 정리 |
| 14 | 성적 데이터 분석기 → 학업 성취도 통계 산출기 |

1위와 4위는 **09-08에 판별 테스트용으로 일부러 심어둔 유사 쌍**(`ag_seed_01` ↔ `ag_seed_03`)이다.
"여기서 흔들릴 것"이라 설계한 지점에서 실제로 흔들렸고, 그 쌍을 집중 학습시켰다.

### 결과 — 3 epoch 채택

| | 파인튜닝 전 | 3 epoch | 5 epoch |
| --- | --- | --- | --- |
| holdout 1등 정답률 | 70.0% | **82.5%** | 82.5% |
| holdout MRR | 0.8256 | **0.9010** | 0.9050 |
| holdout 1·2등 격차 | 0.0981 | **0.2810** | 0.3326 |
| 골든 1등 정답률 | 100% | **100% 유지** | 95.5% ▼ |
| 골든 MRR | 1.0000 | **1.0000 유지** | 0.9773 ▼ |
| 골든 1·2등 격차 | 0.1152 | **0.3052** | 0.3694 |
| 맞힌 질의 순증 (102개 중) | — | **+10개** | +9개 |

**5 epoch 의 더 큰 격차는 외워서 만든 자신감이었다.** 학습 손실이 0.0015까지 떨어졌고
(3 epoch 은 0.0088), 학습 데이터에서는 더 확신했지만 사람이 쓴 골든 쿼리에서 하나를 놓쳤다.
holdout 정답률은 두 설정이 동일하므로, **안전망을 지킨 3 epoch 을 채택**한다.

로컬 서비스 반영 후 데모 질의 4개 재확인 — 4/4 1등, 31~38ms.
`성적 데이터 분석기` 0.572 vs `학업 성취도 통계 산출기` 0.328 으로 유사 쌍이 확실히 분리됐다.

### 판정 기준을 중간에 고쳤다

`evaluate_finetune.py` 의 자동 판정은 처음에 **"골든 쿼리가 1개라도 떨어지면 과적합"** 이었다.
5 epoch 결과를 이 기준으로 보면 "과적합"인데, 원데이터를 세어보면 holdout **+10개** /
골든 **−1개** 로 **순증 +9개**다.

원인은 **세트 크기가 다른 두 지표를 퍼센트로 비교한 것**이다.
22개 중 1개 = 4.5%, 80개 중 10개 = 12.5% — 퍼센트만 보면 비슷해 보이지만 실제 무게는 10배 차이다.
판정을 **맞힌 질의 개수 합산**으로 바꿨다. 자동 판정의 결론을 그대로 쓰지 않고
근거를 다시 계산한 것이 이번 실험에서 가장 중요한 수정이다.

### 한계 — 남은 오답 14개는 모델 문제가 아니다

holdout 오답 14개가 3 epoch 과 5 epoch 에서 **완전히 동일**하다. 더 학습시켜도 안 고쳐진다는 뜻이다.
내용을 보면 원인이 드러난다.

> "점수표 넣으면 통계 내주는 거" → `성적 데이터 분석기` 와 `학업 성취도 통계 산출기` **둘 다 맞다**

**평가 라벨이 단일 정답을 가정하는데 도메인에는 복수 정답이 있다.** 유사 쌍을 일부러
만들어놓고 정답을 하나만 달았기 때문에 생긴 구조적 상한이다. 즉 실제 정답률은
측정값 82.5%보다 높다. 해소하려면 라벨을 복수 정답으로 바꾸고 지표도
Recall@K 계열로 함께 봐야 하는데, 2주 일정에서는 **한계로 명시하고 넘어간다.**

### 운영 주의 — 모델이 바뀌면 전체 재색인이 필요하다

가중치가 바뀌면 **벡터 공간 자체가 달라진다.** 기존 인덱스의 벡터와 새 모델이 만든
질의 벡터는 비교할 수 없다. 스냅샷은 `model_version` 이 다르면 자동으로 버리도록 되어 있고,
백엔드에는 `op: "rebuild"` 요청을 보내달라고 전달해야 한다.

- `model_version`: `ko-sroberta-multitask-pretrained` → **`abc-agent-retriever-v1`**
- 가중치는 커밋하지 않는다 (`ai/.gitignore` 의 `models/`). 파일 전달로 공유한다
- 근거 자료는 커밋한다 — `results/eval_finetune.json`(3 epoch) · `eval_finetune_ep5.json`(5 epoch)

## 2026-09-17 — 하이브리드 검색 (BM25 + 임베딩)

| 항목 | 내용 |
| --- | --- |
| 이슈 | `S15P21A403-280` |
| 모델 | `abc-agent-retriever-v1` (09-14 파인튜닝) |
| 결론 | **가중합 `W_LEXICAL=0.05` 채택.** RRF 는 탈락 |

### 만들기 전에 잰 것 — BM25 가 도움이 되는가

임베딩만으로 부족한 지점이 있다. 임베딩은 "뜻이 가까운 것"을 찾는 게 강점인데,
뒤집으면 **단어가 정확히 겹치는 경우를 특별히 대우하지 않는다.**

그래서 코드를 쓰기 전에 BM25 단독 성능부터 쟀다.

| | 골든 22개 | holdout 80개 |
| --- | --- | --- |
| BM25 단독 | 68.2% | **67.5%** |
| 임베딩 (파인튜닝) | 100% | **82.5%** |

BM25 가 전반적으로 15%p 낮다. 그런데 **임베딩이 틀린 holdout 질의 5개 중 3개를
BM25 는 1등으로 맞혔다.**

```
맞힘  "점수표 넣으면 통계 내주는 거"            → 성적 데이터 분석기
맞힘  "다음에 확인할 것까지 같이 적어줘"         → 학습 상담 기록 정리기
맞힘  "참석 못한 사람한테 공유할 요약본 만들어줘"  → 회의록 요약기
```

**두 방식이 서로 다른 질의에서 틀린다.** 이 상보성이 하이브리드를 시도할 근거였다.

### 두 가지 융합 방식을 같이 쟀다

로드맵은 RRF 를 지정했지만, RRF 에는 이 프로젝트에 불리한 성질이 있다.
**순위만 쓰고 점수를 버리기 때문에 1·2등 격차가 뭉개진다** — 09-14 파인튜닝에서
대표 지표로 삼은 바로 그 값이다. 그래서 점수를 살리는 가중합도 만들어 함께 쟀다.

| 모드 | 골든 22개 | holdout 80개 | 1·2등 격차 (holdout) |
| --- | --- | --- | --- |
| off (임베딩 단독) | 100.0% | 82.5% | 0.2810 |
| rrf | **86.4%** | **75.0%** | 0.0268 |
| **weighted 0.05** | **100.0%** | **86.2%** | 0.2780 |
| weighted 0.10 | 95.5% | 87.5% | 0.2833 |
| weighted 0.15 | 95.5% | 85.0% | 0.3005 |
| weighted 0.20 | 95.5% | 83.8% | 0.3119 |

### RRF 가 무너진 이유

**성능 차가 큰 두 랭킹을 동등하게 취급했기 때문이다.** RRF 는 점수를 버리고 순위만
쓴다. BM25 가 15%p 뒤처지는데도 "BM25 에서 1등"과 "임베딩에서 1등"이 같은 무게를
갖는다. 나쁜 쪽이 좋은 쪽을 끌어내렸다.

1·2등 격차가 0.2810 → 0.0268 로 10분의 1이 된 것도 예상대로다. 순위만 쓰면
점수 간격이 사라진다.

> **배운 것.** 상보성만으로는 앙상블이 성립하지 않는다. **상보성과 성능 균형이
> 둘 다** 필요하고, 균형이 깨졌을 때는 순위 기반 융합이 아니라 **비중으로 차이를
> 반영하는 점수 기반 융합**을 써야 한다.

### 가중치가 관건이었다

처음에 `W_LEXICAL=0.2` 하나만 재고 "골든 −1 · holdout +1, 순증 0" 으로 실패라고
판단했다. 가중치를 훑어보니 그게 아니었다.

```
0.05   골든  +0  ·  holdout  +3     ← 채택
0.10   골든  -1  ·  holdout  +4
0.15   골든  -1  ·  holdout  +2
0.20   골든  -1  ·  holdout  +1
```

**어휘 신호는 조금만 얹으면 이득이고 많이 얹으면 손해다.** 임계가 0.05~0.10 사이에
있다. 0.10 이 holdout 은 더 오르지만(+4) 골든 쿼리를 하나 잃어서, **사람이 쓴 골든
쿼리 100% 유지를 우선**해 0.05 를 골랐다.

한 값만 재고 "효과 없음"으로 닫았으면 잘못된 결론을 log 에 남길 뻔했다.

### 구현 메모

- **문자 bigram 토크나이징.** 한국어는 조사 때문에 공백으로 자르면 '점수표를' 과
  '점수표' 가 다른 토큰이 된다. 2글자씩 자르면 두 토큰이 겹친다. 형태소 분석기는
  정확하지만 JVM 의존성이 붙어 컨테이너가 커진다 — 의존성 0개로 갔다
- **필터는 융합 후에 건다.** 카테고리 필터를 융합 전에 걸면 후보 집합이 달라져
  같은 에이전트가 필터 유무에 따라 다른 점수를 받는다
- **`breakdown.semantic` 은 순수 코사인 유사도를 유지**하고 `lexical` 을 따로 추가했다.
  정렬은 융합값(`relevance`)으로 하되 진단 정보는 원래 값을 남긴다
- `ABC_HYBRID=off` 로 즉시 되돌릴 수 있다. 로드맵 §2.3 컷 2순위 항목이라
  시연 직전에 문제가 생겨도 손쓸 수 있어야 한다

워크플로우로 이어지는 에이전트들이 같이 올라온다.

### ★ 새로 알게 된 것 — BM25 는 에이전트를 추가하면 기존 점수가 전부 바뀐다

골든 1개가 깨졌는데, 원인이 예상과 달랐다.

```
"학부모랑 얘기한 내용 문서로 남겨야 해"
    정답 학습 상담 기록 정리기 → 2위 · 1위는 가정통신문 작성기
```

**둘 다 기존 시드다.** 브랜딩 에이전트가 자리를 뺏은 게 아니다. 그리고 이 질의는
`weighted` 에서만 깨지고 `off` 에서는 멀쩡하다(22/22). 즉 **BM25 가 뒤집었다.**

왜 에이전트를 추가했는데 관계없는 두 시드의 순위가 바뀌는가.

> BM25 점수는 **코퍼스 전체에 의존한다.** 역문서빈도(idf)는 전체 문서 수로 계산하고,
> 길이 정규화는 평균 문서 길이(avgdl)로 나눈다. 문서가 20 → 24개가 되면 이 두 값이
> 바뀌고, **손대지 않은 기존 문서들의 점수도 전부 따라 바뀐다.**
>
> 임베딩은 문서마다 독립으로 계산되므로 이런 일이 없다. 09-17 에 20개로 쟀을 때
> 골든이 100% 였던 것이 24개에서도 100%라는 보장이 안 되는 이유가 이것이다.

**운영 규칙으로 남긴다. 에이전트를 추가하거나 설명문을 고치면 골든 쿼리를 다시 잰다.**
`-278` 재색인(09-22) 때도 같은 이유로 재측정이 필요하다. 하이브리드를 켜 둔 이상
"색인 내용이 바뀌면 랭킹이 바뀐다"가 상시 조건이다.

### 임시 설명문이 너무 넓게 쓰인 흔적

holdout 12개 미스 중 브랜딩이 1위를 뺏은 것이 2건 있다.

```
"PR 올리기 전에 한번 봐줘"   → 1위 통합 마케팅 실행안 작성기
"feat인지 fix인지 정해줘"     → 1위 광고 카피 생성기
```

개발 도메인 질의에 마케팅 에이전트가 올라왔다. "한번 봐줘" · "정해줘" 같은 일반적인
표현이 겹친 것으로 보인다. **09-21 정식 설명문을 쓸 때 좁혀야 할 지점**이고,
그때 이 측정을 다시 돌려 확인한다.

브랜딩 1개 미스(`"한 줄로 각인되는 홍보 문장"` → 1위 커밋 메시지 작성기)도
브랜딩끼리의 문제가 아니다. 2위라 상위 8에는 들고, 시연 질의는 1위가 나온
`"광고에 쓸 문구랑 해시태그 뽑아줘"` 를 쓰면 된다.

### ★ `HF_HUB_OFFLINE=1` — 실패를 앞당기는 장치

sentence-transformers 는 기동할 때마다 허브에 모델 갱신을 확인하러 간다. 로컬은
인터넷이 되니 조용히 넘어가지만 EC2 에서 막히면 **기동 중에 멈춘다.**

껐을 때의 부수 효과가 더 중요하다. `config.py` 는 가중치가 없으면 사전학습 모델로
넘어가는데, 오프라인이라 받지 못하고 **기동 단계에서 명확히 죽는다.**
조용히 다른 모델로 도는 것보다 낫다 — 벡터 공간이 달라 추천이 미묘하게 어긋나고,
시연 중에는 원인을 찾을 수 없다. **틀린 채로 도는 것보다 안 뜨는 게 낫다.**

### 겪은 것

- **`python:3.11-slim` 으로 빌드 실패.** `requirements.txt` 는 로컬 venv 에서 버전을
  따왔으면서 베이스 이미지는 관례대로 3.11 을 골랐다. numpy 2.5.3 이 3.12 이상을
  요구해 설치가 막혔다. **개발 환경과 컨테이너의 파이썬을 맞춰야 한다**는 게 교훈이다
- **이미지 1.98GB 는 목표(1.5GB)를 넘겼다.** 다만 CUDA 가 딸려왔다면 3~4GB 가 된다.
  전송량(426MB)이 작고 디스크는 297GB 여유라 그대로 간다. 더 줄이려면 multi-stage
  빌드로 pip 캐시·빌드 도구를 떼는 방법이 있으나 시연 범위에서 얻을 게 없다
- `compose.prod.yaml` 을 따로 만들었다가 없앴다. ai-runtime 은 운영·로컬 차이를
  환경변수로만 두는데, 두 서비스가 다른 구조면 CI 잡도 갈라진다
