# AI Runtime 연동 — 백엔드 확인 요청

| | |
| --- | --- |
| 보내는 쪽 | 백엔드 |
| 기준 문서 | `ai/docs/integration-guide.md` (v1.0) |
| 급한 것 | 1번 (전송 방식) · 2번 (분기 세부) |

연동 가이드를 기준으로 실행 파이프라인을 만들고 있습니다. 진행하면서 **답이 있어야 설계가 확정되는 것**들이
모였습니다. 급한 순서로 적었고, 3번 이하는 답이 늦어도 지금 작업은 막히지 않습니다.

---

## 1. 전송 방식을 Redis Streams 로 바꿀 수 있을까요 — 제안

지금 계약은 `POST /v1/runs` 로 접수하고 `GET /v1/runs/{id}` 를 2초마다 조회하는 방식입니다.
이것을 **Redis Streams 기반으로 바꾸는 것**을 제안드립니다.

### 왜

**폴링이 사라집니다.** 백엔드가 2초마다 묻는 루프, 타임아웃 판정, 스케줄러가 전부 없어집니다.

**진행 상황을 밀어줄 수 있습니다.** 노드가 끝날 때마다 이벤트를 쓰면, 사용자 화면까지 진짜 push 가 됩니다.
지금은 저희가 폴링한 결과를 SSE 로 중계하는 구조입니다.

**60초 타임아웃 제약이 없어집니다.** 202 + 폴링 구조 자체가 nginx 타임아웃 때문에 나온 것으로 이해하고 있습니다.

**실행 상태가 메모리에만 있는 문제**가 완화됩니다. 재배포 중에 진행 이벤트가 유실되더라도
Stream 에 남아 있으면 저희가 이어받을 수 있습니다.

### 그림

```
백엔드                    MinIO              Redis Stream            AI Runtime
  │ 파일 저장 ──────────────▶│
  │ 실행 요청 ────────────────────────────────▶│
  │                                             │ ──▶ 꺼낸다
  │                          │ ◀───────────────────── 파일 읽는다
  │                                                   노드 1 실행
  │ 구독 ◀───────────── 진행 이벤트 ◀────────────────
  │                                                   노드 2 실행
  │                          │ ◀───────────────────── PDF 쓴다
  │ 구독 ◀───────────── 완료 이벤트 ◀────────────────
```

파일은 Stream 에 싣지 않고 **MinIO 에 두고 키만 넘기는** 방식을 생각하고 있습니다.
저희는 입력 파일과 결과 PDF 를 **어차피 보관해야 해서** 스토리지를 두기로 했습니다.

### 여쭙고 싶은 것

| | |
| --- | --- |
| **1-1** | Redis Stream 을 읽고 쓰는 방식으로 바꿀 수 있을까요. 작업량이 어느 정도일지도 알려주시면 좋겠습니다 |
| **1-2** | MinIO(S3 호환)에서 입력 파일을 읽고 결과 PDF 를 쓰는 것이 가능할까요 |
| **1-3** | 노드가 끝날 때마다 진행 이벤트를 쓰는 것이 가능할까요 |
| **1-4** | 가능하다면 이벤트 형식과 Stream 이름을 어떻게 정할까요. 초안을 주시면 저희가 맞추겠습니다 |

### 안 된다면

**지금 계약(HTTP + 폴링) 그대로 갑니다.** 저희 쪽은 전송 방식을 인터페이스 뒤에 두고 만들고 있어서
도메인은 바뀌지 않습니다. **부담되시면 편하게 말씀해 주세요.**

다만 그 경우 **결과 PDF 를 저희가 받아서 스토리지에 옮기는** 구조가 되는데, 그건 지금 계약대로입니다.

## 2. 분기 — 지원해 주시기로 한 것의 세부

if-else 분기를 지원해 주시기로 한 것으로 알고 있습니다. **병합은 저희도 쓰지 않습니다.**
들어오는 연결선이 노드마다 하나뿐이라 그래프가 트리로 유지됩니다.

| | |
| --- | --- |
| **2-1** | 조건을 **어떤 형식으로 보내야** 할까요. 워크플로우 JSON 에 어떤 필드가 붙는지 알려주세요 |
| **2-2** | 분기로 **안 탄 노드**가 `not_executed` 에 담기나요. 지금 문서에는 실패 시 환원 대상으로만 정의돼 있습니다. 담긴다면 저희가 환불 대상을 그대로 쓸 수 있고, 아니면 경로를 역산해야 합니다 |
| **2-3** | 노드 수 상한(8개)을 **배열 전체 길이**로 보시나요, **실제로 도는 경로 길이**로 보시나요. 분기가 있으면 둘이 달라집니다 |

2-3 은 저희 저장 시점 검사와 어긋나면 **저장은 되고 실행에서 튕기는** 상황이 생겨서 여쭙습니다.

---

## 3. 도구 노드 지원 계획이 있으신가요

지금 워크플로우 JSON 의 노드에는 **종류를 적는 칸이 없고 `prompt` 가 필수**입니다.
그래서 저희가 이해하기로는 **모든 노드가 LLM 호출 하나**입니다.

요구사항 정의서에는 제어 노드·입출력 노드가 있고, API 명세서에는 `TOOL` 노드 종류가 있습니다.
**웹 검색이나 계산 같은 도구 노드를 지원할 계획이 있는지** 알려주시면, 저희가 화면에 그 자리를 둘지 정할 수 있습니다.

없다면 MVP 는 프롬프트 노드만으로 갑니다. **지금 작업은 막히지 않습니다.**

---

## 4. 노드에 참고 자료를 붙일 수 있을까요

지금 파일은 **실행 전체에 하나** 딸리고 첫 노드가 받는 구조로 이해하고 있습니다.

그런데 공급자가 노드를 만들 때 **채점 기준표나 양식 같은 참고 자료를 미리 붙여두고 싶어 할** 것 같습니다.
사용자가 실행할 때 올리는 파일과는 성격이 다릅니다.

지금은 프롬프트 안에 텍스트로 넣는 방법뿐인데, 자료가 크면 그것도 어렵습니다.
**계획이 있으신지, 있다면 대략 언제쯤인지** 알려주시면 좋겠습니다.

---

## 5. 자연어 한 줄로 단계 초안을 만들어 줄 수 있을까요

에이전트를 만들려면 공급자가 **단계를 몇 개로 나눌지 판단하고, 각 단계 프롬프트를 쓰고,
앞 단계 출력이 뒤에 어떤 모양으로 들어갈지까지** 맞춰야 합니다.

"학원 성적을 분석해서 학부모에게 보낼 리포트를 만들고 싶어" 한 줄을 받아
**단계 초안(이름 + 프롬프트)을 뽑아주는 기능**이 있으면, 공급자 진입 장벽이 크게 낮아집니다.

결과물은 저희가 노드 여러 개로 저장하면 되므로 **구조는 바뀌지 않습니다.**
추천 서비스 쪽에 붙이는 게 자연스러워 보이는데, 어떻게 보시는지 궁금합니다.

**급하지 않습니다.** 다만 없으면 마켓에 공급자가 물건을 올리기 어려울 것 같아 미리 여쭙습니다.

---

## 6. 저희 쪽 결정 중 알아두시면 좋을 것

### 6-1. 가격은 에이전트 단위 고정가입니다

수요자는 "이 에이전트 한 번에 5 ABC" 를 삽니다. 내부 노드가 몇 개든 값이 같습니다.

그래서 워크플로우 JSON 의 노드별 `owner_id` · `unit_price` · `base_cost` · `premium_rate` 를
**저희가 쓰지 않습니다.** 형식만 채워 보내고, 돌아온 값 중 보는 것은 `nodes[].status` 뿐입니다.
정산은 저희 가격표로 저희가 계산합니다.

**비워 보내도 되는지, 아니면 형식상 채워야 하는지** 알려주시면 그대로 맞추겠습니다.

### 6-2. 에이전트는 저희가 펼쳐서 보냅니다

수요자가 캔버스에 에이전트를 놓으면, 저희가 그 속을 펼쳐 **평평한 프롬프트 배열**로 만들어 보냅니다.
AI Runtime 은 에이전트라는 개념을 몰라도 됩니다. 문서의 "에이전트 노드 중첩 없음" 과 맞는 방향으로 이해했습니다.

### 6-3. 오류 응답 형식이 다릅니다

AI Runtime 은 `{"detail": {code, message, errors}}`, 저희 API 는 다른 봉투를 씁니다.
**저희가 번역합니다.** 알려주실 것은 없고, 오류 코드가 늘면 공유만 부탁드립니다.

### 6-4. 용어 — "캡슐화"

저희는 코드에서 이 말을 걷어내고 **버전 생성 · 확정 · 공개** 셋으로 나눴습니다.
"내부를 숨긴다" 는 부분이 서비스 설명이지 동작이 아니어서입니다.

연동 가이드에는 "캡슐화" 가 그대로 쓰여 있는데, 문서를 고쳐달라는 뜻은 아닙니다.
**요구사항 정의서 용어를 정리할 때 같이 보면 좋겠다**는 정도입니다.

## 우선순위

| 순위 | 항목 | 왜 |
| --- | --- | --- |
| 1 | **1-1 ~ 1-4** 전송 방식 | 답에 따라 저희 실행 계층 구현이 갈립니다 |
| 2 | **2-1** 분기 조건 형식 | 이게 없으면 분기를 붙일 수 없습니다 |
| 3 | **2-2 · 2-3** 분기 세부 | 환불·저장 검사가 걸립니다 |
| 4 | **6-1** 정산 필드 | 지금은 채워 보내는 중이라 급하진 않습니다 |
| 5 | 3 · 4 · 5 | 계획만 알려주시면 됩니다 |

1번과 2번만 답이 오면 나머지는 저희가 진행하면서 맞출 수 있습니다.
**부담되는 항목은 편하게 "지금은 어렵다" 고 말씀해 주세요.** 그에 맞춰 설계하겠습니다.
