# 에이전트 파이프라인 설계

작업 노드를 만들어 에이전트로 굳히고, 그것을 AI Runtime 으로 실행해 값을 정산하기까지의 설계다.

| 2 | 두 경로 — 판매와 실행은 다른 길이다 |
| 3 | 노드 — 새 애그리거트 |
| 4 | **프론트와 맞춘 것** |
| 5 | 그래프 — 한 줄에서 트리로 |
| 6 | **실행 단위 — 에이전트가 노드 자리를 대신한다** |
| 7 | 가격 — 에이전트 단위 |
| 8 | 실행 — 새 애그리거트 |
| 9 | 패키지와 의존 방향 |
| 10 | 남은 작업 순서 |
| 11 | 미결 · AI 파트 확인 |

원본은 `ai/docs/integration-guide.md` (v1.0) 다. 이 문서와 어긋나면 그쪽이 맞다.

## 1. 경계

AI 가 끼어드는 자리는 셋뿐이다. **지금 붙이는 것은 실행 하나다.** 추천과 색인은 아직 배포되지 않았고,
없어도 실행 파이프라인은 완전히 돈다.

| | 언제 | 어느 서비스 |
| --- | --- | --- |
| 색인 | 에이전트가 마켓에 공개될 때 | 추천 (8100) — 미배포 |
| 추천 | 랜딩에 자연어를 입력할 때 | 추천 (8100) — 미배포 |
| **실행** | 실행 버튼을 누를 때 | 실행 엔진 (8000) — **배포됨** |

### 1.1 AI Runtime 이 하는 일

프롬프트를 순서대로 LLM 에 넣고, 앞 노드 출력을 다음 노드로 넘기고, 분기를 평가하고,
재시도·타임아웃을 처리하고, 마크다운을 PDF 로 만들고, 실패하면 과실 주체를 분류한다.

**그게 전부다.** 계산도 판단도 하지 않는다. 우리가 보낸 값을 그대로 되돌려 준다.

### 1.2 우리가 하는 일

프롬프트 보관, 소유권·버전 판정, 에이전트 펼치기, 값 산정, 선차감, 폴링 중계,
적립·환불, 이력, PDF 보관.

### 1.3 정의는 실행 시점에 실어 보낸다

**AI 가 우리 DB 를 읽게 하지 않는다.** 노드 정의를 요청에 담아 보낸다.

실행은 길게 200초다. 그 사이 공급자가 새 버전을 올리거나 수요자가 워크플로우를 고칠 수 있다.
보내면 **실행이 시작된 순간의 정의가 끝까지 굳는다.** 읽게 하면 1번 노드와 3번 노드가 서로 다른
정의로 돌 수 있고, 나중에 결과를 추적할 수도 없다.

`AgentVersion` 이 원본 워크플로우를 참조하지 않고 그래프를 복사해 갖는 것과 같은 원리다.
읽게 하면 펼치기·소유권·가격 해석까지 AI 가 알아야 하고, DB 접속 정보도 AI 가 갖게 된다.

프롬프트 8개는 많아야 수십 KB 이고 같은 도커 네트워크 안에서 오간다. 실어 보내는 비용은 없다.

## 2. 두 경로

캔버스 화면은 같지만 뒤에서 일어나는 일이 다르다. **섞어서 설계하면 안 된다.**

| | 판매 경로 | 실행 경로 |
| --- | --- | --- |
| 무엇을 만드나 | `Agent` · `AgentVersion` | `Execution` |
| 무엇으로 조립하나 | **내 것만** | 남의 에이전트 포함 |
| 남의 것이 섞이면 | 거부 (`AGENT_FOREIGN_NODE_INCLUDED`) | 정상 |
| 결과물을 팔 수 있나 | — | **없다** |

`Workflow` 는 타입이 하나다. 둘을 가르지 않는다. 남의 에이전트를 하나 지우면 다시 팔 수 있게 되고,
원작자가 자기 에이전트를 내리면 소유자가 아무것도 안 해도 못 팔게 된다. **저장하면 반드시 낡으므로
매번 계산한다.**

### 2.1 그래서 프롬프트 편집기는 뺄 수 없다

되파는 경로가 막혀 있으므로 **마켓에 올라오는 모든 에이전트는 한 사람이 직접 쓴 프롬프트로만
이루어진다.** 공급자가 프롬프트를 못 쓰면 마켓에 물건이 하나도 안 올라온다.

순서상 뒤로 미룰 수는 있어도 범위에서 뺄 수는 없다.

### 2.2 저장은 항상 되고, 유형만 갈린다

**워크플로우와 에이전트를 만드는 흐름은 같다.** 사용자는 캔버스에서 하나를 만들 뿐이고,
저장할 때 **남의 것이 섞였는지**에 따라 팔 수 있는지가 갈린다.

그래서 **저장은 막지 않는다.** 없는 노드를 가리키는 것만 거부하고(참조 무결성), 소유자는 보지 않는다.
저장 시점에 배치를 거부하면 사용자가 무엇을 만들 수 있는지 미리 알 수 없게 된다.

소유권은 **팔 때 한 번** 본다. `AgentVersionPolicy` 가 배치된 기본 노드와 에이전트를 둘 다 훑는다.

| | 저장 | 판매 |
| --- | --- | --- |
| 내 노드 · 내 에이전트 | 된다 | 된다 |
| 남의 공개 에이전트 | 된다 | **거부** |
| 남의 노드 | 된다 | **거부** |

**판매 가능 여부는 저장하지 않고 매번 계산한다.** 남의 에이전트를 하나 지우면 다시 팔 수 있게 되고,
원작자가 내리면 소유자가 아무것도 안 해도 못 팔게 된다. 저장하면 반드시 낡는다.

### 2.3 "팔 수 있나" 는 FE 가 판정한다

**응답에 싣지 않는다.** FE 가 이미 안다 — 팔레트가 항목마다 `mine` 을 내려주고,
캔버스가 `canSellWorkflow(nodes) = nodes.every(n => n.mine)` 로 판정해 등록 버튼을 가른다 (4.5).

서버는 **굳힐 때 한 번** 다시 본다. 그 사이에 바뀌었을 수 있고, 등록 요청을 그대로 믿을 수는
없기 때문이다. 화면을 가르는 것과 거부하는 것은 다른 일이라 두 곳에 있는 것이 맞다.

## 3. 노드 — 남은 것

애그리거트 · 저장 · API 는 들어갔다. **공급자가 노드를 만드는 화면이 남았다.**

### 3.1 에이전트를 만드는 화면은 하나다

노드 만드는 화면과 에이전트 만드는 화면을 따로 두면 공급자가 세 번 왕복하며 "노드" 라는 개념을
계속 이해하고 있어야 한다. **한 화면에서 단계를 쌓아 올린다.**

```
1단계  성적 데이터를 분석한다        [프롬프트]
2단계  분석 결과로 가정통신문을 쓴다   [프롬프트]
+ 단계 추가
```

공급자 눈에 "노드" 라는 말이 나오지 않는다. **단계를 추가하면 그게 노드다.** 우리 내부 개념일 뿐이다.

### 3.2 프롬프트는 자유 입력으로 시작한다

폼으로 칸을 나누면 두 가지가 문제다. 어떤 프롬프트가 잘 도는지 한 번도 안 돌려봤으므로 **지금 좋은 폼을
설계할 근거가 없고**, 칸을 미리 나누면 만들 수 있는 노드의 종류가 좁아진다.

**나중에 폼이나 자동 생성을 붙여도 막히지 않는다.** 그때 "어떻게 만들어졌나" 를 기록하는 칸을 추가하면
되고, 자유 입력으로 만든 기존 노드는 그 칸이 비어 있으니 계속 자유 입력으로 편집한다.

### 3.3 자연어 한 줄 → 단계 초안

에이전트 하나 만들려면 단계를 몇 개로 나눌지 판단하고, 각 단계 프롬프트를 쓰고, 앞 단계 출력이 뒤에
어떤 모양으로 들어갈지까지 맞춰야 한다. **공급자 온보딩의 핵심이고, 없으면 마켓에 물건이 안 올라온다.**

노드 구조를 바꾸는 것이 아니라 앞에 붙는 도우미라 나중에 얹어도 된다. AI 파트에 요청해야 한다 (11.2).

## 4. 프론트와 맞춘 것

`frontend/src/api/agents.ts` 를 기준으로 맞췄다. **명세가 "확정" 인 것은 그쪽이 맞다.**

### 4.1 등록이 곧 공개다

FE 모델에 `visibility` 가 없다. **에이전트로 등록했다는 것이 곧 공개**라는 뜻이다.
그래서 `Visibility` 를 걷어내고 `Agent` 에서 공개 여부를 들지 않는다.

배치 가능 여부는 **공개 버전이 있는가** 하나로 판정한다. 소유자는 아직 공개 버전이 없어도 자기 것을 놓을 수 있다.

**팔 수 없는 워크플로우는 애초에 공개되지 않는다.** 남의 것이 섞이면 에이전트가 되지 못하고,
에이전트가 아니면 마켓에 존재하지 않는다. 공개 여부를 따로 들 필요가 없는 것은 이 때문이다.

### 4.2 `POST /agents` — 명세를 쪼갠다

Notion 「에이전트 등록」 명세가 있다. **그대로는 만들 수 없다** — 없는 도메인에 기댄다.

| 명세 | 우리 | 왜 |
| --- | --- | --- |
| `multipart/form-data` | `application/json` | 올릴 파일이 없으면 multipart 일 이유가 없다 |
| `executionId` 필수 | **안 받는다** | 실행 도메인이 없어 검증할 대상이 없다. 생기면 넣는다 |
| `iconFile` · `inputFiles` · `outputFiles` | 없음 | 파일 업로드가 없다 |
| 응답 `images` · `blockchain` | 없음 | 위와 같다 |
| 응답 `price` | **넣는다** | `AgentVersion.finalPrice()` 로 지금 계산된다 |
| `AGENT_001` (테스트 미통과) | 쓰지 않는다 | `executionId` 를 안 받으므로 걸릴 일이 없다 |
| 검증 통과 요구 (`AGENT_WORKFLOW_NOT_VALIDATED`) | **걷어냈다** | `ValidationStatus` 를 `VALID` 로 만드는 길이 프로덕션에 없어 무조건 걸렸다. 실행 도메인이 붙어 시험 실행이 생기면 그때 되살린다 |

받는 것은 `workflowId` · `revision` 과 프로필 다섯이다. **회차를 같이 받는다** — 사용자가 보던
회차와 굳히는 회차가 다르면 막아야 한다 (`WORKFLOW_016`).

**원본 워크플로우를 잠그지 않는다.** 한 트랜잭션 안에서 읽으므로 워크플로우 행과 그래프 행이
같은 스냅샷에서 나온다. 그 사이 `PUT` 이 커밋해도 우리가 복사한 것은 회차 N 의 일관된 그래프이고,
"출처 회차 N" 으로 박히는 것이 맞다. `replace` 가 락을 잡는 것은 같은 행을 **쓰기** 때문이다.

**대신 배치된 노드 행에는 공유 락을 잡는다** (`readAllForShare`). 그래프는 값 복사지만 실행에는
`node_definition` 행이 필요하다. 워크플로우 행을 잠그지 않으므로 "등록 진행 중 → 원본 워크플로우
삭제 → 노드 삭제" 가 겹칠 수 있고, 다형 참조라 FK 도 막아 주지 않아 지워진 노드를 가리키는 버전이
남는다. 저장 경로(`CatalogNodeSourceResolver.findByIdForShare`)와 같은 모양으로 막는다.

필드 길이는 명세 값을 그대로 쓴다 — `name` 2\~40, `summary` 80, `description` 2000(필수),
`usageExample` 500, `onboardingMessage` 20.

### 4.3 워크플로우 저장 — 명세와 다르게 가기로 한 것

| | 명세 | 우리 | 왜 |
| --- | --- | --- | --- |
| 노드 식별 | `order` | **`nodeKey`** | `order` 는 한 줄을 계약에 박는다. 갈라지면 두 노드가 같은 순서라 번호를 못 매긴다 |
| 연결선 | `sourceOrder` · `targetOrder` | **`edgeKey` · `sourceNodeKey` · `targetNodeKey`** | 위와 같다. FE 캔버스가 연결선을 개별 선택하므로(`selEdge`) 식별자가 필요하다 |
| 수정 | "`PUT` 은 두지 않는다" | **`PUT` 을 둔다** | 편집 라우트가 `/edit/nodes/:workflowId` 로 수정을 전제한다. 굳히기 전 워크플로우는 초안이고, 초안을 못 고치면 캔버스가 쓸모없다. 명세의 "수정 없음" 은 **등록 이후 불변성과 혼동한 것**으로 본다 |
| 응답 `nodeCount` · `edgeCount` | 있음 | **뺀다** | 요청에서 센다 |
| 응답 `executeOnly` · `foreignNodeOrders` | 있음 | **넣지 않는다** | FE 가 이미 안다 — 4.5 |
| 배치할 노드 | 기존 노드 id | **id 또는 새 노드 본문** | 4.5 |
| 노드 종류 | 없음 | **`node_definition.node_type` 에 저장한다** | FE 팔레트가 `nodeType` 을 받아 쓴다. 배치도 종류로 갈린다 — `LLM` 만 본문을 싣는다 |
| HTTP | 201 | 200 → **201 로 고친다** | |
| 좌표 | 안 받는다 | 안 받는다 | 같다 |

**키는 순서를 뜻하지 않는다.** 캔버스 안에서 겹치지만 않으면 되는 이름표이고, 실행 순서는 엣지를
따라 위상 정렬로 계산한다(`WorkflowGraph.nodesInOrder`). 배열 순서에도 의미가 없다.

**분기가 들어와도 형식은 안 바뀐다.** 같은 노드가 `sourceNodeKey` 로 두 번 나오면 갈라짐,
`targetNodeKey` 로 두 번 나오면 합류다. 엣지 목록은 이미 어떤 DAG 든 표현한다. 바뀌는 것은
검증뿐 — 한 줄 검증(`soleStart` · `WORKFLOW_GRAPH_NOT_LINEAR`)을 DAG 검증으로 되돌린다 (5장).

합류에서만 엣지에 `inputOrder` 가 붙는다. 앞이 여럿일 때 어느 결과를 먼저 이어 붙일지는 연결만으로
알 수 없기 때문이다. 배열 순서에 기대면 FE 가 정렬을 바꿀 때 결과가 바뀐다.

조건 분기는 **제어 노드**로 놓는다 (5.4). 조건식은 AI Runtime 이 평가하므로 우리는 문자열로
나르기만 한다 — 문법은 `ai-runtime-questions.md` 2번이다.

### 4.4 마켓·마이페이지 필드는 대부분 다른 도메인이 있어야 채워진다

| 필드 | 무엇이 있어야 |
| --- | --- |
| `price` | **지금 가능.** `AgentVersion.finalPrice()` 를 문자열로 |
| `executionCount` · `successRate` | 실행 이력 |
| `revenue` · `trend`(7일) | 정산 이력 |
| `averageRating` · `reviewCount` | 리뷰 도메인 |
| `favorited` · `favoriteCount` | 즐겨찾기 도메인 |
| `owner.nickname` · `profileImageUrl` | 회원 도메인 |
| `iconUrl` · `images` | 파일 업로드 |
| `provenance` | 블록체인 |

**금액은 전부 문자열로 내린다.** FE 가 "소수점 오차를 막기 위해 문자열이다 — 숫자로 되돌리지 않는다"
고 못 박아 뒀다. 통화 필드는 두지 않는다. 단위가 ABC 하나뿐이라 화면이 붙인다.

**버전은 FE 모델 어디에도 없다.** 새 버전을 올리는 화면이 아직 없는 것으로 보고 지금은 두지 않는다.
`AgentVersion` 은 우리 안에만 있고 응답에 나가지 않는다.

### 4.5 FE 코드를 읽고 고친 것

**여기 적힌 것은 전부 `origin/develop-FE` 의 소스에서 확인했다.** 앞 절들을 쓸 때는 Notion 명세와
추론만 봤고, 그래서 아래 다섯 줄이 틀려 있었다.

| | FE 가 실제로 하는 것 | 우리가 잘못 적어둔 것 |
| --- | --- | --- |
| 판매 가능 판정 | `canSellWorkflow(nodes) = nodes.every(n => n.mine)` — 팔레트가 준 `mine` 으로 **FE 가 스스로 판정한다** | "소유권은 서버만 안다" — 틀렸다. 응답에 실을 필요가 없다 |
| `POST /agents` 본문 | `CreateAgentRequest` 는 **프로필 다섯뿐.** 주석에 "워크플로우 연결은 명세가 오면 붙인다" | FE 가 `workflowId` 를 보내는 것처럼 적었다. **우리가 내려줘야 하는 계약이다** |
| `POST /agents` 응답 | `CreatedAgent = { agentId }` | `price` 를 넣기로 했다. FE 가 안 쓰므로 여분이다 |
| 노드 팔레트 | `GET /workflows/node-palette` (`scope` · `keyword` · 커서) 를 부른다 | **우리에게 엔드포인트가 없다** |
| 워크플로우 저장 | **호출이 없다.** 캔버스는 `CANVAS_NODES` 하드코딩. 주석에 "저장·조회 API 가 아직 없어 자리표시자를 둔다" | 계약만 있고 FE 가 아직 안 붙였다 |
| 분기 | `canConnect` 가 **들어오는 선만 1개**로 막고 나가는 선은 여럿 허용 — **캔버스는 이미 분기를 그린다** | 우리는 한 줄만 받고 `WORKFLOW_013` 으로 거부한다 |

#### 새 작업 노드는 저장 시점에 DB 에 없다

팔레트에서 끌어다 놓는 것은 이미 있는 노드·에이전트다. 그런데 공급자가 **프롬프트와 모델을 적어
새 단계를 만들면** 그것은 아직 행이 아니다. 3.1 이 "단계를 추가하면 그게 노드다 / 공급자 눈에
노드라는 말이 나오지 않는다" 라고 해놓고, 저장 계약은 `sourceId` 를 필수로 받고 있었다.

**배치에 실어 보낸다.** `sourceId` 가 있으면 기존 것을 놓고, 없으면 `name` · `prompt` · `model` 로
노드를 만들어 놓는다. 한 트랜잭션이라 워크플로우 저장이 실패하면 노드도 남지 않는다.

먼저 `POST /nodes` 를 부르게 하면 단계 3개에 요청이 4번이고, 중간에 끊기면 **주인 없는 노드가
카탈로그에 남는다.** 사용자는 "노드를 만든" 적이 없는데 목록에 생긴다.

## 5. 그래프 — 한 줄에서 트리로

### 5.1 무엇이 바뀌나

분기(if-else)를 받는다. **병합은 지금 넣지 않는다** — 자리는 5.4 가 열어 둔다.

병합이 없으면 들어오는 선이 노드마다 최대 하나이므로 **그래프가 트리로 유지된다.** 위상 정렬이 필요 없고,
실행 경로는 여전히 한 줄이다. 시작점에서 걸어 내려가다 분기에서 한쪽만 고르면 된다.

| 지금 | 바꾼 뒤 |
| --- | --- |
| 나가는 선 1개 (`WORKFLOW_GRAPH_NOT_LINEAR`) | 분기 노드만 2개, 나머지는 1개 |
| 들어오는 선 1개 | **그대로** — 이것이 트리를 보장한다 |
| `nodesInOrder()` 전순서 하나 | 경로가 여러 개. 전순서가 없다 |
| `chainLength()` | `longestPathLength()` |

`nodesInOrder()` 는 저장·응답에서 쓰이므로 **당장 없애지 않는다.** 분기가 없는 그래프에서는 지금대로
동작하고, 분기가 있으면 경로 목록을 내는 메서드를 따로 둔다.

### 5.2 실행 길이는 버전이 들고 다닌다

`GraphLimits` 의 값이 **노드 20개 / 깊이 10** 인데 한 줄이라 실효 상한은 10 하나다.
**AI 상한은 8개다.** 지금 9~10개짜리는 저장은 되고 실행에서 튕긴다.

8은 시간에서 나온 값이다 — 노드당 약 25초 × 8 ≈ 200초, 총 실행 시간 5분(PER-003)에서 역산.
그러므로 재야 할 것은 **실제로 돌아가는 프롬프트 노드 수**다.

#### 매번 펼쳐 세지 않는다

`AgentVersion` 은 불변이다. 만들어지는 순간 그래프가 굳고 다시 바뀌지 않는다.
그러므로 **펼친 노드 수를 버전을 만들 때 한 번 계산해 버전에 박아 둔다.**

계산도 재귀가 아니다. 그래프에 놓인 버전이 **이미 자기 값을 들고 있기 때문**이다.

> 새 버전의 노드 수 = 내 기본 노드 수 + 놓인 버전들이 든 값의 합

한 단계만 본다. 몇 겹이든 상관없다. **원가도 같은 방식으로 한 번 더해 박아 둔다** (7.3).

| 언제 | 무엇을 하나 |
| --- | --- |
| 버전을 만들 때 | **한 번.** 놓인 버전들의 값을 읽어 더해 박는다 |
| 워크플로우를 저장할 때 | **조회만.** 박힌 값을 더해 상한을 본다 |
| 주문서를 만들 때 | **끝까지 펼친다.** 프롬프트 원문이 필요하다 |

재귀가 실제로 필요한 것은 **마지막 하나뿐**이다.

#### 어느 수를 재나

| 기준 | 왜 틀리나 |
| --- | --- |
| 전체 노드 수 | 분기가 있으면 안 도는 노드까지 세어 멀쩡한 워크플로우가 거부된다 |
| 펼치기 전 개수 | 에이전트 셋을 조합하면 펼쳤을 때 9개가 되는 것을 못 막는다 |
| **펼친 뒤 가장 긴 경로** | **이것이 맞다** |

### 5.3 사용자에게는 노드 수로 말하지 않는다

**에이전트는 블랙박스다.** 수요자는 속에 노드가 몇 개인지 모르고 알 필요도 없다.
그런데 "노드 수가 8개를 넘습니다" 라고 거절하면 **자기가 셋을 놓았는데 왜 여덟이냐** 가 된다.

**시간으로 말한다.**

> 이 조합은 실행에 5분 이상 걸려 실행할 수 없습니다.

그리고 마켓의 에이전트마다 **예상 실행 시간**을 표시한다. 가격을 표시하는 것과 같다.
수요자가 조합하는 중에 미리 가늠할 수 있어야 한다.

속 구성은 여전히 감춰진다. 밖으로 나가는 것은 "이 에이전트는 약 50초 걸린다" 하나뿐이고 **그것은
상품 정보다.** 8이라는 숫자도 원래 시간에서 역산한 것이므로 되돌리는 것뿐이다.

### 5.4 제어 노드 — 분기는 배치이지 카탈로그가 아니다

분기를 **제어 노드**로 놓는다. 나중에 병합·반복이 생겨도 배치 종류만 늘어난다.

`SourceType` 이 셋이 된다.

| | `reference_id` | 가리키는 것 | 카탈로그에 남나 |
| --- | --- | --- | --- |
| `NODE` | 노드 id | `node_definition` | 사용자 자산 |
| `AGENT` | 에이전트 id + 버전 id | `agent_version` | 사용자 자산 |
| **`CONTROL`** | **없음** | 아무것도 | **남지 않는다** |

**제어 노드는 `node_definition` 행을 만들지 않는다.** 그래서 "사용자 자산인 카탈로그에 시스템
노드가 섞인다" 는 걱정이 생기지 않는다. `graph_node` 에만 존재하는 배치다.

`graph_node` 는 `reference_id` 가 nullable 이 되고 `control_type` 이 붙는다. 도메인에는
`BaseNode` · `AgentNode` 옆에 `ControlNode` 가 하나 는다.

#### 조건은 노드가 들고, 엣지는 갈래를 가리킨다

분기 노드가 조건식을 들고, 나가는 엣지가 **어느 갈래인지**만 말한다(`branch_label`).
엣지마다 조건식을 달면 제어 노드를 둔 뜻이 없어지고, 갈래가 셋으로 늘 때 조건이 흩어진다.

| | 어디에 |
| --- | --- |
| 조건식 (문자열, AI 가 평가) | `graph_node.condition` — 제어 노드 |
| 어느 갈래인가 (`TRUE` · `FALSE` · …) | `graph_edge.branch_label` |

병합 노드가 생기면 **그 노드에서만** "들어오는 선 1개" 제약을 푼다. 나머지 노드는 그대로라
트리가 유지된다. 합류에서 붙는 `inputOrder` 도 병합 노드로 들어오는 엣지에만 달린다.

#### 세고 더할 때 제어 노드는 빠진다

`baseNodeReferences()` · `agentReferences()` 가 제어 노드를 자연히 걸러낸다. 그래서 소유권 검사에
걸리지 않고(주인이 없다), `VersionCost` 의 `promptNodeCount` 에도 들어가지 않는다. 5.2 의 상한은
**실제로 도는 프롬프트 수**를 재는 것이므로 이것이 맞다.

## 6. 실행 단위 — 에이전트가 노드 자리를 대신한다

### 6.1 필요한 것

**값 · 주인 · 펼치기를 답하는 공통 타입 하나.** 이름이 무엇이든 역할은 이렇다.

> 워크플로우의 한 자리에 놓인 것. 자기 값을 알고, 자기 주인을 알고,
> **프롬프트 목록으로 자신을 펼칠 줄 안다.**

잎은 프롬프트 하나를 내놓는다. 가지는 자기 버전의 그래프를 꺼내 자식들의 펼침을 이어 붙인다.
그러면 위 네 군데가 전부 **"펼쳐서 세라 / 펼쳐서 더해라"** 한 줄이 된다.

**다만 세고 더하는 것은 5.2 대로 버전에 박힌 값을 읽는다.** 실제로 펼치는 것은 주문서를 만들 때뿐이다.

### 6.2 버전 고정이 순환을 막는다

배치가 버전까지 고정하므로 **순환이 생기지 않는다.**

A 3판이 B 1판을 담고 있는데 나중에 B 4판이 A 3판을 담아도, A 3판은 여전히 B 1판만 담는다.
방어 코드를 따로 두지 않아도 되는 것은 이 때문이다.

## 7. 가격 — 에이전트 단위

### 7.1 파는 단위와 값을 매기는 단위를 맞춘다

**에이전트 하나에 값 하나다.** 내부 노드가 몇 개든, 어느 경로를 타든 고정가다.

수요자는 "이 에이전트 쓰는 데 5 ABC" 를 사는 것이지 속에 노드가 몇 개인지 알 바 아니다.
**속을 숨기는 것이 에이전트인데 가격이 속을 드러내면 앞뒤가 맞지 않는다.**

| 규칙 | 내용 |
| --- | --- |
| 조합 | 배치된 에이전트 값의 합. 반복이 없으므로 각 에이전트는 **탔거나 안 탔거나** 둘 중 하나 |
| 내부 분기 | 가격에 영향 없음 |
| 선차감 | **가장 비싼 경로.** 적게 잡으면 실행 중 잔액이 모자라고, 전부 더하면 잔액 충분한 사용자도 막힌다 |
| 부분 성공 | **없다.** 내부 노드가 하나라도 실패하면 그 에이전트는 실패다. 결과물이 안 나왔으면 산 것이 아니다 |
| 정산 근거 | 우리 가격표로 우리가 계산한다. AI 의 `contribution` 은 쓰지 않고 **노드 성공 여부만** 본다 |

부분 성공을 없앤 것이 노드 단위 정산보다 명확하다. "둘은 성공했으니 그만큼은 줘야 하나" 같은
판단이 필요 없다.

### 7.2 AI 주문서의 정산 필드

주문서는 노드마다 `owner_id` · `unit_price` 를 요구한다. 에이전트 단위 가격과 맞지 않는다.

**쓰지 않는다.** 형식만 채워 보내고, 돌아온 값 중 우리가 보는 것은 `nodes[].status` 뿐이다.
AI 는 받은 값을 되돌려 줄 뿐 계산하지 않으므로 무시해도 된다.

### 7.3 원가는 버전에 박아 둔다

노드의 원가는 `BaseCostCalculator` 가 산출해 저장할 때 박는다. 지금 구현은 고정값이고, AI 서버가
산출해 주면 **구현만 갈아끼운다.** 매번 계산하지 않는 이유는 그래야 팔리고 있는 에이전트 값이
소리 없이 바뀌지 않기 때문이다.

에이전트 버전의 원가는 속 노드 원가의 합이고, 거기에 등급 프리미엄(T1 +50% … T4 +0%)을 얹은 것이
최종 단가다. `AgentVersion` 이 `VersionCost` 로 받아 든다.

**합산하는 주체가 아직 없다.** 6장의 실행 단위 타입과 함께 붙인다 — 스냅샷을 훑어 놓인 버전의
박힌 값을 읽어 더하는 것이고, 5.2 대로 재귀가 아니다.

판매가는 고정인데 원가는 노드 수에 비례하므로 **노드를 많이 쓰는 에이전트는 마진이 줄어든다.**
불필요하게 단계를 늘리지 않을 유인이 되므로 그대로 둔다.

## 8. 실행 — 새 애그리거트

### 8.1 무엇이 생기나

| | 무엇인가 |
| --- | --- |
| `Execution` | 실행 한 건. 상태 · 선차감액 · `run_id` · 이력 |
| `ExecutionPlan` | AI 에 보낼 주문서. 펼친 노드 배열 + **노드 → 에이전트 매핑** |
| `AiRuntimeClient` | 도메인이 선언하는 인터페이스. 구현은 바깥 |

### 8.2 펼쳐 보냈으니 접어서 본다

AI 는 에이전트를 모르므로 평평한 노드 배열을 받는다. 그런데 정산은 에이전트 단위다.

**주문서를 만들 때 어느 노드가 어느 에이전트에서 나왔는지 매핑을 기록해 둔다.** AI 는 그것을 갖고
있지 않으므로, 안 남기면 결과를 받고 나서 복원할 수 없다.

**실제로 재귀가 도는 곳은 여기 하나뿐이다.** 프롬프트 원문이 필요해 끝까지 내려가야 한다.

### 8.3 흐름

| | 하는 일 |
| --- | --- |
| 1 | 워크플로우를 읽어 주문서를 조립한다. 에이전트는 펼치고, 시작·끝 노드는 실행 설정으로 접는다 |
| 2 | 가장 비싼 경로만큼 **미리 뗀다.** AI 를 부르기 전에 한다 |
| 3 | `POST /v1/runs` — **실행 한 건에 호출 한 번.** 즉시 `run_id` 만 돌아온다 |
| 4 | 2초마다 조회해 프론트로 중계한다 |
| 5 | 에이전트 단위로 접어 정산한다 |
| 6 | PDF 를 받아 보관하고, 안 탄 경로를 환불한다 |

동기로 기다리지 않는 이유는 노드 3개면 75초라 nginx 기본 타임아웃 60초를 넘기 때문이다.
끊기면 **이미 지불한 LLM 비용과 실행이 통째로 날아간다.**

프론트가 보는 SSE 는 이 폴링 결과를 중계하는 것이다. **AI 에 SSE 는 없다.**

### 8.4 지켜야 할 것

| 항목 | 내용 |
| --- | --- |
| 멱등성 | 폴링은 같은 상태를 여러 번 본다. `(run_id, node_id)` 를 기록해 **두 번 적립하지 않는다** |
| 타임아웃 | `노드 수 × 40초 + 60초` 를 넘도록 상태가 안 바뀌면 실패로 처리한다 |
| 404 | 재배포하면 이전 `run_id` 가 사라진다. **이력 원본은 우리 DB** 이므로 그것으로 답한다 |
| 노드 출력 | 조회 옵션을 켜면 각 노드 출력 전문이 온다. **남의 에이전트 속이 드러나므로 켜지 않는다** |
| PDF | AI 쪽 파일은 임시다. 받아서 우리 스토리지에 저장하고 우리 주소를 발급한다 |

### 8.5 폴링 루프 구조 — 먼저 정할 것

실행이 동시에 열 건이면 2초마다 도는 루프가 열 개이고, 각각 최대 200초씩 살아 있다.

실행마다 비동기 작업을 띄우는 방식과 스케줄러 하나가 진행 중인 실행 전부를 훑는 방식 중
**어느 쪽인지 먼저 정한다.** 잘못 정하면 나중에 통째로 다시 쓴다.

## 9. 패키지와 의존 방향

```
domain
├── AbcAmount
├── user        사용자 · `UserId`
├── node        작업 노드 카탈로그
├── workflow    그래프 · 배치 · 그래프 정책
├── agent       에이전트 · 버전 · 가격
└── execution   실행 단위 · 주문서 · 폴링 · 정산
```

```
workflow   ->  domain
node       ->  workflow, domain
agent      ->  workflow, node, domain
execution  ->  agent, workflow, node, domain
```

**`workflow` 는 아무도 모른다.** 지금 지켜지고 있는 방향이고, 계속 지킨다. `NodeReference` 가
`AgentId` 도 `NodeId` 도 모르기 때문에 성립한다 (RULE.md 11.3).

`node` 가 `workflow` 를 아는 것은 `NodeSourceResolver` 를 구현하기 때문이다. `agent` 가
`workflow` 를 아는 것과 같은 모양이다.

### 9.1 실행 단위를 어디에 두나

6장의 공통 타입은 **노드와 에이전트를 둘 다 알아야 한다.** `workflow` 에는 둘 수 없다.

`execution` 이 유력하다. 네 쓰임 중 셋(선차감·주문서·정산)이 실행 쪽이고, 나머지 하나인 저장 시점
상한 검사도 **"실행 계획을 세워 본다"** 로 읽으면 같은 자리다.

다만 그러면 워크플로우 저장이 `execution` 을 거치게 된다. `workflow` 가 `execution` 을 직접 알면
방향이 깨지므로, 검사는 **저장 서비스가 조립해 부른다.**

### 9.2 애그리거트를 가로지르는 조회

협력자는 Reader 를 직접 문다 (RULE 11.4). 인터페이스는 **구현이 실제로 갈릴 때만** 둔다 (RULE 6장).

| 인터페이스 | 선언 | 구현 | 무엇을 묻나 |
| --- | --- | --- | --- |
| `NodeSourceResolver` | `workflow` | `node` · `agent` | 이 참조가 실재하는가 |
| `BaseCostCalculator` | `node` | `node` (고정값) | 이 프롬프트의 원가는 얼마인가 |
| `AiRuntimeClient` | `execution` | 아직 없음 | 실행을 맡기고 상태를 묻는다 |

`AgentOwnershipView` 는 걷었다. 노드 소유권 · 사용 여부를 묻던 두 인터페이스도 이미 걷었고,
정책이 `AgentReader` · `NodeDefinitionReader` 를 직접 문다.

`BaseCostCalculator` 가 **PSA 의 본보기다.** 지금 구현은 파라미터를 무시하고 고정값을 내지만,
시그니처가 이미 프롬프트와 모델을 받으므로 AI 서버 구현으로 바꿀 때 계약을 다시 안 고쳐도 된다.

## 10. 남은 작업 순서

**값을 건드리는 것이 마지막이다.** 돈부터 붙이면 무엇이 틀렸는지 알아내기 어렵다.

| | 무엇을 | 끝났다고 보는 기준 |
| --- | --- | --- |
| 1 | **실행 단위 타입** — 값 · 주인 · 펼치기를 답하는 공통 타입 (6장) | 네 군데가 같은 것을 부른다 |
| 2 | **주문서 조립 + `mock=true`** | 가짜 실행이 1초에 끝나고 응답 구조가 맞는다 |
| 3 | **실행 · 폴링 · 이력 · PDF** (8장) | 진행 게이지가 돌고 PDF 가 떨어진다. **값은 아직 안 건드린다** |
| 4 | **에이전트 영속화 · 마켓 API** | 버전을 만들고 공개해 목록에 뜬다 |
| 5 | **그래프 트리 확장 · 분기** (5장) | 분기가 있는 워크플로우가 저장되고, 긴 조합이 시간 메시지로 거부된다 |
| 6 | **선차감 · 정산 · 환불** | 에이전트 단위로 정산되고 안 탄 경로가 돌아온다 |

2단계에서 `mock` 을 반드시 거친다. LLM 을 부르지 않아 1초에 끝나고, **GMS 크레딧은 팀 공용**이며,
응답 구조는 실제와 완전히 같다. 형식 문제를 여기서 전부 턴다.

**1~3 은 에이전트 없이 끝까지 간다.** 내 노드만으로 만든 워크플로우는 펼칠 것도 정산 쪼갤 것도 없다.
그것으로 파이프라인 전 구간을 검증하고 나서 4부터 에이전트를 얹는다.

5 는 다른 것과 얽히지 않으므로 아무 때나 껴도 된다. **`GraphLimits` 를 8로 내리는 것도 여기서 한다** —
지금 내려봐야 실행이 없어 확인할 방법이 없다.

## 11. 미결 · AI 파트 확인

### 11.1 우리가 정할 것

| 항목 | 선택지 | 걸리는 것 |
| --- | --- | --- |
| 값을 누가 매기나 | 판매자 / 우리 | 판매자가 매기면 **원가 이상으로 하한**을 걸어야 한다 |
| 노드 시험 실행 | 넣는다 / 미룬다 | AI 에 단독 실행이 없다. 노드 1개짜리 임시 워크플로우로 우회 가능 |
| **자기 에이전트 중첩** | 허용 / 판매용에서 금지 | 아래 |
| 자기 노드만으로 실행 | 값을 받나 | 수요자가 자기 노드로 짜서 돌리면 자기에게 내는 셈이 된다 |
| 폴링 루프 구조 | 실행별 비동기 / 스케줄러 일괄 | 8.5 |
| PDF 보관 위치 | 서버 로컬 / 오브젝트 스토리지 | MVP 는 로컬 + 정적 서빙이 제일 싸다 |
| 실행 단위 타입 위치 | `execution` / 새 자리 | 9.1 |

#### 정해진 것

| 항목 | 결론 |
| --- | --- |
| 금액 타입 | `AbcAmount` 하나. `Money` 는 걷어냈다 |
| 원가 산정 | `BaseCostCalculator` 뒤에 숨기고 지금은 고정값. AI 서버가 산출해 주면 구현만 갈아끼운다 |
| 원가를 어디 두나 | 노드에 박는다. 매번 계산하면 팔리고 있는 에이전트 값이 소리 없이 바뀐다 |
| 입력 출처 위치 | 노드가 아니라 **배치** |

#### 자기 에이전트 중첩

남의 에이전트는 판매 경로에서 애초에 막히므로, 중첩이 생기는 경로는 **자기 것뿐**이다.
공급자가 자기 에이전트를 자기 새 워크플로우에 놓고 그것을 다시 파는 경우다. 지금 코드는 허용한다.

**세는 비용은 문제가 아니다.** 5.2 대로 버전이 값을 들고 다니므로 몇 겹이든 더하기 한 번이다.
순환도 6.2 대로 버전 고정이 막는다.

**남는 쟁점은 정산이다.** 에이전트가 정산 단위인데 중첩되면 안쪽 에이전트도 정산 단위인지가 갈린다.
같은 사람이라 자기가 자기에게 주는 꼴이므로 의미가 없고, 결국 **"최상위 에이전트만 정산 단위"**
라는 예외가 붙는다. 규칙이 하나에서 둘이 된다.

**금지를 권한다.** 잃는 것은 "내 에이전트를 재사용" 인데 워크플로우를 복사해 노드를 직접 넣으면 된다.
명세의 중첩 깊이 3 도 남의 에이전트를 상정한 값으로 보이므로 함께 다시 본다.

### 11.2 AI 파트에 물을 것

| 항목 | 왜 필요한가 |
| --- | --- |
| 분기로 안 탄 노드가 `not_executed` 에 담기나 | 담기면 환불 대상을 그대로 쓴다. 아니면 우리가 경로를 역산해야 한다 |
| 노드 수 상한을 배열 전체로 보나 경로로 보나 | 다르면 우리 저장 검사와 어긋난다 |
| 도구 노드 지원 계획 | 주문서에 노드 종류를 적는 칸이 없다. 있으면 단계 종류가 여러 개가 된다 |
| 노드별 참고 파일 지원 계획 | 채점 기준표 같은 자료. 지금은 프롬프트에 텍스트로 박는 수밖에 없다 |
| 자연어 → 단계 초안 생성 | 공급자 진입 장벽 전체를 좌우한다. 없으면 마켓에 물건이 안 올라온다 |

### 11.3 이미 어긋나 있는 것

| 항목 | 우리 | AI |
| --- | --- | --- |
| 노드 수 상한 | 실효 10 | **8** — 10장 5단계에서 함께 고친다 |
| 오류 형식 | `ApiResult` | `{"detail": {code, message, errors}}` — 번역 계층과 `EXE_*` 코드가 필요하다 |
| 용어 | 캡슐화를 걷어내고 **버전 생성 · 확정 · 공개** 로 나눔 | 연동 문서가 "캡슐화" 를 그대로 쓴다 |

### 11.4 응답에 남은 빈 값

`WorkflowSaveResponse.estimatedCost` 가 아직 `"0"` 이다. 노드에 원가가 생겼으므로 이제 셀 수 있지만,
선차감이 10장 6단계라 그때 함께 채운다. **지금 채우면 계산 규칙이 두 곳에 흩어진다.**
