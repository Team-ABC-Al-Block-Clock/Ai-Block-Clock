# 에이전트 파이프라인 설계

작업 노드를 만들어 에이전트로 굳히고, 그것을 AI Runtime 으로 실행해 값을 정산하기까지의 설계다.
**구현이 끝난 장은 [`completed/`](completed/agent-pipeline.md) 로 걷어냈다.** 여기에는 남은 것만 둔다.

| 장 | 내용 | 남은 것 |
| --- | --- | --- |
| 1 | 경계 | 저장 시점 검증 · 실측 원가 (1.5) |
| 2 | 두 경로 | — 전부 completed |
| 3 | 노드 | 단계 초안 도우미 (3.3) |
| 4 | 프론트와 맞춘 것 | 마켓 · 마이페이지 필드 — 리뷰 · 이미지 · 써 본 에이전트 (4.4) |
| 5 | 그래프 | 실행 길이 상한 · 시간으로 말하기 (5.1 ~ 5.3) |
| 6 | 실행 단위 | — 전부 completed |
| 7 | 가격 | — 규칙만 남았다 (7.1 ~ 7.3) |
| 8 | 실행 | 흐름의 남은 칸 (8.3) |
| 9 | 패키지와 의존 방향 | |
| 10 | 남은 작업 순서 | |
| 11 | 미결 · AI 파트 확인 | |

원본은 `ai/docs/integration-guide.md` 다. 이 문서와 어긋나면 그쪽이 맞다.
**09-26 에 계약이 v2.0 · v2.1 로 다시 쓰였다** — 노드 입출력 스키마가 `output {kind, example}` 로 바뀌고, 연결 형식 검사가
없어지고, 원가가 `cost_abc` 대신 `cost_usd` 로 온다. 이 문서의 계약 인용은 대부분 09-22 갱신본 기준이고,
v2.0 에 맞춰 바꿀 일은 [`contract-v2.md`](contract-v2.md) 에 모았다.

## 1. 경계

AI 가 끼어드는 자리는 셋이다 — 색인 · 추천 (8100) 과 실행 (8000). **우리 쪽 연동은 셋 다 붙었다.**
Runtime 이 하는 일 · 우리가 하는 일 · 정의를 실어 보내는 이유 · 추천과 색인은 [`completed/`](completed/agent-pipeline.md) 1장으로 옮겼다.

### 1.5 저장 시점 검증과 실측 원가

**`validate` 는 아직 부르지 않는다.** 원가는 ~~`FixedBaseCostCalculator` 의 3 ABC 고정~~ → MR !118 이 판매자
테스트 실행으로 잰 값을 쓰게 바꿨다(12장).

`POST /v1/workflows/validate` 는 워크플로우 JSON 만 받아 **실행하지 않고** 검증 결과와 견적을 돌려준다.
과금이 없다.

| 우리가 복제하지 않아도 되는 것 | |
| --- | --- |
| 그래프 규모 상한 | 캔버스 8 · 전개 후 20 · 최장 경로 8 · 중첩 깊이 1 |
| 순환 · 엣지 정합 | `from` · `to` 가 실재하고 순환이 없는가 |
| 스키마 호환 | 병합 지점의 출력 스키마가 같은가 |
| 분기 정합 | `branch` 에 조건이 있고 나가는 간선이 `true` · `false` 하나씩인가 |

넷 다 **정의만 보면 정해지는 정적인 값**이라 저장 시점과 실행 시점의 판정이 갈리지 않는다. 분기가 있어도
실제로 도는 경로가 아니라 가능한 최댓값으로 세기 때문이다.

**v2.0 에서 둘 다 바뀌었다.** `validate` 는 금액 없이 `estimate.worst_case_nodes` 만 주고, 스키마 호환 행은
없어졌다(연결 형식 검사 자체가 없다). 실측 원가는 `cost_abc` 대신 **`cost_usd` 로만 온다** — 판매자 테스트
실행(`mode=test`)에서 잰 `cost_usd` 로 노드 원가를 정한다(NOD-007, 12장). 등급 · 단가 · 선차감액 · 환불 ·
정산은 모두 우리 몫이다.

## 3. 노드 — 남은 것

애그리거트 · 저장 · API 와, 배치에 새 단계를 실어 저장하는 길까지 들어갔다. 화면 설계(3.1 · 3.2)는
[`completed/`](completed/agent-pipeline.md) 3장으로 옮겼다. **공급자가 노드를 만드는 화면은 FE 몫으로 남았다.**

### 3.3 자연어 한 줄 → 단계 초안

에이전트 하나 만들려면 단계를 몇 개로 나눌지 판단하고, 각 단계 프롬프트를 쓰고, 앞 단계 출력이 뒤에
어떤 모양으로 들어갈지까지 맞춰야 한다. **공급자 온보딩의 핵심이고, 없으면 마켓에 물건이 안 올라온다.**

노드 구조를 바꾸는 것이 아니라 앞에 붙는 도우미라 나중에 얹어도 된다. AI 파트에 요청해야 한다 (11.2).

## 4. 프론트와 맞춘 것

`frontend/src/api/agents.ts` 를 기준으로 맞췄다. **명세가 "확정" 인 것은 그쪽이 맞다.** 등록 · 저장 계약과 FE 코드를
읽고 고친 기록(4.1 · 4.2 · 4.3 · 4.5)은 [`completed/`](completed/agent-pipeline.md) 4장으로 옮겼다.

### 4.4 마켓·마이페이지 필드 — 남은 것은 다른 도메인에 걸려 있다

**MR !141** 이 마켓 목록 · 상세(`/marketplace/agents`), 내 에이전트(`GET /agents`), 즐겨찾기
(`/marketplace/agents/{id}/favorites` · `/users/me/favorites`)를 연다.

| 필드 | 어디서 |
| --- | --- |
| `price` | 공개 버전 판매가 (!141) |
| `executionCount` · `successRate` | `agent_grade_metric` 의 성공 + 공급자 탓 실패 (!141). 성공률은 실행이 없으면 0 — 등급 계산의 1 과 다르다 |
| `revenue` | 요청자가 그 에이전트로 받은 정산금 합 (!141) |
| `trend`(7일) | 정산 행 날짜로 센다 (!141). **실행 행에 에이전트가 남지 않아** 정산이 없는 실패는 빠진다 |
| `favorited` · `favoriteCount` | 즐겨찾기 표 V38 (!141) |
| `averageRating` · `reviewCount` | `agent_grade_metric` 의 시드 값. **리뷰 도메인이 없다** |
| `owner.nickname` | 채운다 |
| `profileImageUrl` | 받기만 하고 저장하지 않는다 — `null` |
| `iconUrl` · `images` | `thumbnailUrl` · `[]`. **올리는 곳이 없다** |
| `provenance` | MR !139 (원본 증명 조회) |
| 써 본 에이전트 `myExecutionCount` · `totalSpent` · `lastExecutedAt` | **요청자별 실행 이력이 없다** — `trend` 와 같은 까닭 |

**금액은 전부 문자열로 내린다.** FE 가 "소수점 오차를 막기 위해 문자열이다 — 숫자로 되돌리지 않는다"
고 못 박아 뒀다. 통화 필드는 두지 않는다. 단위가 ABC 하나뿐이라 화면이 붙인다.

**버전은 FE 모델 어디에도 없다.** 새 버전 공개(`PUT /agents/{agentId}`)는 들어갔지만 응답에 버전을 싣지 않는다.
`AgentVersion` 은 우리 안에만 있다.

## 5. 그래프 — 한 줄에서 트리로

### 5.1 무엇이 바뀌나

분기(if-else)와 **분기 뒤 합류**를 받는다. 갈래가 다 돌고 결과를 묶는 **병합은 지금 넣지 않는다** — 자리는 5.4 가 열어 둔다.

**분기 뒤 합류는 받는다(MR !119).** 갈라질 수 있는 것은 분기 노드뿐이고 분기는 한쪽만 돌기 때문에, 들어오는 선이
여럿이어도 실제로 도착하는 선은 하나다. 실행 경로는 여전히 한 줄이다. 합류 뒤의 분기 조건은 어느 갈래로 와도 거치는
노드만 읽는다. 아래 표의 "들어오는 선 1개" 는 합류가 들어오기 전의 규칙이다.

| 지금 | 바꾼 뒤 |
| --- | --- |
| 나가는 선 1개 | 분기 노드만 2개(참 · 거짓 하나씩), 나머지는 1개 (`WORKFLOW_GRAPH_NOT_TREE`) |
| 들어오는 선 1개 | **푼다** — 분기 뒤 합류를 받는다. 갈라지는 곳이 분기뿐이라 도착하는 선은 늘 하나다 |
| `nodesInOrder()` 전순서 하나 | 경로가 여러 개. 전순서가 없다 |
| `chainLength()` | `longestPathLength()` |

트리 검증 · `longestPathLength()` · 제어 노드(5.4, completed)까지 들어갔다. **남은 것은 분기가 있을 때 경로 목록을
내는 메서드**다 — 분기 실행을 열 때 만든다. 지금은 분기가 있으면 실행 조립이 `EXECUTION_005` 로 막는다.

### 5.2 실행 길이는 버전이 들고 다닌다

`GraphLimits` 의 값이 **노드 20개 / 깊이 10** 이다. 트리가 된 뒤로는 둘 다 산다.
**AI 상한은 8개다.** 지금 9~10개짜리는 저장은 되고 실행에서 튕긴다. **아직 내리지 않았다.**

8은 시간에서 나온 값이다 — 노드당 약 25초 × 8 ≈ 200초, 총 실행 시간 5분(PER-003)에서 역산.
그러므로 재야 할 것은 **실제로 돌아가는 프롬프트 노드 수**다.

#### 매번 펼쳐 세지 않는다

`AgentVersion` 은 불변이다. 만들어지는 순간 그래프가 굳고 다시 바뀌지 않는다.
그러므로 **펼친 노드 수를 버전을 만들 때 한 번 계산해 버전에 박아 둔다.**

계산도 재귀가 아니다. 그래프에 놓인 버전이 **이미 자기 값을 들고 있기 때문**이다.

> 새 버전의 노드 수 = 내 기본 노드 수 + 놓인 버전들이 든 값의 합

한 단계만 본다. 몇 겹이든 상관없다. **원가도 같은 방식으로 한 번 더해 박아 둔다** (7.3).

| 언제 | 무엇을 하나 |
| --- | --- |
| 버전을 만들 때 | **한 번.** 놓인 버전들의 값을 읽어 더해 박는다 |
| 워크플로우를 저장할 때 | **조회만.** 박힌 값을 더해 상한을 본다 — **아직 없다** |
| 주문서를 만들 때 | **끝까지 펼친다.** 프롬프트 원문이 필요하다 |

재귀가 실제로 필요한 것은 **마지막 하나뿐**이다.

#### 어느 수를 재나

| 기준 | 왜 틀리나 |
| --- | --- |
| 전체 노드 수 | 분기가 있으면 안 도는 노드까지 세어 멀쩡한 워크플로우가 거부된다 |
| 펼치기 전 개수 | 에이전트 셋을 조합하면 펼쳤을 때 9개가 되는 것을 못 막는다 |
| **펼친 뒤 가장 긴 경로** | **이것이 맞다** |

### 5.3 사용자에게는 노드 수로 말하지 않는다

**에이전트는 블랙박스다.** 수요자는 속에 노드가 몇 개인지 모르고 알 필요도 없다.
그런데 "노드 수가 8개를 넘습니다" 라고 거절하면 **자기가 셋을 놓았는데 왜 여덟이냐** 가 된다.

**시간으로 말한다.**

> 이 조합은 실행에 5분 이상 걸려 실행할 수 없습니다.

그리고 마켓의 에이전트마다 **예상 실행 시간**을 표시한다. 가격을 표시하는 것과 같다.
수요자가 조합하는 중에 미리 가늠할 수 있어야 한다.

속 구성은 여전히 감춰진다. 밖으로 나가는 것은 "이 에이전트는 약 50초 걸린다" 하나뿐이고 **그것은
상품 정보다.** 8이라는 숫자도 원래 시간에서 역산한 것이므로 되돌리는 것뿐이다.

## 7. 가격 — 에이전트 단위

### 7.1 파는 단위와 값을 매기는 단위를 맞춘다

**에이전트 하나에 값 하나다.** 내부 노드가 몇 개든, 어느 경로를 타든 고정가다.

수요자는 "이 에이전트 쓰는 데 5 ABC" 를 사는 것이지 속에 노드가 몇 개인지 알 바 아니다.
**속을 숨기는 것이 에이전트인데 가격이 속을 드러내면 앞뒤가 맞지 않는다.**

| 규칙 | 내용 |
| --- | --- |
| 조합 | 배치된 에이전트 값의 합. 반복이 없으므로 각 에이전트는 **탔거나 안 탔거나** 둘 중 하나 |
| 내부 분기 | 가격에 영향 없음 |
| 선차감 | **가장 비싼 경로.** 적게 잡으면 실행 중 잔액이 모자라고, 전부 더하면 잔액 충분한 사용자도 막힌다 |
| 부분 성공 | ~~없다~~ → **단계 단위로 센다 (295 에서 바뀜).** 성공한 단계만 쓴 만큼에 넣는다 |
| 정산 근거 | ~~판매가 고정~~ → ~~실측 `cost_abc` × 배율 (295)~~ → **성공한 단계마다 접수할 때 정한 단가(원가 × 배율) (계약 v2.0, 12장).** 엔진이 잰 원가는 청구에 쓰지 않는다 |

**두 번 바뀌었다.** 295(09-24)에서 "실측 × 배율, 떼어 둔 것이 상한" 으로 바꿨다가, 계약 v2.0(09-26)에서 엔진이 ABC
금액을 주지 않게 되며 **"금액은 전부 백엔드 단가표에서"** 로 맞췄다(12장). 견적 · 선차감은 그대로 판매가로 떼고,
끝난 뒤에는 성공한 단계의 단가만 받는다. 모두 성공하면 에이전트 값은 판매가 그대로다.

### 7.2 AI 주문서의 정산 필드

계약 v2.0 에서 `unit_price` · `base_cost` · `premium_rate` 는 **없어졌다**(보내면 무시하고 경고). 정산 필드는 노드마다
`owner_id` 뿐이다.

돌아온 값 중 우리가 보는 것은 `nodes[].status` · `failure.fault` 둘이다(환불 295 · 책임 298). `nodes[].cost_usd` 는
판매자 테스트 실행에서 원가를 잴 때만 읽는다(12장). 책임을 남길 때는 실패한 단계의, 정산할 때는 성공한 단계의
`owner_id` · `agent_id` 도 읽는다(301) — 우리가 보낸 값이 그대로 돌아온다. 정산 귀속에 `contribution[]` 은 쓰지 않는다. AI 는 받은 값을 되돌려 줄 뿐 계산하지 않으므로 나머지는 무시해도 된다.

### 7.3 원가는 버전에 박아 둔다

노드의 원가는 `BaseCostCalculator` 가 정해 노드에 박는다. 새 노드는 기본값으로 시작하고, 판매자가 테스트 실행을
하면 잰 원가로 다시 정한다(12장). 버전을 굳힐 때 그때의 노드 원가를 복사해 두므로, 노드 원가가 바뀌어도
**팔리고 있는 에이전트 값은 소리 없이 바뀌지 않는다.** 새 원가는 다음 버전부터 쓴다.

에이전트 버전의 원가는 속 노드 원가의 합이고, 거기에 등급 프리미엄(T1 +50% … T4 +0%)을 얹은 것이
최종 단가다. `AgentVersion` 이 `VersionCost` 로 받아 든다.

판매가는 고정인데 원가는 노드 수에 비례하므로 **노드를 많이 쓰는 에이전트는 마진이 줄어든다.**
불필요하게 단계를 늘리지 않을 유인이 되므로 그대로 둔다.

**원가는 모델을 따로 보지 않는다.** 판매자 테스트 실행으로 잰 달러 원가가 모델 차이를 그대로 담는다(12.4). 잰 적이
없는 노드는 모델과 상관없이 기본값 0.0135 ABC(Pro 노드당 최대 실측 × 1.5)다. 엔진이 실행 한 건을 첫 단계의
모델로 돌리는 한계는 [`contract-v2.md`](contract-v2.md) 4.1 에 있다.

## 9. 패키지와 의존 방향

```
domain
├── AbcAmount
├── user        사용자 · `UserId`
├── file        디스크 입출력 (`FileStore`)
├── payment     잔액 · 장부
├── node        작업 노드 카탈로그
├── workflow    그래프 · 배치 · 그래프 정책
├── agent       에이전트 · 버전 · 가격
└── execution   실행 단위 · 주문서 · 폴링 · 환불
```

```
workflow   ->  domain
node       ->  workflow, file, domain
agent      ->  workflow, node, domain
execution  ->  agent, workflow, node, payment, file, domain
```

**`workflow` 는 아무도 모른다.** 지금 지켜지고 있는 방향이고, 계속 지킨다. `NodeReference` 가
`AgentId` 도 `NodeId` 도 모르기 때문에 성립한다 (RULE.md 11.3).

`node` 가 `workflow` 를 아는 것은 `NodeSourceResolver` 를 구현하기 때문이다. `agent` 가
`workflow` 를 아는 것과 같은 모양이다.

### 9.1 실행 단위를 어디에 두나

6장의 공통 타입은 **노드와 에이전트를 둘 다 알아야 한다.** `workflow` 에는 둘 수 없다.

**`execution` 에 두었다** (`ExecutionUnit` · `NodeUnit` · `AgentUnit`). 네 쓰임 중 셋(선차감·주문서·정산)이 실행 쪽이고, 나머지 하나인 저장 시점
상한 검사도 **"실행 계획을 세워 본다"** 로 읽으면 같은 자리다.

저장 시점 상한 검사(5.2)를 붙이면 워크플로우 저장이 `execution` 을 거치게 된다. `workflow` 가 `execution` 을 직접 알면
방향이 깨지므로, 검사는 **저장 서비스가 조립해 부른다.**

### 9.2 애그리거트를 가로지르는 조회

협력자는 Reader 를 직접 문다 (RULE 11.4). 인터페이스는 **구현이 실제로 갈릴 때만** 둔다 (RULE 6장).

| 인터페이스 | 선언 | 구현 | 무엇을 묻나 |
| --- | --- | --- | --- |
| `NodeSourceResolver` | `workflow` | `node` · `agent` · `workflow`(제어 · 입출력) | 이 참조가 실재하는가 |
| `BaseCostCalculator` | `node` | `node` (고정값) | 이 프롬프트의 원가는 얼마인가 |

`AgentOwnershipView` 는 걷었다. 노드 소유권 · 사용 여부를 묻던 두 인터페이스도 이미 걷었고,
정책이 `AgentReader` · `NodeDefinitionReader` 를 직접 문다.

`BaseCostCalculator` 가 **PSA 의 본보기다.** 지금 구현은 파라미터를 무시하고 고정값을 내지만,
시그니처가 이미 프롬프트와 모델을 받으므로 AI 서버 구현으로 바꿀 때 계약을 다시 안 고쳐도 된다.

`AiRuntimeClient` 는 인터페이스가 아니라 `client/ai` 모듈의 구체 클래스다. 구현이 갈리지 않아 인터페이스를 두지 않았다.

## 10. 남은 작업 순서

**값을 건드리는 것이 마지막이다.** 돈부터 붙이면 무엇이 틀렸는지 알아내기 어렵다.

| | 무엇을 | 끝났다고 보는 기준 |
| --- | --- | --- |
| ~~1~~ | **실행 단위 타입** — 값 · 주인 · 펼치기를 답하는 공통 타입 (6장) | 네 군데가 같은 것을 부른다 |
| ~~2~~ | **주문서 조립 + `mock=true`** | 가짜 실행이 1초에 끝나고 응답 구조가 맞는다 |
| 3 | **실행 · 폴링 · 이력 · PDF** (8장) | 진행 게이지가 돌고 PDF 가 떨어진다. — **이력 목록만 남았다** |
| 4 | **에이전트 영속화 · 마켓 API** | 버전을 만들고 공개해 목록에 뜬다 — **마켓 API 는 MR !141. 리뷰 · 이미지 · 써 본 에이전트가 남았다** |
| 5 | **그래프 트리 확장 · 분기** (5장) | 분기가 있는 워크플로우가 저장되고, 긴 조합이 시간 메시지로 거부된다 — **저장까지 됐다. 분기 실행은 MR !134. 상한 8 · 시간 메시지가 남았다** |
| 6 | **선차감 · 정산 · 환불** | 에이전트 단위로 정산되고 안 탄 경로가 돌아온다 — **선차감 · 환불 · 정산 모두 들어갔다** |

2단계에서 `mock` 을 반드시 거친다. LLM 을 부르지 않아 1초에 끝나고, **GMS 크레딧은 팀 공용**이며,
응답 구조는 실제와 완전히 같다. 형식 문제를 여기서 전부 턴다.

**1~3 은 에이전트 없이 끝까지 간다.** 내 노드만으로 만든 워크플로우는 펼칠 것도 정산 쪼갤 것도 없다.
그것으로 파이프라인 전 구간을 검증하고 나서 4부터 에이전트를 얹는다.

5 는 다른 것과 얽히지 않으므로 아무 때나 껴도 된다. **`GraphLimits` 를 8로 내리는 것도 여기서 한다** —
지금 내려봐야 실행이 없어 확인할 방법이 없다.

| --- | --- |
| 금액 타입 | `AbcAmount` 하나. `Money` 는 걷어냈다 |
| 원가 산정 | `BaseCostCalculator`. 판매자 테스트 실행으로 잰 달러 원가의 최근 5번 중앙값 × 1.5 × 환산율, 없으면 설정 기본값 (12장) |
| 원가를 어디 두나 | 노드에 박는다. 매번 계산하면 팔리고 있는 에이전트 값이 소리 없이 바뀐다 |
| 입력 출처 위치 | 노드가 아니라 **배치** |
| 자기 에이전트를 자기가 쓸 때 | **할증 없이 원가만** (BE 임시 결정). 할증은 판매자 몫이라 자기에게 주는 돈이다. 원가까지 받지 않을지는 기획 대기 |
| 결과물 보관 위치 | **서버 로컬 디스크 + 도커 이름 볼륨.** Runtime 과 나눠 쓸 저장소가 필요 없어졌다 |
| 에이전트 중첩 | **금지.** 계약이 중첩 깊이 1 로 못박았다 — 에이전트 안에 에이전트를 넣을 수 없다 |
| 폴링 루프 구조 | 실행마다 공용 스케줄러에 다음 조회를 예약한다 ([`completed/`](completed/agent-pipeline.md) 8.13) |
| 실행 단위 타입 위치 | `domain/execution` |
| 끝난 뒤 사용액 | **성공한 단계마다 접수할 때 정한 단가의 합, 떼어 둔 금액이 상한** (계약 v2.0, 12장). 1 ABC = 1 USD 는 설정 `node.base-cost.abc-per-usd` |

자기 실행은 정산금 적립과 등급 집계에서 **빼야 한다** (301 · 303). MVP 는 수수료 없이 차감액 전액을
정산금으로 주므로(PAY-015), 빼지 않으면 원가만 내도 ABC 가 출금 가능한 정산금으로 바뀌고 사용량이 부풀어 등급이 오른다.

#### 업로드 원본 보관 기간

요구사항 정의서 OI-08 의 권장안은 **"업로드 원본은 실행 완료 즉시 폐기"** 다. 이대로 가면 재실행(MYP-003 ·
EXE-017)이 불가능하다. 원본이 없으면 사용자가 매번 같은 파일을 다시 올려야 하고, "실패 지점부터 재실행" 은
아예 성립하지 않는다.

**원본도 결과물과 같은 30일로 두기를 권한다.** 잃는 것은 보관 기간 동안의 디스크와 노출 면적이고, 얻는 것은
재실행 전체다. 확정은 팀이 한다.

정해지면 폐기 배치를 하나 붙인다. 지울 것은 셋이다.

| | 키 | 조건 |
| --- | --- | --- |
| 실행 입력 파일 | `executions/{id}/input{ext}` | 보관 기간이 지났다 |
| 실행 결과 | `execution_result` 가 가리키는 파일 | 보관 기간이 지났다 |
| 노드 참고 자료 | `nodes/{nodeId}/{refFileId}{ext}` | **어느 노드도 · 어느 굳힌 버전도 가리키지 않는다** — 잘못 세면 팔린 에이전트가 실행 중에 깨진다 |

재실행 API 도 아직 없다. 보관 기간을 정할 때 같이 본다.

#### 자기 에이전트 중첩

남의 에이전트는 판매 경로에서 애초에 막히므로, 중첩이 생기는 경로는 **자기 것뿐**이다.
공급자가 자기 에이전트를 자기 새 워크플로우에 놓고 그것을 다시 파는 경우다. 지금 코드는 허용한다.

**세는 비용은 문제가 아니다.** 5.2 대로 버전이 값을 들고 다니므로 몇 겹이든 더하기 한 번이다.
순환도 6.2 대로 버전 고정이 막는다.

**남는 쟁점은 정산이다.** 에이전트가 정산 단위인데 중첩되면 안쪽 에이전트도 정산 단위인지가 갈린다.
같은 사람이라 자기가 자기에게 주는 꼴이므로 의미가 없고, 결국 **"최상위 에이전트만 정산 단위"**
라는 예외가 붙는다. 규칙이 하나에서 둘이 된다.

**금지로 정해졌다.** 우리가 고를 것도 없이 계약이 중첩 깊이 1 이다. 잃는 것은 "내 에이전트를 재사용"
인데 워크플로우를 복사해 노드를 직접 넣으면 된다. 요구사항 정의서의 중첩 깊이 3 은 계약에 맞춰 내린다.

**코드는 아직 요구사항대로 허용한다.** AGT-001 이 본인 에이전트 캡슐화를 허용하고, AGT-006 이 안쪽을 Base Cost
로 더하라고 한다. 그래서 안쪽 에이전트의 등급 할증은 붙지 않고 바깥 등급 할증만 한 번 붙는다(MR !83 리뷰).
AI Runtime 은 중첩 깊이 1 이라(integration-guide 5.2) 요구사항과 어긋난다. 지금은 BE 가 펼쳐 `llm` 노드로만
보내 걸리지 않지만, 에이전트 안에 분기가 생겨 `agent` 형식으로 보내면 막힌다. 기획 · AI 팀에 올려 둔 상태다.

### 11.2 AI 파트에 물었고, 답이 왔다

계약 09-22 갱신본이 [`ai-runtime-questions.md`](ai-runtime-questions.md) 의 질문을 거의 다 답했다. v2.0 에서 몇 줄이 다시
바뀌었다 — 분기 조건은 저장할 때 `validate` 가 견본 필드로 검사하고, `refund_scope` 는 그대로다.

| 물은 것 | 답 |
| --- | --- |
| 전송을 Redis Streams 로 바꿀 수 있나 | **바꾸지 않는다.** 계약 §4 가 큐를 쓰지 않는 이유를 셋 적어 두었다 — 재배달로 정산이 중복되고, 접수 시점의 동기 검증이 사라지고, 얻는 것이 폴링 제거 하나뿐이다. **HTTP + 폴링이 확정이다** |
| MinIO 에서 파일을 읽고 PDF 를 쓸 수 있나 | **필요 없어졌다.** Runtime 이 스토리지에 직접 쓰지 않는다. 우리가 `/artifact` · `/pdf` 로 받아 우리 저장소에 넣는다 |
| 분기 조건을 어떤 형식으로 보내나 | `branch` 노드의 `condition` 과 `edges` 의 `when` 이다 (계약 §5.2 · §5.3) |
| 안 탄 노드가 `not_executed` 에 담기나 | **담긴다.** `branch_not_taken` · `upstream_failed` 로 사유까지 온다. 환불 대상을 그대로 쓴다 |
| 노드 수 상한을 배열로 보나 경로로 보나 | **둘 다.** 캔버스 8 · 전개 후 20 · 최장 경로 8 이고, 넷 다 정적인 값이라 판정이 갈리지 않는다 (1.5) |
| 도구 노드 계획이 있나 | **MVP 에 없다.** `type` 은 `llm` · `branch` · `agent` 셋이다 |
| 노드에 참고 자료를 붙일 수 있나 | **된다.** `ref_files` 와 `ref_file_<node_id>_<n>` 파트가 열렸다 |
| 정산 필드를 비워 보내도 되나 | **전부 선택이다.** 다만 `0` 으로 채우지 않는다 — `0` 과 "값 없음" 을 구분할 수 없다 |

**남은 것은 하나다.** 자연어 한 줄로 단계 초안을 만들어 줄 수 있는지 (질문 2). 답이 없어도 지금 작업은
막히지 않는다.

**실패 책임까지 AI 가 판정해 준다.** `failure.fault` 가 `supplier` · `consumer` · `platform` 로 오고
`refund_scope` 가 환원 대상과 정산 유지 대상을 나눠 준다. PAY-011 을 우리가 역산하지 않아도 된다.
받은 판정을 남기는 규칙은 [`completed/`](completed/agent-pipeline.md) 8.5.

### 11.3 이미 어긋나 있는 것

| 항목 | 우리 | 계약 |
| --- | --- | --- |
| **에이전트를 펼치는 쪽** | 백엔드가 평평한 프롬프트 배열로 펼쳐 보낸다 (`AgentUnit` · `ExecutionUnitAssembler`) | **Runtime 이 펼친다.** `type: "agent"` 노드에 `nodes` · `edges` 를 그대로 끼워 보내라고 한다 |
| 오류 형식 | `ApiResult` | `{"detail": {code, message, errors}}` — 번역 계층과 `EXE_*` 코드가 필요하다 |
| 용어 | 캡슐화를 걷어내고 **버전 생성 · 확정 · 공개** 로 나눔 | 연동 문서가 "캡슐화" 를 그대로 쓴다 |
| **모델 단위** | 노드마다 모델을 저장한다. 실행할 때는 첫 단계의 모델을 최상위 `model` 로 싣는다 (MR !126) | 실행 한 건에 모델 하나. 엔진은 노드의 `model` 을 읽지 않고 Gemini(GMS)만 부른다 |

**모델이 섞이면 틀린다.** 한 워크플로우에 Flash 노드와 Pro 노드가 있으면 첫 단계의 모델로 전부 돈다. 판매자가 고른
모델로 돌지 않고 오류도 나지 않는다. 품질 · 실패 책임 · 원가가 모두 어긋난다. **엔진이 노드별 `model` 을 받아야 풀린다**
— 알고 둔 한계이고, AI 파트에 요청한다. 노드별 모델을 저장하는 칸은 그때 그대로 실으려고 둔다.

노드 수 상한(우리 10 · 계약 8)은 5단계에서 내린다. 1.5 의 `validate` 를 부르면 우리가 값을 들고 있을
이유 자체가 줄어든다.

#### 에이전트를 누가 펼치나 — 다시 봐야 한다

6장은 **우리가 펼쳐 평평한 배열로 보낸다**는 전제 위에 서 있고, 그렇게 구현해 머지까지 했다.
계약은 다르게 말한다.

**계약이 분명하게 적은 것:** 에이전트 안에 분기 · 분할 · 병합이 있으면 **평평한 배열로는 펼 수 없다.**
`nodes` + `edges` 형태로 보내면 되지만, 그 경우 종단 payload 가 선언된 출력 스키마를 지키는지 보는
**경계 검증(`AGENT_BOUNDARY_VIOLATION`)이 적용되지 않는다.** v2.0 은 경계 검증 자체를 없앴다.

| 어느 쪽으로 가나 | 얻는 것 | 잃는 것 |
| --- | --- | --- |
| 우리가 펼친다 (지금) | 이미 돌아간다. Runtime 이 에이전트를 몰라도 된다 | 분기가 들어오는 순간 못 편다. 경계 검증이 없다 |
| 그대로 끼워 보낸다 | 경계 검증. 분기가 들어와도 그대로 | `ExecutionUnitAssembler` 를 다시 쓴다 |

**분기 실행을 열기 전에 정한다.** 트리 저장은 이미 들어갔다. 분기가 들어오면 지금 구조가 먼저 막히므로,
그때 고치는 것과 지금 고치는 것의 차이는 순서뿐이다.

### 12.2 청구 — 금액은 우리 단가표에서

접수할 때 단계마다 `단가 = 그 단계 노드의 원가 × 놓인 자리의 배율` 을 정해 `execution_charge_rate.unit_price` 에 남긴다.
끝나면 성공한 단계의 단가를 더한 만큼 쓰고 나머지를 돌려준다. 엔진이 잰 원가가 단가보다 크든 작든 받는 값은 단가다.

에이전트 판매가는 버전 원가 합에 배율을 한 번 곱해 반올림하고, 단가는 단계마다 곱해 반올림한다. 끝자리에서 단가 합이
판매가를 넘으면 떼어 둔 것까지만 받고 몫을 같은 비율로 줄인다(끝자리 차이는 가장 큰 몫에).

### 12.3 플랫폼 탓 실패 — 플랫폼 부담 계정

계약 8.5 는 "플랫폼 과실로 공급자가 손해 보지 않게, 앞서 성공한 노드는 정산을 유지하고 차액은 플랫폼이 부담" 이다.
그래서 사용자 예치는 환불로 모두 돌려주고, 판매자 정산은 **`PLATFORM_EXPENSE`(참조 `PLATFORM`) 에서 빼서** 준다.
이 계정은 마이너스로 쌓이며 "플랫폼이 판매자에게 대신 준 ABC" 를 보여 준다.

`ABC_ISSUANCE`(발행) 에서 꺼내지 않은 까닭은, 발행 계정은 체인 위 토큰으로 받친 ABC 만 세야 해서다(1 토큰 = 1 ABC).
플랫폼 부담만큼은 보관 지갑에 토큰이 없으므로, 판매자들이 출금하면 운영자가 그만큼 지갑을 채워야 한다.

엔진이 기한 안에 끝을 알리지 않아 우리가 끊은 실행은 어느 단계가 성공했는지 몰라 정산하지 않고 전부 돌려준다.

### 12.4 노드 원가 — 판매자 테스트 실행

`POST /api/v1/nodes/{nodeId}/test-runs` 가 노드 하나를 엔진에 `mode=test` 로 실제로 돌린다. 참고 자료도 함께 나간다.
`GET .../test-runs/{testRunId}` 로 끝을 조회하면 결과물(봉투 JSON)과 새 원가가 온다.

| 규칙 | 내용 | 까닭 |
| --- | --- | --- |
| 원가 | 최근 성공한 테스트 5번의 `cost_usd` **중앙값** × 1.5 × 환산율(1) | 판매가 전액이 판매자 몫이라 최댓값이면 긴 입력 한 번으로 원가를 부풀릴 수 있다 |
| 잰 적이 없으면 | 설정 기본값 0.0135 ABC | AI 파트가 알린 Pro 노드당 최대 실측 0.009 달러 × 1.5 |
| mock · 실패 | 원가에 넣지 않는다 | 모델을 부르지 않았거나 결과물이 없다 |
| 비용 | 무료. ABC 가 움직이지 않는다 | 엔진이 test 의 `contribution` 을 비워 보낸다 |
| 한도 | 노드당 하루(UTC) 5번. 엔진에 넘기지 못한 테스트는 세지 않는다 | 모델 요금은 플랫폼이 낸다 |
| 동시성 | 접수는 노드 행을 잠그고 센다. 닫을 때는 노드 행을 잠근 뒤 최근 기록을 읽는다 | 한도를 넘겨 받지 않고, 동시에 끝난 테스트를 빠뜨리지 않는다 |
| 결과물 | 닫을 때 한 번 받아 **JSON 으로 읽어 본 뒤** `node_test_run.result_json` 에 둔다. 다시 볼 때는 둔 것을 준다 | 조회마다 엔진을 부르지 않는다. 엔진이 JSON 이 아닌 것을 주면 결과물 없이 닫아, 응답이 깨지지 않는다 |
| 접수 지우기 | 엔진에 넘기기 전 실패일 때만 지운다 | 엔진이 받은 뒤 지우면 도는 실행의 원가와 결과물을 잃는다 |
| 이미 굳힌 버전 | 원가를 바꾸지 않는다. 새 원가는 다음 버전부터 | 팔리는 값이 소리 없이 바뀌지 않게 |
| 노드를 고치면 | 그동안 잰 원가를 이어 쓴다 | 다시 테스트하면 최근 기록부터 바뀐다 |

끝은 판매자가 조회할 때 엔진에 물어 안다. 실행처럼 뒤에서 따라가지 않는 까닭은 돈이 묶이지 않아 늦게 닫혀도 잃는 것이 없어서다.
