# 끝난 설계 — 에이전트 파이프라인

[`../agent-pipeline.md`](../agent-pipeline.md) 에서 **구현이 끝나** 걷어낸 장이다. 지금 코드가
왜 그 모양인지 되짚을 때만 본다. **현재 규칙의 원본이 아니다** — 규칙은 `docs/RULE.md`,
구조는 `docs/ARCHITECTURE.md` 가 원본이다.

> 카테고리·등급·공개 범위 필터는 명세에 없고, 화면에 표시할 자리가 없다 — `agents.ts`

### 6.1 지금 표현되지 않는 것

`GraphNode` 가 답하는 것은 셋뿐이다 — 어느 자리인가, 어떤 종류인가, 무엇을 가리키는가.
전부 **배치 정보**다. "이것이 실행되면 결과를 내는 한 덩어리다" 는 어디에도 없다.

그래서 아래 셋을 물을 데가 없다.

| 물음 | 지금 |
| --- | --- |
| 이 자리에 놓인 것의 **값이 얼마인가** | 값은 `AgentVersion` 에만 있다 |
| 실행하면 **프롬프트 몇 개로 펼쳐지는가** | 펼치기라는 개념이 없다 |
| **누구 것인가** | `AgentPlacement` 로 에이전트만 골라낸다. 노드는 못 본다 |

### 6.2 합성 구조다

한 자리에 놓이는 것은 둘 중 하나다.

- **잎** — 노드. 프롬프트 하나, LLM 한 번. 더 쪼개지지 않는다.
- **가지** — 에이전트 버전. 안에 그래프가 있고 거기 또 잎과 가지가 있다.

고리는 이미 코드에 있다.

```
그래프 ──담는다──> AgentNode ──(식별자, 조회 필요)──> AgentVersion ──담는다──> 그래프
```

`AgentNode` 가 식별자만 들어 **한 칸이 끊겨 있다.** 끊어 둔 것은 맞다. 객체를 직접 물면 워크플로우
하나 읽는데 에이전트가 통째로 딸려 온다. 애그리거트를 넘는 참조는 식별자여야 한다.

문제는 **그 끊긴 고리를 이어 걷는 타입이 없다**는 것이다. 구조는 있는데 그것을 다루는 물건이 없다.

### 6.3 없으면 같은 분기가 네 군데에서 반복된다

| 어디 | 무엇을 |
| --- | --- |
| 저장할 때 | 펼친 경로 길이가 상한을 넘는가 |
| 팔 때 | 놓인 것이 전부 내 것인가 |
| 선차감할 때 | 놓인 것들의 값 합이 얼마인가 |
| 주문서 만들 때 | 놓인 것을 프롬프트 목록으로 편다 |

네 군데 전부 `sourceType` 을 보고 갈라지게 된다. **한 곳만 고치고 다른 데를 빠뜨리는 것이 시간 문제다.**

### 8.3 선차감 — 엔진에 넘기기 전에 뗀다

**순서가 바뀌었다.** 전에는 엔진을 먼저 부르고 받은 실행 번호로 실행을 저장했다. 그 뒤에 잔액을 보면
이미 돌기 시작한 실행을 막게 되고, 엔진 호출을 트랜잭션 안에 넣으면 커넥션을 쥔 채 기다린다
(ARCHITECTURE 4.2). 그래서 이렇게 나눴다.

| | 트랜잭션 | 하는 일 |
| --- | --- | --- |
| 1 | 없음 | 같은 `requestId` 로 접수한 실행이 있으면 그것을 돌려주고 끝낸다. **다시 따라가지 않는다** |
| 2 | 없음 | 엔진에 보낼 요청(JSON · 파일 위치)을 **떼기 전에** 다 만든다. 여기서 실패하면 뗀 것이 없다 |
| 3 | **하나** | 실행을 적는다 → 쓸 수 있는 잔액 행을 잠그고 읽는다 → 모자라면 전부 되돌린다 → 견적만큼 `ABC_BALANCE` → `EXECUTION_ESCROW` |
| 4 | 없음 | 엔진에 넘긴다 |
| 5a | 하나 | 받았으면 실행 번호를 붙이고, 컨트롤러가 뒤에서 따라가기(!84)를 건다 |
| 5b | **하나** | 4 · 5a 에서 **무엇이 실패하든** 예치를 되돌리고 실행을 `FAILED` 로 남긴다 |

3 과 5b 는 `ExecutionReservationManager` 가 맡는다. 엔진 호출을 사이에 둔 두 쓰기 묶음이라 Service
트랜잭션 하나로 묶을 수 없어서다. 충전 확정(`ChargeConfirmationManager`)과 같은 모양이다.

`start` 는 `ExecutionStart` 로 새로 만든 실행인지를 함께 돌려준다. 같은 요청 번호로 돌려받은 앞 실행을
다시 따라가면 조회가 두 줄기가 되고, 따라가기를 시작하며 상태를 `QUEUED` 로 적어 끝난 실행이 되살아난다
(MR !88 리뷰). 따라가기는 api 계층(`api.batch`)이라 Service 가 부를 수 없어 컨트롤러가 가른다.

| 지키는 것 | 어떻게 |
| --- | --- |
| 잔액이 음수가 되지 않는다 | 잔액을 `SELECT ... FOR UPDATE` 로 읽는다. 일반 조회는 트랜잭션 첫 조회 시점 값을 볼 수 있어 동시 실행이 같은 돈을 두 번 쓴다. 잠금을 빼면 동시성 테스트가 깨지는 것까지 확인했다 |
| 한 실행에 한 번만 뗀다 | 장부 키 `execution-reserve:{실행ID}` (UNIQUE) |
| 같은 누름을 두 번 떼지 않는다 | `execution` 의 UNIQUE `(requester_id, request_id)`. 차례로 다시 오면 앞 실행을 돌려주고, 동시에 오면 늦은 쪽이 `EXECUTION_006`(409) |
| 되돌리기도 한 번만 | 장부 키 `execution-release:{실행ID}`. 실행 뒤 결과를 보고 하는 환불과 키가 달라 서로 막지 않는다 |
| 잔액이 모자라면 아무것도 남지 않는다 | 실행 기록과 차감이 한 트랜잭션이다. `PAYMENT_008`(402) 에 견적 API 와 같은 이름으로 금액을 싣는다 |

`mock` 실행도 똑같이 뗀다. 모델을 부르지 않아 실측 원가가 0 이라 끝나면 전부 돌아오고 정산할 것도 없다(8.4 · 8.6).

**남은 한계**

| 상황 | 지금 | 필요한 것 |
| --- | --- | --- |
| 엔진이 받았는데 응답만 10초를 넘긴다 | 클라이언트가 "꺼져 있음" 과 같은 `REQUEST_FAILED` 로 알려 구분할 수 없다. 실패로 보고 돌려주므로 엔진 쪽 실행이 공짜가 될 수 있다 | 시간 초과를 따로 알리고, 결과 불명은 재조회로 확인 |
| 엔진이 받은 뒤 실행 번호 저장이 실패한다 | 돌려주고 `FAILED` 로 남긴다. 엔진 쪽 실행은 공짜가 된다. 사용자 돈을 묶어 두는 것보다 낫다고 봤다 | 엔진에 실행 취소를 요청하는 길 |
| 돌려주기마저 실패한다 (DB 가 통째로 안 될 때) | 원래 실패에 덧붙이고 `ERROR` 로그에 실행 ID 를 남긴다. 예치는 묶인다 | 번호 없는 채 오래된 실행을 찾아 정리하는 작업 |

### 8.4 끝난 뒤 환불 — 쓰지 않은 만큼 돌려준다 (PAY-009 · PAY-010)

**떼어 둔 것 = 쓴 만큼 + 돌려줄 만큼.** 돌려줄 만큼은 `EXECUTION_ESCROW` → `ABC_BALANCE` 로 옮기고,
쓴 만큼은 같은 자리에서 단계 주인의 정산금으로 옮긴다(8.6). 닫힌 실행의 예치에는 아무것도 남지 않는다.

| 단계 | 쓴 만큼에 넣나 |
| --- | --- |
| 성공 (`nodes[].status = succeeded`) | 넣는다. **실측 원가 `cost_abc` × 접수 때 정한 배율** |
| 실패 | 넣지 않는다. 토큰을 썼어도 결과물을 받지 못했다 |
| 돌지 않음 (`skipped` · `pending`) | 넣지 않는다. 분기로 안 간 것과 앞이 실패해 못 간 것 모두 |
| 플랫폼 탓 실패 (`failure.fault = platform`) | **전부 돌려준다.** 성공한 단계도 넣지 않는다 (계약 8.5). 공급자에게도 주지 않는다 (8.6) |
| 주인을 가리킬 수 없는 성공 (`owner_id` 가 비었거나 숫자가 아님, 단계 번호가 빔) | 넣지 않는다. 받을 사람이 없는 값을 사용자에게 받지 않는다. 우리가 늘 채워 보내므로 엔진이 값을 잃을 때만 생기고, 생기면 `WARN` 로그로 남긴다 |

- **배율은 `1 + 등급 할증`이다.** 노드와 내 에이전트는 1, 남의 에이전트는 그 버전 등급의 배율이다. 견적에서
  판매가를 셀 때 쓴 값과 같다. 에이전트를 펼친 단계는 모두 그 에이전트 자리의 배율을 따른다.
- **배율은 접수할 때 단계마다 적어 둔다(`execution_charge_rate`).** 실행 중에 등급이 바뀌거나 워크플로우를 고쳐도
  접수한 순간의 값으로 센다. 떼어 둔 금액은 `execution.reserved_abc` 에 적는다.
- **떼어 둔 것보다 더 받지 않는다.** 실측이 견적을 넘어도 접수할 때 알린 금액이 상한이다.
- **`mock` 은 전부 돌아온다.** 모델을 부르지 않아 `cost_abc` 가 0 이다. 접수 때는 똑같이 떼므로 잔액 검사는 그대로 거친다.

**실행을 닫는 자리는 `ExecutionReservationManager.finish` 하나다.** 끝을 알아차리는 길이 둘이라, 둘 다 여기로 온다.
상태만 옮기는 `moveTo` 로 끝난 실행을 닫으면 환불이 빠진다(MR !94 리뷰).

| 누가 | 언제 | 엔진이 알린 상태(`run`) |
| --- | --- | --- |
| 모니터(`ExecutionMonitor`) | 뒤에서 2초마다 묻다가 끝을 볼 때 | 마지막 응답 |
| 모니터 | 기한(단계 수 × 40초 + 60초) 동안 변화가 없어 실패로 끊을 때 | **없음 → 플랫폼 탓으로 보고 전부 돌려준다** |
| 조회(`GET /runs/{id}`) | 모니터가 놓친 실행(재기동 · 닫기 실패)을 엔진에 물어 끝을 볼 때 | 그 응답 |

`finish` 는 한 트랜잭션에서 실행 행을 잠그고 → 이미 닫혔으면 그만 → 닫고 → 쓰지 않은 만큼 돌려주고 → 쓴 만큼을 정산한다(8.6).

| 지키는 것 | 어떻게 |
| --- | --- |
| 닫혔는데 돌려주지 않은 실행이 없다 | 상태를 옮기는 것과 환불이 한 트랜잭션이다. 모니터에서 실패하면 기록이 안 끝난 채 남아 조회가 다시 닫는다 |
| 모니터와 조회가 겹쳐도 한 번만 돌려준다 | 실행 행을 `SELECT ... FOR UPDATE` 로 잠그고 닫혔는지 먼저 본다. 뒤에 장부 키 `execution-refund:{실행ID}` (UNIQUE) 가 한 번 더 막는다 |
| 되돌리기와 부딪히지 않는다 | 엔진이 받지 않은 실행은 `execution-release:` 로 돌려주고 끝난 상태라 여기에 오지 않는다 |
| 선차감 전의 실행 | 뗀 것이 없어(`reserved_abc` 비어 있음) 닫기만 한다. V22 가 장부에서 이미 뗀 금액을 옮겨 적는다 |

**남은 한계**

| 상황 | 지금 | 필요한 것 |
| --- | --- | --- |
| 우리 서버가 재기동하고 사용자도 조회하지 않는다 | 모니터가 따라가던 목록은 메모리라 사라지고, 조회가 없으면 끝을 알아차릴 길이 없어 예치가 묶인다 | 기동할 때 안 끝난 실행을 다시 따라가기 |
| 서버 재기동 뒤 엔진도 실행을 잊었다 (404) | 조회가 `EXECUTION_002` 로 실패하고 예치가 묶인다 | 기한을 넘긴 안 끝난 실행을 실패로 닫고 돌려주기 |
| 책임별 차등 정산 | ~~`platform` 만 전액 환불로 가르고 `supplier` · `consumer` 는 같게 본다~~ → 환불은 계약대로 같다. 책임은 8.5 에서 남긴다 | PAY-011 (들어감) |

### 8.5 실패 책임 — 누구 탓인지 남긴다 (PAY-011)

**판정은 엔진이 한다.** `failure.fault` 가 `supplier` · `consumer` · `platform` 로 오고(계약 8.5 · 9.2),
우리는 받은 것을 한 가지 규칙(`ExecutionFailure`)으로 정리해 **실행을 닫는 트랜잭션(`finish`) 안에서** `execution_failure` 에 남긴다(V23).
오류 코드를 보고 우리가 다시 판정하지 않는다 — 계약 9.2 의 표를 베끼게 되고 엔진과 어긋날 수 있다.

| 상황 | 남기는 책임 | 오류 코드 |
| --- | --- | --- |
| 엔진이 `fault` 를 알림 | 그대로 | 엔진의 `error_code` |
| `fault` 가 비었거나 모르는 값 | `PLATFORM` | 엔진의 `error_code` |
| 실패했는데 `failure` 가 없음 | `PLATFORM` | `ABC_RUNTIME_UNREPORTED` |
| 기한 안에 끝을 알리지 않아 우리가 끊음 | `PLATFORM` | `ABC_RUNTIME_STALLED` |
| 엔진에 넘기지 못함 (선차감 되돌리기) | `PLATFORM` | `ABC_RUNTIME_UNREACHABLE` |

**근거가 없으면 플랫폼 탓이다.** 공급자나 수요자에게 넘길 근거가 없는 실패는 우리가 진다(PAY-011 "판정 불가는 시스템 책임").
환불(8.4)도 같은 판정을 본다 — 책임을 모르는 실패는 성공한 단계까지 돌려준다.

**실행 행이 아니라 따로 둔 표에 적는다(MR !98 리뷰).** `execution` 은 모든 실행의 생애 주기와 선차감을 맡고 목록 조회와
`findForUpdate` 잠금이 쓰는 행이다. 판정은 실패한 실행에만 있고, 한 번 적고 고치지 않고, 읽는 쪽도 성공률 · 정산이라
성격이 다르다. 단계별 배율을 `execution_charge_rate` 로 뗀 것과 같은 결이다.

| 칸 (`execution_failure`) | 뜻 | 언제 채우나 |
| --- | --- | --- |
| `execution_id` (PK) | 어느 실행인가 | 실패한 실행마다 한 줄. **PK 라 같은 실행을 두 번 적으면 DB 가 막는다** |
| `failed_step_id` · `failure_code` | 어느 단계에서 무슨 오류로 | 엔진이 알린 만큼. 칸(16 · 64)보다 길면 잘라 넣는다 |
| `fault` | 누구 탓인가 | 늘 |
| `affects_success_rate` | 공급자 성공률에 넣나 | 공급자 탓이고 엔진이 `true` 로 알릴 때만 참. 값이 없으면 넣지 않는다 |
| `supplier_id` · `agent_id` | 어느 공급자 · 에이전트 탓인가 | 공급자 탓일 때만 |

- **실행 ID 를 우리가 정해 넣으므로 늘 새 줄로 넣는다(`Persistable`).** 그러지 않으면 JPA 가 이미 있는 줄을 찾아 덮어써
  PK 가 두 번 적기를 막지 못한다.
- **엔진이 보낸 값은 잘라 넣는다.** 계약에 길이가 없다. 넘친 채 저장하다 실패하면 같은 트랜잭션의 실행 닫기와 환불까지
  되돌려지고, 모니터가 올 때마다 같은 자리에서 실패해 실행이 영영 닫히지 않는다(MR !98 리뷰).
- **엔진에 넘기지 못한 실행(`release`)도 같은 `finish` 로 닫는다.** 이미 닫혔으면 판정을 다시 적지 않는다.
- 성공률 · 정산용 인덱스(`agent_id` · `supplier_id`)는 이 표를 조회하는 쪽이 생길 때 그 조회에 맞춰 건다.

- **공급자 탓이어도 성공률에 넣지 않는 오류가 있다.** `REF_FILE_REJECTED` · `PROMPT_TEMPLATE_INVALID` 는 `supplier` 지만
  `affects_success_rate: false` 로 온다(계약 9.2).
- **누구 탓인지는 우리가 보낸 값으로 찾는다.** 단계마다 `owner_id`(!91)와 `agent_id`(298 에서 더함 — 캔버스에 놓인
  에이전트 자리의 에이전트)를 실어 보내면 엔진이 `nodes[]` 에 그대로 돌려준다. 실패한 단계의 것을 읽는다.
  에이전트 안의 에이전트는 바깥 자리의 에이전트로 묶는다 — 팔린 물건이 바깥 에이전트다.
- **이미 닫힌 실행은 판정을 바꾸지 않는다.** 모니터와 조회가 겹쳐도 처음 닫은 쪽의 판정이 남는다.

**사용자 환불은 책임에 따라 갈리지 않는다.** 계약 8.5 에서 `supplier` · `consumer` 둘 다 "실패 단계 이후 환원, 앞서 성공한
단계 정산 유지" 다. 책임이 가르는 것은 **공급자 쪽**이다.

| 읽는 곳 | 무엇을 |
| --- | --- |
| 성공률 (PAY-018, 303) | `affects_success_rate` 가 참인 실패만 그 에이전트의 실패로 센다. 자기 실행 · mock 은 따로 뺀다 |
| 정산 (PAY-012, 301) | `PLATFORM` 이면 정산하지 않는다. 계약은 플랫폼이 차액을 내 공급자 정산을 유지하라고 하지만 플랫폼 계정을 두지 않았다 (8.6) |

**남은 한계**

| 상황 | 지금 | 필요한 것 |
| --- | --- | --- |
| 플랫폼이 끼운 입출력 노드가 실패 | 입출력 노드가 있으면 실행을 막아(`EXECUTION_005`) 아직 생기지 않는다 | 풀리면 `fault: supplier` 로 와도 남의 탓이 아니게 가려야 한다 (AI 질문 3-2) |
| 엔진이 `owner_id` · `agent_id` 를 돌려주지 않음 | 책임은 남기고 공급자 · 에이전트는 비워 둔다 | 필요하면 접수 때 단계마다 주인 · 에이전트를 적어 둔다 (`execution_charge_rate` 처럼) |
| 이 표보다 먼저 끝난 실행 | 줄이 없다 | 성공률 집계에서 책임 모름으로 빼거나 플랫폼으로 본다 (303) |

### 8.6 정산 — 쓴 만큼을 단계 주인에게 준다 (PAY-012)

**수수료가 없다.** 사용자가 쓴 만큼(8.4)이 전부 그 단계를 만든 주인의 정산금(`PAYOUT_BALANCE`)으로 간다.
플랫폼 수익 계정은 두지 않는다 (2026-09-25 담당 결정. AI `grading-formula.md` 4장 "MVP 는 수수료 0%" 와 같다).
실행을 닫는 트랜잭션(`finish`) 안에서 환불과 함께 적는다.

```
접수 (8.3)   ABC_BALANCE(사용자)      ──떼어 둔 것──▶  EXECUTION_ESCROW(사용자)
닫기 (8.4)   EXECUTION_ESCROW(사용자) ──돌려줄 만큼──▶ ABC_BALANCE(사용자)
닫기 (8.6)   EXECUTION_ESCROW(사용자) ──쓴 만큼────▶   PAYOUT_BALANCE(단계 주인마다)
```

| 단계 | 누구에게 얼마를 |
| --- | --- |
| 성공 | 그 단계의 주인(`nodes[].owner_id`)에게 실측 원가 × 접수 때 배율. 남의 에이전트면 할증까지 판매자 몫이다 |
| 실패 · 돌지 않음 | 없다. 사용자에게 받지 않았다 (8.4) |
| 공급자 · 수요자 탓 실패의 앞선 성공 단계 | 준다. 사용자가 그만큼 냈다 (계약 8.5 와 같다) |
| 플랫폼 탓 실패 | **주지 않는다.** 계약 8.5 는 "정산 유지, 차액은 플랫폼 부담" 이지만 차액을 낼 플랫폼 계정이 없다. AI 팀에 알릴 것 |
| 내 에이전트 · 내 노드를 내가 씀 | **내 정산금으로 간다.** 원가만 낸 것이(293) 내 예치에서 내 정산금으로 옮겨 간다. 등급 집계(303)에서는 뺀다 |

**주인은 엔진이 돌려준 `owner_id` 로 찾는다.** 우리가 단계마다 실어 보낸 값(!91)이 그대로 돌아온다.
에이전트 안의 단계는 버전을 굳힐 때 박은 주인(V18 — 에이전트 주인)이다. 실패 책임(8.5)과 같은 규칙(`StepOwner`)으로 읽는다.

**실측이 떼어 둔 것을 넘으면 모두 같은 비율로 줄인다.** 사용자는 떼어 둔 만큼만 낸다(8.4). 이때 각자 실측 몫에
비례해 나눈다 — 실행 순서로 나누면 뒤에 놓인 판매자만 덜 받는다. 여섯째 자리 아래는 버리고, 버려서 남은 끝자리는
가장 큰 몫에 붙여 **정산금의 합 = 쓴 만큼** 을 맞춘다. 상한에 걸리지 않으면 각자 제 몫 그대로다.

| 무엇을 남기나 | 어디에 |
| --- | --- |
| 돈의 이동 | 장부 거래 하나(`SETTLEMENT`, 키 `execution-settlement:{실행ID}`). 예치 한 줄 −, 주인마다 한 줄 + |
| 단계마다 누구에게 얼마 | `execution_settlement` (V24) — 실행 · 단계 · 노드 이름 · 주인 · 에이전트 · 금액 · 적은 시각 |

노드 이름은 실행할 때 보낸 이름을 적는다. 노드를 고치거나 지워도 무엇으로 벌었는지 남는다.
정산 내역 · 수익 통계(PAY-013/014, 302)가 이 표를 읽는다. 자기 실행은 `execution.requester_id = supplier_id` 로 가른다.

| 지키는 것 | 어떻게 |
| --- | --- |
| 떼어 둔 것 = 돌려준 것 + 정산한 것 | 한 계산(`ExecutionUsage`)에서 쓴 만큼과 나눈 몫을 함께 낸다 |
| 한 번만 적립한다 | 실행 행을 잠그고 닫혔는지 먼저 본다(8.4). 장부 키 UNIQUE 와 `execution_settlement` 의 UNIQUE `(execution_id, step_id)` 가 한 번 더 막는다 |
| 일부만 옮겨지지 않는다 | 주인이 여럿이어도 장부 거래 하나다. 닫기 · 환불 · 정산이 한 트랜잭션이다 |
| 엔진이 보낸 긴 값에 닫기가 막히지 않는다 | 단계 번호(16) · 노드 이름(40)은 칸보다 길면 잘라 넣는다 — 실패 판정(8.5)과 같다. 넘친 채 저장하다 실패하면 닫기 · 환불 · 정산이 통째로 되돌려지고 모니터가 올 때마다 같은 자리에서 다시 실패한다 (MR !100 리뷰) |
| 판매자 몫이 소리 없이 사라지지 않는다 | 단계 번호가 비었거나 주인을 못 읽어 건너뛴 성공 단계는 `WARN` 로그에 실행(`run`) · 단계 · 받은 `owner_id` 를 남긴다 (MR !100 리뷰) |

**남은 한계**

| 상황 | 지금 | 필요한 것 |
| --- | --- | --- |
| 엔진이 `owner_id` 를 잃고 돌려준다 | 그 단계는 받지도 주지도 않고 `WARN` 로그를 남긴다 (8.4) | 접수 때 단계마다 주인을 적어 두고 그것을 믿는다 (`execution_charge_rate` 처럼) |
| 플랫폼 탓 실패의 앞선 성공 단계 | 공급자가 그 몫을 받지 못한다 | 플랫폼 계정을 두기로 하면 계약대로 플랫폼이 낸다 |
| 이 표보다 먼저 닫힌 실행 | 쓴 만큼이 예치에 남아 있다 | 필요하면 한 번 정리한다. 배포 전이라 dev 데이터뿐이다 |
