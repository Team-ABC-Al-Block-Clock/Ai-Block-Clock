# 끝난 설계 — 에이전트 파이프라인

[`../agent-pipeline.md`](../agent-pipeline.md) 에서 **구현이 끝나** 걷어낸 장이다. 지금 코드가
왜 그 모양인지 되짚을 때만 본다. **현재 규칙의 원본이 아니다** — 규칙은 `docs/RULE.md`,
구조는 `docs/ARCHITECTURE.md` 가 원본이다.

### 4.1 프로필

| FE 가 보내는 것 | 우리 |
| --- | --- |
| `name` · `summary` · `description` · `usageExample` · `onboardingMessage` | `AgentProfile` 에 그대로 |
| — | `thumbnailUrl` 은 남겼다. 아이콘 업로드가 붙을 자리다 |

`category` · `tags` 는 **걷어냈다.** 마켓 목록에도 상세에도 나오지 않고, FE 가 보내지도 않는다.

> 카테고리·등급·공개 범위 필터는 명세에 없고, 화면에 표시할 자리가 없다 — `agents.ts`

### 6.1 지금 표현되지 않는 것

`GraphNode` 가 답하는 것은 셋뿐이다 — 어느 자리인가, 어떤 종류인가, 무엇을 가리키는가.
전부 **배치 정보**다. "이것이 실행되면 결과를 내는 한 덩어리다" 는 어디에도 없다.

그래서 아래 셋을 물을 데가 없다.

| 물음 | 지금 |
| --- | --- |
| 이 자리에 놓인 것의 **값이 얼마인가** | 값은 `AgentVersion` 에만 있다 |
| 실행하면 **프롬프트 몇 개로 펼쳐지는가** | 펼치기라는 개념이 없다 |
| **누구 것인가** | `AgentPlacement` 로 에이전트만 골라낸다. 노드는 못 본다 |

### 6.2 합성 구조다

한 자리에 놓이는 것은 둘 중 하나다.

- **잎** — 노드. 프롬프트 하나, LLM 한 번. 더 쪼개지지 않는다.
- **가지** — 에이전트 버전. 안에 그래프가 있고 거기 또 잎과 가지가 있다.

고리는 이미 코드에 있다.

```
그래프 ──담는다──> AgentNode ──(식별자, 조회 필요)──> AgentVersion ──담는다──> 그래프
```

`AgentNode` 가 식별자만 들어 **한 칸이 끊겨 있다.** 끊어 둔 것은 맞다. 객체를 직접 물면 워크플로우
하나 읽는데 에이전트가 통째로 딸려 온다. 애그리거트를 넘는 참조는 식별자여야 한다.

문제는 **그 끊긴 고리를 이어 걷는 타입이 없다**는 것이다. 구조는 있는데 그것을 다루는 물건이 없다.

### 6.3 없으면 같은 분기가 네 군데에서 반복된다

| 어디 | 무엇을 |
| --- | --- |
| 저장할 때 | 펼친 경로 길이가 상한을 넘는가 |
| 팔 때 | 놓인 것이 전부 내 것인가 |
| 선차감할 때 | 놓인 것들의 값 합이 얼마인가 |
| 주문서 만들 때 | 놓인 것을 프롬프트 목록으로 편다 |

네 군데 전부 `sourceType` 을 보고 갈라지게 된다. **한 곳만 고치고 다른 데를 빠뜨리는 것이 시간 문제다.**

### 8.3 선차감 — 엔진에 넘기기 전에 뗀다

**순서가 바뀌었다.** 전에는 엔진을 먼저 부르고 받은 실행 번호로 실행을 저장했다. 그 뒤에 잔액을 보면
이미 돌기 시작한 실행을 막게 되고, 엔진 호출을 트랜잭션 안에 넣으면 커넥션을 쥔 채 기다린다
(ARCHITECTURE 4.2). 그래서 이렇게 나눴다.

| | 트랜잭션 | 하는 일 |
| --- | --- | --- |
| 1 | 없음 | 같은 `requestId` 로 접수한 실행이 있으면 그것을 돌려주고 끝낸다. **다시 따라가지 않는다** |
| 2 | 없음 | 엔진에 보낼 요청(JSON · 파일 위치)을 **떼기 전에** 다 만든다. 여기서 실패하면 뗀 것이 없다 |
| 3 | **하나** | 실행을 적는다 → 쓸 수 있는 잔액 행을 잠그고 읽는다 → 모자라면 전부 되돌린다 → 견적만큼 `ABC_BALANCE` → `EXECUTION_ESCROW` |
| 4 | 없음 | 엔진에 넘긴다 |
| 5a | 하나 | 받았으면 실행 번호를 붙이고, 컨트롤러가 뒤에서 따라가기(!84)를 건다 |
| 5b | **하나** | 4 · 5a 에서 **무엇이 실패하든** 예치를 되돌리고 실행을 `FAILED` 로 남긴다 |

3 과 5b 는 `ExecutionReservationManager` 가 맡는다. 엔진 호출을 사이에 둔 두 쓰기 묶음이라 Service
트랜잭션 하나로 묶을 수 없어서다. 충전 확정(`ChargeConfirmationManager`)과 같은 모양이다.

`start` 는 `ExecutionStart` 로 새로 만든 실행인지를 함께 돌려준다. 같은 요청 번호로 돌려받은 앞 실행을
다시 따라가면 조회가 두 줄기가 되고, 따라가기를 시작하며 상태를 `QUEUED` 로 적어 끝난 실행이 되살아난다
(MR !88 리뷰). 따라가기는 api 계층(`api.batch`)이라 Service 가 부를 수 없어 컨트롤러가 가른다.

| 지키는 것 | 어떻게 |
| --- | --- |
| 잔액이 음수가 되지 않는다 | 잔액을 `SELECT ... FOR UPDATE` 로 읽는다. 일반 조회는 트랜잭션 첫 조회 시점 값을 볼 수 있어 동시 실행이 같은 돈을 두 번 쓴다. 잠금을 빼면 동시성 테스트가 깨지는 것까지 확인했다 |
| 한 실행에 한 번만 뗀다 | 장부 키 `execution-reserve:{실행ID}` (UNIQUE) |
| 같은 누름을 두 번 떼지 않는다 | `execution` 의 UNIQUE `(requester_id, request_id)`. 차례로 다시 오면 앞 실행을 돌려주고, 동시에 오면 늦은 쪽이 `EXECUTION_006`(409) |
| 되돌리기도 한 번만 | 장부 키 `execution-release:{실행ID}`. 실행 뒤 결과를 보고 하는 환불과 키가 달라 서로 막지 않는다 |
| 잔액이 모자라면 아무것도 남지 않는다 | 실행 기록과 차감이 한 트랜잭션이다. `PAYMENT_008`(402) 에 견적 API 와 같은 이름으로 금액을 싣는다 |

`mock` 실행도 똑같이 뗀다. 모델을 부르지 않아 실측 원가가 0 이라 끝나면 전부 돌아오고 정산할 것도 없다(8.4 · 8.6).

**남은 한계**

| 상황 | 지금 | 필요한 것 |
| --- | --- | --- |
| 엔진이 받았는데 응답만 10초를 넘긴다 | 클라이언트가 "꺼져 있음" 과 같은 `REQUEST_FAILED` 로 알려 구분할 수 없다. 실패로 보고 돌려주므로 엔진 쪽 실행이 공짜가 될 수 있다 | 시간 초과를 따로 알리고, 결과 불명은 재조회로 확인 |
| 엔진이 받은 뒤 실행 번호 저장이 실패한다 | 돌려주고 `FAILED` 로 남긴다. 엔진 쪽 실행은 공짜가 된다. 사용자 돈을 묶어 두는 것보다 낫다고 봤다 | 엔진에 실행 취소를 요청하는 길 |
| 돌려주기마저 실패한다 (DB 가 통째로 안 될 때) | 원래 실패에 덧붙이고 `ERROR` 로그에 실행 ID 를 남긴다. 예치는 묶인다 | 번호 없는 채 오래된 실행을 찾아 정리하는 작업 |

### 8.4 끝난 뒤 환불 — 쓰지 않은 만큼 돌려준다 (PAY-009 · PAY-010)

> **계약 v2.0 (2026-09-26) 에서 바뀌었다.** 쓴 만큼은 실측 × 배율이 아니라 성공한 단계마다 접수할 때 정한 단가의 합이다.
> 플랫폼 탓이어도 앞서 성공한 판매자는 플랫폼 부담으로 정산받는다. [`../agent-pipeline.md`](../agent-pipeline.md) 12장.

**떼어 둔 것 = 쓴 만큼 + 돌려줄 만큼.** 돌려줄 만큼은 `EXECUTION_ESCROW` → `ABC_BALANCE` 로 옮기고,
쓴 만큼은 같은 자리에서 단계 주인의 정산금으로 옮긴다(8.6). 닫힌 실행의 예치에는 아무것도 남지 않는다.

| 단계 | 쓴 만큼에 넣나 |
| --- | --- |
| 성공 (`nodes[].status = succeeded`) | 넣는다. **실측 원가 `cost_abc` × 접수 때 정한 배율** |
| 실패 | 넣지 않는다. 토큰을 썼어도 결과물을 받지 못했다 |
| 돌지 않음 (`skipped` · `pending`) | 넣지 않는다. 분기로 안 간 것과 앞이 실패해 못 간 것 모두 |
| 플랫폼 탓 실패 (`failure.fault = platform`) | **전부 돌려준다.** 성공한 단계도 넣지 않는다 (계약 8.5). 공급자에게도 주지 않는다 (8.6) |
| 주인을 가리킬 수 없는 성공 (`owner_id` 가 비었거나 숫자가 아님, 단계 번호가 빔) | 넣지 않는다. 받을 사람이 없는 값을 사용자에게 받지 않는다. 우리가 늘 채워 보내므로 엔진이 값을 잃을 때만 생기고, 생기면 `WARN` 로그로 남긴다 |

- **배율은 `1 + 등급 할증`이다.** 노드와 내 에이전트는 1, 남의 에이전트는 그 버전 등급의 배율이다. 견적에서
  판매가를 셀 때 쓴 값과 같다. 에이전트를 펼친 단계는 모두 그 에이전트 자리의 배율을 따른다.
- **배율은 접수할 때 단계마다 적어 둔다(`execution_charge_rate`).** 실행 중에 등급이 바뀌거나 워크플로우를 고쳐도
  접수한 순간의 값으로 센다. 떼어 둔 금액은 `execution.reserved_abc` 에 적는다.
- **떼어 둔 것보다 더 받지 않는다.** 실측이 견적을 넘어도 접수할 때 알린 금액이 상한이다.
- **`mock` 은 전부 돌아온다.** 모델을 부르지 않아 `cost_abc` 가 0 이다. 접수 때는 똑같이 떼므로 잔액 검사는 그대로 거친다.

**실행을 닫는 자리는 `ExecutionReservationManager.finish` 하나다.** 끝을 알아차리는 길이 둘이라, 둘 다 여기로 온다.
상태만 옮기는 `moveTo` 로 끝난 실행을 닫으면 환불이 빠진다(MR !94 리뷰).

| 누가 | 언제 | 엔진이 알린 상태(`run`) |
| --- | --- | --- |
| 모니터(`ExecutionMonitor`) | 뒤에서 2초마다 묻다가 끝을 볼 때 | 마지막 응답 |
| 모니터 | 기한(단계 수 × 40초 + 60초) 동안 변화가 없어 실패로 끊을 때 | **없음 → 플랫폼 탓으로 보고 전부 돌려준다** |
| 조회(`GET /runs/{id}`) | 모니터가 놓친 실행(재기동 · 닫기 실패)을 엔진에 물어 끝을 볼 때 | 그 응답 |

`finish` 는 한 트랜잭션에서 실행 행을 잠그고 → 이미 닫혔으면 그만 → 닫고 → 쓰지 않은 만큼 돌려주고 → 쓴 만큼을 정산한다(8.6).

| 지키는 것 | 어떻게 |
| --- | --- |
| 닫혔는데 돌려주지 않은 실행이 없다 | 상태를 옮기는 것과 환불이 한 트랜잭션이다. 모니터에서 실패하면 기록이 안 끝난 채 남아 조회가 다시 닫는다 |
| 모니터와 조회가 겹쳐도 한 번만 돌려준다 | 실행 행을 `SELECT ... FOR UPDATE` 로 잠그고 닫혔는지 먼저 본다. 뒤에 장부 키 `execution-refund:{실행ID}` (UNIQUE) 가 한 번 더 막는다 |
| 되돌리기와 부딪히지 않는다 | 엔진이 받지 않은 실행은 `execution-release:` 로 돌려주고 끝난 상태라 여기에 오지 않는다 |
| 선차감 전의 실행 | 뗀 것이 없어(`reserved_abc` 비어 있음) 닫기만 한다. V22 가 장부에서 이미 뗀 금액을 옮겨 적는다 |

**남은 한계**

| 상황 | 지금 | 필요한 것 |
| --- | --- | --- |
| 우리 서버가 재기동하고 사용자도 조회하지 않는다 | 모니터가 따라가던 목록은 메모리라 사라지고, 조회가 없으면 끝을 알아차릴 길이 없어 예치가 묶인다 | 기동할 때 안 끝난 실행을 다시 따라가기 |
| 서버 재기동 뒤 엔진도 실행을 잊었다 (404) | 조회가 `EXECUTION_002` 로 실패하고 예치가 묶인다 | 기한을 넘긴 안 끝난 실행을 실패로 닫고 돌려주기 |
| 책임별 차등 정산 | ~~`platform` 만 전액 환불로 가르고 `supplier` · `consumer` 는 같게 본다~~ → 환불은 계약대로 같다. 책임은 8.5 에서 남긴다 | PAY-011 (들어감) |

### 8.5 실패 책임 — 누구 탓인지 남긴다 (PAY-011)

**판정은 엔진이 한다.** `failure.fault` 가 `supplier` · `consumer` · `platform` 로 오고(계약 8.5 · 9.2),
우리는 받은 것을 한 가지 규칙(`ExecutionFailure`)으로 정리해 **실행을 닫는 트랜잭션(`finish`) 안에서** `execution_failure` 에 남긴다(V23).
오류 코드를 보고 우리가 다시 판정하지 않는다 — 계약 9.2 의 표를 베끼게 되고 엔진과 어긋날 수 있다.

| 상황 | 남기는 책임 | 오류 코드 |
| --- | --- | --- |
| 엔진이 `fault` 를 알림 | 그대로 | 엔진의 `error_code` |
| `fault` 가 비었거나 모르는 값 | `PLATFORM` | 엔진의 `error_code` |
| 실패했는데 `failure` 가 없음 | `PLATFORM` | `ABC_RUNTIME_UNREPORTED` |
| 기한 안에 끝을 알리지 않아 우리가 끊음 | `PLATFORM` | `ABC_RUNTIME_STALLED` |
| 엔진에 넘기지 못함 (선차감 되돌리기) | `PLATFORM` | `ABC_RUNTIME_UNREACHABLE` |

**근거가 없으면 플랫폼 탓이다.** 공급자나 수요자에게 넘길 근거가 없는 실패는 우리가 진다(PAY-011 "판정 불가는 시스템 책임").
환불(8.4)도 같은 판정을 본다 — 책임을 모르는 실패는 성공한 단계까지 돌려준다.

**실행 행이 아니라 따로 둔 표에 적는다(MR !98 리뷰).** `execution` 은 모든 실행의 생애 주기와 선차감을 맡고 목록 조회와
`findForUpdate` 잠금이 쓰는 행이다. 판정은 실패한 실행에만 있고, 한 번 적고 고치지 않고, 읽는 쪽도 성공률 · 정산이라
성격이 다르다. 단계별 배율을 `execution_charge_rate` 로 뗀 것과 같은 결이다.

| 칸 (`execution_failure`) | 뜻 | 언제 채우나 |
| --- | --- | --- |
| `execution_id` (PK) | 어느 실행인가 | 실패한 실행마다 한 줄. **PK 라 같은 실행을 두 번 적으면 DB 가 막는다** |
| `failed_step_id` · `failure_code` | 어느 단계에서 무슨 오류로 | 엔진이 알린 만큼. 칸(16 · 64)보다 길면 잘라 넣는다 |
| `fault` | 누구 탓인가 | 늘 |
| `affects_success_rate` | 공급자 성공률에 넣나 | 공급자 탓이고 엔진이 `true` 로 알릴 때만 참. 값이 없으면 넣지 않는다 |
| `supplier_id` · `agent_id` | 어느 공급자 · 에이전트 탓인가 | 공급자 탓일 때만 |

- **실행 ID 를 우리가 정해 넣으므로 늘 새 줄로 넣는다(`Persistable`).** 그러지 않으면 JPA 가 이미 있는 줄을 찾아 덮어써
  PK 가 두 번 적기를 막지 못한다.
- **엔진이 보낸 값은 잘라 넣는다.** 계약에 길이가 없다. 넘친 채 저장하다 실패하면 같은 트랜잭션의 실행 닫기와 환불까지
  되돌려지고, 모니터가 올 때마다 같은 자리에서 실패해 실행이 영영 닫히지 않는다(MR !98 리뷰).
- **엔진에 넘기지 못한 실행(`release`)도 같은 `finish` 로 닫는다.** 이미 닫혔으면 판정을 다시 적지 않는다.
- 성공률 · 정산용 인덱스(`agent_id` · `supplier_id`)는 이 표를 조회하는 쪽이 생길 때 그 조회에 맞춰 건다.

- **공급자 탓이어도 성공률에 넣지 않는 오류가 있다.** `REF_FILE_REJECTED` · `PROMPT_TEMPLATE_INVALID` 는 `supplier` 지만
  `affects_success_rate: false` 로 온다(계약 9.2).
- **누구 탓인지는 우리가 보낸 값으로 찾는다.** 단계마다 `owner_id`(!91)와 `agent_id`(298 에서 더함 — 캔버스에 놓인
  에이전트 자리의 에이전트)를 실어 보내면 엔진이 `nodes[]` 에 그대로 돌려준다. 실패한 단계의 것을 읽는다.
  에이전트 안의 에이전트는 바깥 자리의 에이전트로 묶는다 — 팔린 물건이 바깥 에이전트다.
- **이미 닫힌 실행은 판정을 바꾸지 않는다.** 모니터와 조회가 겹쳐도 처음 닫은 쪽의 판정이 남는다.

**사용자 환불은 책임에 따라 갈리지 않는다.** 계약 8.5 에서 `supplier` · `consumer` 둘 다 "실패 단계 이후 환원, 앞서 성공한
단계 정산 유지" 다. 책임이 가르는 것은 **공급자 쪽**이다.

| 읽는 곳 | 무엇을 |
| --- | --- |
| 성공률 (PAY-018, 303) | `affects_success_rate` 가 참인 실패만 그 에이전트의 실패로 센다. 자기 실행 · mock 은 따로 뺀다 |
| 정산 (PAY-012, 301) | `PLATFORM` 이면 정산하지 않는다. 계약은 플랫폼이 차액을 내 공급자 정산을 유지하라고 하지만 플랫폼 계정을 두지 않았다 (8.6) |

**남은 한계**

| 상황 | 지금 | 필요한 것 |
| --- | --- | --- |
| 플랫폼이 끼운 입출력 노드가 실패 | 입출력 노드가 있으면 실행을 막아(`EXECUTION_005`) 아직 생기지 않는다 | 풀리면 `fault: supplier` 로 와도 남의 탓이 아니게 가려야 한다 (AI 질문 3-2) |
| 엔진이 `owner_id` · `agent_id` 를 돌려주지 않음 | 책임은 남기고 공급자 · 에이전트는 비워 둔다 | 필요하면 접수 때 단계마다 주인 · 에이전트를 적어 둔다 (`execution_charge_rate` 처럼) |
| 이 표보다 먼저 끝난 실행 | 줄이 없다 | 성공률 집계에서 책임 모름으로 빼거나 플랫폼으로 본다 (303) |

### 8.6 정산 — 쓴 만큼을 단계 주인에게 준다 (PAY-012)

> **계약 v2.0 (2026-09-26) 에서 바뀌었다.** 플랫폼 탓이면 사용자에게 전부 돌려주고, 앞서 성공한 단계의 주인은 `PLATFORM_EXPENSE` 에서 제 단가를 받는다.
> [`../agent-pipeline.md`](../agent-pipeline.md) 12.3.

**수수료가 없다.** 사용자가 쓴 만큼(8.4)이 전부 그 단계를 만든 주인의 정산금(`PAYOUT_BALANCE`)으로 간다.
플랫폼 수익 계정은 두지 않는다 (2026-09-25 담당 결정. AI `grading-formula.md` 4장 "MVP 는 수수료 0%" 와 같다).
실행을 닫는 트랜잭션(`finish`) 안에서 환불과 함께 적는다.

```
접수 (8.3)   ABC_BALANCE(사용자)      ──떼어 둔 것──▶  EXECUTION_ESCROW(사용자)
닫기 (8.4)   EXECUTION_ESCROW(사용자) ──돌려줄 만큼──▶ ABC_BALANCE(사용자)
닫기 (8.6)   EXECUTION_ESCROW(사용자) ──쓴 만큼────▶   PAYOUT_BALANCE(단계 주인마다)
```

| 단계 | 누구에게 얼마를 |
| --- | --- |
| 성공 | 그 단계의 주인(`nodes[].owner_id`)에게 실측 원가 × 접수 때 배율. 남의 에이전트면 할증까지 판매자 몫이다 |
| 실패 · 돌지 않음 | 없다. 사용자에게 받지 않았다 (8.4) |
| 공급자 · 수요자 탓 실패의 앞선 성공 단계 | 준다. 사용자가 그만큼 냈다 (계약 8.5 와 같다) |
| 플랫폼 탓 실패 | **주지 않는다.** 계약 8.5 는 "정산 유지, 차액은 플랫폼 부담" 이지만 차액을 낼 플랫폼 계정이 없다. AI 팀에 알릴 것 |
| 내 에이전트 · 내 노드를 내가 씀 | **내 정산금으로 간다.** 원가만 낸 것이(293) 내 예치에서 내 정산금으로 옮겨 간다. 등급 집계(303)에서는 뺀다 |

**주인은 엔진이 돌려준 `owner_id` 로 찾는다.** 우리가 단계마다 실어 보낸 값(!91)이 그대로 돌아온다.
에이전트 안의 단계는 버전을 굳힐 때 박은 주인(V18 — 에이전트 주인)이다. 실패 책임(8.5)과 같은 규칙(`StepOwner`)으로 읽는다.

**실측이 떼어 둔 것을 넘으면 모두 같은 비율로 줄인다.** 사용자는 떼어 둔 만큼만 낸다(8.4). 이때 각자 실측 몫에
비례해 나눈다 — 실행 순서로 나누면 뒤에 놓인 판매자만 덜 받는다. 여섯째 자리 아래는 버리고, 버려서 남은 끝자리는
가장 큰 몫에 붙여 **정산금의 합 = 쓴 만큼** 을 맞춘다. 상한에 걸리지 않으면 각자 제 몫 그대로다.

| 무엇을 남기나 | 어디에 |
| --- | --- |
| 돈의 이동 | 장부 거래 하나(`SETTLEMENT`, 키 `execution-settlement:{실행ID}`). 예치 한 줄 −, 주인마다 한 줄 + |
| 단계마다 누구에게 얼마 | `execution_settlement` (V24) — 실행 · 단계 · 노드 이름 · 주인 · 에이전트 · 금액 · 적은 시각 |

노드 이름은 실행할 때 보낸 이름을 적는다. 노드를 고치거나 지워도 무엇으로 벌었는지 남는다.
정산 내역 · 수익 통계(PAY-013/014, 302)가 이 표를 읽는다. 자기 실행은 `execution.requester_id = supplier_id` 로 가른다.

| 지키는 것 | 어떻게 |
| --- | --- |
| 떼어 둔 것 = 돌려준 것 + 정산한 것 | 한 계산(`ExecutionUsage`)에서 쓴 만큼과 나눈 몫을 함께 낸다 |
| 한 번만 적립한다 | 실행 행을 잠그고 닫혔는지 먼저 본다(8.4). 장부 키 UNIQUE 와 `execution_settlement` 의 UNIQUE `(execution_id, step_id)` 가 한 번 더 막는다 |
| 일부만 옮겨지지 않는다 | 주인이 여럿이어도 장부 거래 하나다. 닫기 · 환불 · 정산이 한 트랜잭션이다 |
| 엔진이 보낸 긴 값에 닫기가 막히지 않는다 | 단계 번호(16) · 노드 이름(40)은 칸보다 길면 잘라 넣는다 — 실패 판정(8.5)과 같다. 넘친 채 저장하다 실패하면 닫기 · 환불 · 정산이 통째로 되돌려지고 모니터가 올 때마다 같은 자리에서 다시 실패한다 (MR !100 리뷰) |
| 판매자 몫이 소리 없이 사라지지 않는다 | 단계 번호가 비었거나 주인을 못 읽어 건너뛴 성공 단계는 `WARN` 로그에 실행(`run`) · 단계 · 받은 `owner_id` 를 남긴다 (MR !100 리뷰) |

**남은 한계**

| 상황 | 지금 | 필요한 것 |
| --- | --- | --- |
| 엔진이 `owner_id` 를 잃고 돌려준다 | 그 단계는 받지도 주지도 않고 `WARN` 로그를 남긴다 (8.4) | 접수 때 단계마다 주인을 적어 두고 그것을 믿는다 (`execution_charge_rate` 처럼) |
| 플랫폼 탓 실패의 앞선 성공 단계 | 공급자가 그 몫을 받지 못한다 | 플랫폼 계정을 두기로 하면 계약대로 플랫폼이 낸다 |
| 이 표보다 먼저 닫힌 실행 | 쓴 만큼이 예치에 남아 있다 | 필요하면 한 번 정리한다. 배포 전이라 dev 데이터뿐이다 |

### 8.7 정산 내역 · 수익 통계 — 받은 것을 공급자가 본다 (PAY-013/014)

8.6 이 남긴 두 곳을 **읽기만** 한다. 돈은 옮기지 않는다.

| API | 읽는 곳 | 주는 것 |
| --- | --- | --- |
| `GET /api/v1/credits/balance` 의 `payoutAmount` | 장부 `PAYOUT_BALANCE` | 출금할 수 있는 정산금. 쓸 수 있는 잔액 · 예치와 한 응답으로 낸다 |
| `GET /api/v1/settlements` | `execution_settlement` + `execution.requester_id` | 단계마다 실행 · 단계 · 노드 이름 · 에이전트 · 금액 · 자기 실행 여부 · 시각. 최신순, 기간 · 에이전트 조건, 커서 |
| `GET /api/v1/settlements/statistics` | 위와 같은 줄 | 합계 · 그중 자기 실행 · 실행 수, 기간별(`DAY` · `MONTH`), 에이전트별 수익과 호출 수 |

**받는 사람은 늘 로그인 사용자다.** 쿼리 조건에서 `supplier_id` 를 빼지 않고, 다른 공급자를 고르는 파라미터를
두지 않는다. 남의 에이전트 ID 를 넣어도 받는 사람 조건이 먼저라 빈 결과다.

**통계와 내역은 같은 쿼리를 읽는다.** 조건이 같으면 통계 합계 = 내역 합이다. 날짜 묶기를 DB 함수로 하면
H2 와 MySQL 이 갈려서, 조건 안의 줄을 모두 읽어 `SettlementStatistics` 가 묶는다. 날짜 경계는 장부 내역과 같은
UTC 다 (`DatePeriod`).

| 정한 것 | 이유 |
| --- | --- |
| 호출 수 = **실행 수** | 에이전트 하나가 한 실행에서 단계 여럿을 돌면 줄이 여럿 생긴다. 줄을 세면 부푼다 |
| 자기 실행도 수익에 넣고 `selfUse` 로 표시 | 정산금에 실제로 들어온다. 빼면 잔액과 합이 안 맞는다. 등급 집계(303)에서만 뺀다 |
| "기여도" 칸을 따로 두지 않음 | 수수료가 없어 단계가 받은 금액이 곧 그 단계의 몫이다 |
| 에이전트 이름을 싣지 않음 | 정산을 받는 에이전트는 모두 받는 사람 자신의 것이라 FE 가 내 에이전트 목록으로 이름을 붙인다 |
| 바로 놓인 노드로 받은 것 | 에이전트별 통계에서 `agentId: null` 한 줄로 모은다 |
| 인덱스는 V25 로 | V24 와 다른 MR 이다. V24 가 먼저 배포되면 V24 를 고친 순간 체크섬이 깨진다 |

**남은 한계**

| 상황 | 지금 | 필요한 것 |
| --- | --- | --- |
| 기간을 넓게 잡은 통계 | 조건 안의 줄을 모두 읽는다 | 줄이 많아지면 일 단위 집계 테이블이나 DB 집계로 바꾼다 |
| 내역 커서 | 오프셋 커서다 (RULE 12). 넘기는 사이 새 정산이 끼면 한 줄 밀린다 | 정렬 키(`created_at`, `id`) 기반 커서 |

### 8.8 ABC 는 넘길 수 없다 — 장부가 거래의 모양을 본다 (PAY-004)

ABC 는 사용자끼리 주고받을 수 없는 이용권이다. 넘기는 API 가 없는 것만으로는 부족하다 — 장부는 증감의 합이 0 인지만
봤으므로 `A 의 ABC_BALANCE −10, B 의 ABC_BALANCE +10` 같은 거래를 코드가 만들면 그대로 들어갔다.
그래서 `LedgerTransaction` 생성자가 거래 종류마다 **빠지는 칸 하나와 들어가는 칸**을 정해 두고 그 모양만 받는다.

| 거래 | 빠지는 칸 (−) | 들어가는 칸 (+) | 사람 |
| --- | --- | --- | --- |
| `CHARGE` | `ABC_ISSUANCE` (`SYSTEM`) | `ABC_BALANCE` 한 줄 | 받는 사람 하나 |
| `RESERVE` | `ABC_BALANCE` | `EXECUTION_ESCROW` 한 줄 | **같은 사람** |
| `REFUND` (되돌리기 · 환불) | `EXECUTION_ESCROW` | `ABC_BALANCE` 한 줄 | **같은 사람** |
| `SETTLEMENT` | `EXECUTION_ESCROW` (실행한 사람) | `PAYOUT_BALANCE` 한 줄 이상 | 달라도 된다 — 쓴 값을 치르는 것이다 |

남에게 ABC 가 가는 길은 정산으로 공급자의 **정산금**에 넣는 것 하나뿐이다. 받은 쪽의 쓸 수 있는 잔액으로는 가지 않는다.
모양이 다르면 `LEDGER_INVALID_TRANSACTION`(500) 이다. 사용자가 고칠 요청이 아니라 코드가 잘못 만든 거래이기 때문이다.

| 지키는 것 | 어떻게 |
| --- | --- |
| 팩터리를 거치지 않은 거래도 막는다 | 검사가 생성자에 있어 어떤 길로 만들어도 지나간다 |
| 거래 종류가 늘면 규칙도 정한다 | `switch` 가 모든 `LedgerEventType` 을 받아야 컴파일된다 |
| 요청으로 남의 계정을 가리킬 수 없다 | ABC 를 넣는 API 는 충전 신청(`POST /credits/charges`) 하나이고 받는 사람은 로그인한 사람이다. 나머지(`/credits/balance` · `/credits/transactions` · `/settlements`)는 조회이고 로그인한 사람 것만 읽는다. 장부의 주인은 늘 서버가 세션 · 실행 행에서 정한다 |
| 남의 입금으로 충전할 수 없다 | 보낸 지갑이 신청한 사람의 지갑이어야 한다(`SENDER_WALLET_MISMATCH`, PAY-001/002) |

체인 위 abcToken 은 여기서 막지 않는다. 충전 전의 토큰은 일반 ERC-20 이라 지갑끼리 옮길 수 있고, 서비스가 다루는
ABC 는 충전된 뒤 장부에 적힌 것이다(242 결정).

### 8.9 등급 재료와 지표 — 닫힌 실행을 에이전트마다 센다 (PAY-016 ~ 018)

**재료만 저장하고 지표는 매번 계산한다.** 에이전트마다 한 줄(`agent_grade_metric`, V26)에 성공 수 · 공급자 탓 실패 수 ·
평가 수 · 평균 평점 · 기준 시점만 둔다. 보정 평점 · 정규화 사용량 · 성공률은 이 재료를 수식(`AgentGradeProperties`)에
넣어 그때그때 낸다. 계산 결과를 칸으로 두면 조정값을 바꿨을 때 낡은 값이 남고, 손으로 넣는 시드와 계산 칸이 어긋날 수 있다.
등급을 매긴 결과와 그 이력은 종합 점수 · 등급(PAY-019/020, 8.10)과 재산정 배치(PAY-022)가 남긴다.

| 재료 | 어디서 오나 |
| --- | --- |
| 성공 수 · 공급자 탓 실패 수 | 실행을 닫을 때(`finish`) 더한다. 닫기 · 판정 · 환불 · 정산과 한 트랜잭션이라 한 번만 센다 |
| 평가 수 · 평균 평점 | **리뷰 기능이 없다.** FE 는 리뷰를 보여 주기만 하고(mock) 쓰는 화면도 API 도 없다. 시연 시드로만 들어온다 |
| 줄이 없는 에이전트 | 한 번도 세지 않은 신규다. 모두 0 으로 읽는다 (`AgentGradeMetricReader`) |

**한 실행은 에이전트마다 한 번이다.** 에이전트 안의 단계가 여럿이어도 한 덩어리로 판다 (302 의 "호출 수 = 실행 수" 와 같다).

| 닫힌 실행에서 그 에이전트는 | 센다 |
| --- | --- |
| 모든 단계가 성공했다 (분기로 건너뛴 단계는 괜찮다) | 성공 +1 |
| 공급자 탓으로 실패했고 엔진이 `affects_success_rate: true` 로 알렸다 | 실패 +1 |
| 공급자 탓이지만 성공률에 넣지 말라는 오류 (`REF_FILE_REJECTED` 등) | 세지 않는다 |
| 수요자 탓으로 실패했거나, 앞에서 멈춰 돌지 못했다 | 세지 않는다 |
| 플랫폼 탓 실패 · 기한 안에 끝을 알리지 않음 | 세지 않는다. 우리가 막은 것이다 (계약 8.5 "영향 없음") |
| 자기 에이전트를 자기가 썼다 | 세지 않는다. 원가만 내고 사용량과 성공률을 올릴 수 있다 (8.6 · 8.7 의 `selfUse`) |
| 모델을 부르지 않았다 (mock — 실측 원가가 모두 0) | 성공으로 세지 않는다 |

규칙은 `AgentRunOutcomes` 한 곳에 있다. 실패가 그 에이전트를 깎는지는 `ExecutionFailure.countsAgainst` 가 답한다.

**지표 수식은 AI `grading-formula.md` v1.0 이다.** 조정값은 설정(`agent-grade.*`)에 두고 범위를 벗어나면 기동을 막는다.

| 지표 | 수식 | 범위 |
| --- | --- | --- |
| 보정 평점 | `(v × R + m × C) / (v + m)`, 평가가 없으면 `C` | 1 ~ 5 |
| 평점 점수 | `(보정 평점 − 1) / 4 × 100` | 0 ~ 100 |
| 사용량 점수 | `log10(성공 수 + 1) / log10(U_max) × 100`, 넘으면 100 | 0 ~ 100 |
| 성공률 | `성공 / (성공 + 공급자 탓 실패)`, 센 실행이 없으면 1 | 0 ~ 1 |
| 성공률 페널티 | `성공률 ^ k` | 0 ~ 1 |

| 조정값 | 설정 | 초기값 |
| --- | --- | --- |
| `m` 보정 강도 | `agent-grade.rating-prior-count` | 10 |
| `C` 전체 평균 평점 | `agent-grade.rating-prior-mean` | 3.5 |
| `U_max` 사용량 상한 | `agent-grade.usage-cap` | 1000 |
| `k` 성공률 지수 | `agent-grade.success-rate-exponent` | 2 |

로그 · 거듭제곱은 `StrictMath` 로 계산한다. `Math` 는 JVM 마다 끝자리가 다를 수 있다 — "같은 입력이면 같은 지표" 를 지키려는 것이다.

| 지키는 것 | 어떻게 |
| --- | --- |
| 동시에 닫혀도 하나를 잃지 않는다 | 읽고 고쳐 쓰지 않고 `INSERT … ON DUPLICATE KEY UPDATE` 한 문장으로 더한다. 처음 세는 에이전트가 동시에 와도 한 줄만 생긴다 |
| 서로 기다리며 멈추지 않는다 | 한 실행이 여러 에이전트를 셀 때 늘 ID 순서로 센다 |
| 한 번만 센다 | 실행을 닫는 트랜잭션 안에서만 센다(`MANDATORY`). 이미 닫힌 실행은 세지 않는다 |
| 손으로 넣은 값이 범위를 벗어나지 않는다 | CHECK — 수는 0 이상, 평가가 있으면 평점이 1 ~ 5, 없으면 평점이 비어 있다 |

**시연 시드는 손으로 한 번 넣는다.** 에이전트 ID 는 시연 판매자가 등록할 때 생겨서 마이그레이션에 박을 수 없다.
`storage` 의 `db/seed/agent-grade-demo.sql` 은 Flyway 가 읽지 않는 자리다. `<AGENT_ID>` 를 AI `seed_values.json` 의
`ag_brand_01` 자리에 등록된 에이전트 ID 로 바꿔 넣으면 성공 120 · 실패 5 · 평가 25 · 평점 4.6 이 된다.
이 값의 지표는 평점 점수 82.14 · 사용량 점수 69.43 · 성공률 0.96 이고, AI 문서의 가중치에 넣으면 종합 점수 71.0(Tier 2)이다.
그 뒤 실제 실행은 시드 위에 더해진다. 나머지 시연 에이전트는 넣지 않아 신규(Tier 4)로 남는다.

**남은 한계**

| 상황 | 지금 | 필요한 것 |
| --- | --- | --- |
| 리뷰 | 평가 수 · 평점을 시드로만 넣는다 | 리뷰 작성 기능(MKT-007)이 생기면 리뷰를 쓸 때 평가 수 · 평균을 함께 고친다 |
| mock 실패 | mock 여부를 실행에 적지 않아, mock 실행이 공급자 탓으로 실패하면 실패로 센다 | mock 이 공급자 오류를 낼 일은 드물다. 필요하면 접수 때 mock 여부를 적는다 |
| 이 표보다 먼저 닫힌 실행 | 세지 않았다 | 필요하면 `execution_failure` · `execution_settlement` 로 한 번 채운다. 배포 전이라 dev 데이터뿐이다 |
| 추천 색인의 `success_rate` | ~~기본값 1.0 을 보낸다~~ → 재료에서 계산한 성공률을 보낸다 (8.11) | — |

### 8.10 종합 점수와 등급 — 지표로 Tier 를 매기고 남긴다 (PAY-019/020)

**매기고 남기기까지다. 가격 반영은 8.11 이다.** 재료(8.9)를 읽어 점수 · 등급을 매기고
`agent_grade_history`(V27)에 한 줄 남긴다. 가격에 쓰는 등급은 `agent_version.tier` 이고, 이 칸을 바꾸면 그 에이전트의
판매가가 바로 바뀐다. 이미 시작한 실행은 옛 가격을 지키는 것 · 주기 · 대상 고르기와 함께 재산정 배치(PAY-022, 320)가 한다.
매기는 자리는 8.11 의 `AgentGradeService.regrade(에이전트)` 하나다 (처음 이름은 `grade` 였다).

**수식은 AI `grading-formula.md` v1.0 2 · 3장이다.**

```
Score = (W1 × 평점 점수 + W2 × 사용량 점수) × 성공률 페널티
```

성공률은 가중합 항이 아니라 곱셈 항이다. 성공률이 0.5 면 점수가 4 분의 1 이 된다.
점수는 소수 넷째 자리에서 반올림한 값으로 등급을 매긴다 — 이력에 남은 점수로 다시 매겨도 같은 등급이 나오게 하려는 것이다.

| 등급 | 점수 구간 (이상) | 허들: 성공률 | 허들: 평가 수 | 할증 (`Tier`) |
| --- | --- | --- | --- | --- |
| Tier 1 | 80 | 0.98 | 50 | +50% |
| Tier 2 | 65 | 0.95 | 20 | +30% |
| Tier 3 | 45 | 0.90 | — | +10% |
| Tier 4 | 그 외 · 신규 | — | — | +0% |

**매기는 순서** (`AgentTierLadder`)

1. 점수로 닿은 가장 높은 등급을 후보로 잡는다 (`scoreTier`).
2. 후보의 허들을 넘으면 그 등급이다. 못 넘으면 한 칸씩 내려가며 허들을 넘는 첫 등급이다 (`tier`).
   예: 82 점인데 평가 30 회 → Tier 1 허들(50 회)에 걸리고 Tier 2 허들(20 회)은 넘어 Tier 2.
3. 허들은 깎기만 한다. 점수가 닿지 못한 등급으로 올리지 않는다. Tier 4 는 조건이 없어 늘 여기서 멈춘다.

아래 등급의 점수 구간이 늘 더 낮으므로 내려간 등급의 점수는 다시 보지 않는다. 이 순서가 뒤집히지 않게 기동할 때 막는다.

| 조정값 | 설정 | 초기값 | 기동을 막는 경우 |
| --- | --- | --- | --- |
| `W1` 평점 가중치 | `agent-grade.rating-weight` | 0.6 | 0 ~ 1 밖, 또는 W2 와 더해 1 이 아니다 |
| `W2` 사용량 가중치 | `agent-grade.usage-weight` | 0.4 | 〃 |
| 등급마다 점수 구간 · 허들 | `agent-grade.tiers.tier-{1,2,3}.min-score` · `min-success-rate` · `min-review-count` | 위 표 | 점수 0 ~ 100 · 성공률 0 ~ 1 밖, 평가 수 음수, 높은 등급의 구간이 낮은 등급보다 낮거나 같다 |

가중치는 `BigDecimal` 로 받는다. `double` 로는 0.7 + 0.3 이 1 이 되지 않을 수 있어 "더해 1" 검사가 흔들린다.
구간 경계(80 · 65 · 45)는 AI 문서가 🔶 로 둔 값이라 분포를 보고 팀이 바꿀 수 있다.

**이력 한 줄에 남기는 것** — 한 번 적고 고치지 않는다. 매길 때마다 쌓는다.

| 칸 | 뜻 |
| --- | --- |
| `successful_runs` · `supplier_failures` · `review_count` · `average_rating` · `measured_at` | 매긴 순간의 재료. 재료 표(8.9)는 계속 바뀌어서 옮겨 두지 않으면 그때 왜 그 등급이었는지 다시 볼 수 없다 |
| `rating_score` · `usage_score` · `success_rate` | 매긴 순간의 수식으로 낸 지표. 조정값이 바뀌어도 그때의 값이 남는다 |
| `score` | 종합 점수. 0 ~ 100, 소수 넷째 자리 |
| `score_tier` · `tier` | 점수로 닿은 등급 · 허들까지 본 확정 등급. 다르면 허들에 걸린 것이다 |
| `created_at` | 매긴 때 |

8.9 는 "지표를 저장하지 않는다" 였다. 재료 표는 **지금** 을 나타내서 낡은 계산 칸이 남으면 안 되고,
이력은 **그때** 를 나타내서 그때의 계산을 그대로 두는 것이 목적이다.

**시연 시드의 결과** — 평점 점수 82.142857 · 사용량 점수 69.426179 · 성공률 0.96 → 점수 71.0150, Tier 2 (AI 문서 5장 검산과 같다).
신규 에이전트는 평점 점수 62.5(전체 평균 3.5) · 사용량 0 · 성공률 1 → 37.5, Tier 4.

**남은 한계**

| 상황 | 지금 | 필요한 것 |
| --- | --- | --- |
| 가격 반영 | ~~`agent_version.tier` 를 바꾸지 않는다~~ → 재산정이 모든 버전을 바꾼다 (8.11) | — |
| 부르는 곳 | ~~테스트뿐이다~~ → 매일 새벽 배치 (8.11) | — |
| 같은 재료로 다시 매김 | ~~부를 때마다 한 줄씩 쌓인다~~ → 마지막 줄과 같으면 더하지 않는다 (8.11) | — |
| 리뷰 없는 평가 수 허들 | 시드 에이전트 말고는 평가 수가 0 이라 Tier 1 · 2 허들을 넘지 못한다. 사용량만으로 Tier 3 까지는 오른다 | 리뷰 기능(MKT-007) |
| 에이전트별 이력 조회 | ~~읽는 곳이 없어 색인도 두지 않았다~~ → 배치가 마지막 줄을 읽어 `(agent_id, id)` 색인을 V28 에 두었다 | 화면 조회는 남음 |

### 8.11 등급 · 단가 재산정 — 매일 새벽 가격 등급을 바꾼다 (PAY-021/022)

**8.10 이 매긴 등급을 가격 칸(`agent_version.tier`)으로 옮긴다.** 할증률(`Tier.premiumRate`)은 고정값이라 바꾸지 않는다.
판매가 = 원가 × (1 + 할증) 계산(`AgentVersion.finalPrice`)은 전부터 있었고, tier 칸만 바뀌면 견적 · 선차감이 알아서 새 가격을 쓴다.

```
매일 03:00 (Asia/Seoul)   AgentGradeScheduler.regradeAll
  └─ selectTargets        공개된 에이전트 전부
  └─ 에이전트마다          regrade — 에이전트 하나가 트랜잭션 하나
       ├─ 재료 읽기 → 점수 · 등급 (8.10)
       ├─ 등급 이력          마지막 줄과 같으면 더하지 않는다
       ├─ 모든 버전 tier     다른 버전만 바꾼다
       └─ 변경 이력          바뀐 버전마다 한 줄 (V28)
  └─ 추천 색인 다시 넣기    한 번, 트랜잭션 밖
```

**정한 것**

| 무엇 | 정한 것 | 이유 |
| --- | --- | --- |
| 주기 | 하루 한 번 새벽 3시. `agent-grade.regrade.cron` · `zone` 설정 | 가격이 하루 동안 바뀌지 않아 사용자가 예측할 수 있다. AI 문서 6장이 주기를 BE 에 맡겼다 |
| 시연 | 관리자 API 를 두지 않는다. 시연 전에 cron 을 가까운 시각으로 잠깐 바꿔 한 번 돌린다 | 권한 검사 등 만들 것이 늘지 않는다 |
| 대상 | 공개된 에이전트 전부 | 수가 적다. 바뀐 것을 골라내지 않고 같은 결과를 남기지 않는 쪽으로 막는다 |
| 어느 버전 | 그 에이전트의 **모든 버전** | 등급은 에이전트 단위다. 옛 버전에 고정된 워크플로우만 옛 할증을 내면 같은 에이전트의 가격이 버전마다 갈린다 |
| 새 버전 | 직전 버전의 등급을 이어받는다 (`AgentVersion.next`). 첫 버전만 Tier 4 | 새 버전이 Tier 4 로 시작하면 다음 재산정까지 버전끼리 등급이 갈린다 |
| 진행 중인 실행 | 손대지 않는다 | 접수할 때 단계마다 배율을 `execution_charge_rate`(V22)에 적고 고치지 않는다. 새 등급은 다음 접수부터다 |

**중복을 막는 법** — 배치를 몇 번 돌려도 같은 것이 쌓이지 않는다.

| 기록 | 새 줄을 남기는 때 |
| --- | --- |
| 등급 이력 (`agent_grade_history`) | 마지막 줄과 재료 · 점수 · 등급 중 하나라도 다를 때. 조정값이 바뀌어 점수가 달라지면 재료가 같아도 남긴다 |
| 변경 이력 (`agent_tier_change`, V28) | 버전의 tier 가 실제로 바뀔 때. 이미 그 등급인 버전은 남기지 않는다. `before_tier <> after_tier` 를 CHECK 로도 막는다 |

변경 이력 한 줄에는 에이전트 · 버전, 바뀌기 전 · 뒤 등급과 판매가(그 버전의 원가 × 배율), 근거인 등급 이력 줄(`grade_history_id`),
바뀐 때(`created_at`)를 남긴다.

**실패** — 에이전트 하나가 실패하면 그 에이전트의 트랜잭션만 되돌리고 나머지를 계속 매긴다. 실패한 ID 는 `WARN` 로그로 남고,
끝에 대상 · 실패 수를 `INFO` 로 남긴다. 다음 회차가 모든 에이전트를 재료에서 새로 매기므로 재처리 목록을 따로 두지 않는다.

**추천 색인** — 다 매긴 뒤 `AgentIndexService.rebuild` 를 한 번 부른다. 기동할 때 쓰던 것과 같은 길이다.
색인의 `tier` 는 가격 등급, `success_rate` 는 등급과 같은 수식으로 재료에서 계산한 값이다(전에는 늘 1.0). 등록할 때도 같다.
색인에 넣지 못해도 등급은 이미 바뀌었다. 로그만 남기고 다음 회차나 기동 때 채운다.

**스레드** — `@Scheduled` 작업은 `BatchSchedulerConfig` 의 `batch-` 스레드에서 돈다. 실행 조회(`executionScheduler`) · 충전 확인(`chargeScheduler`)
과 나눈다. 따로 정하지 않으면 스프링이 `TaskScheduler` 빈 중에서 골라 쓰는데, 무엇을 고를지가 빈 수에 따라 달라진다.

**남은 한계**

| 상황 | 지금 | 필요한 것 |
