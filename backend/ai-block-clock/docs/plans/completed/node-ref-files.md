# 끝난 설계 — 노드 참고 자료

**구현이 끝나 `plans/` 에서 통째로 옮겼다.** 지금 코드가 왜 그 모양인지 되짚을 때만 본다. 남은 것은 둘이고
다른 문서가 맡는다 — `ref_files` 값의 모양은 [`../ai-runtime-questions.md`](../ai-runtime-questions.md) 1장,
안 쓰는 파일 폐기는 [`../agent-pipeline.md`](../agent-pipeline.md) 11.1 의 보관 기간이다.

공급자가 작업 노드를 만들 때 채점 기준표 · 양식 같은 자료를 붙여 두면, 실행할 때마다 우리가 그 노드와
함께 AI Runtime 에 보낸다.

| 요구사항 | |
| --- | --- |
| NOD-001 | 노드는 프롬프트와 모델로 이루어진다. 자료는 그 프롬프트가 기대는 근거다 |
| NOD-009 · SEC-001 | 자료도 지식 자산이다. 소유자 외에 원본이 노출되면 안 된다 |
| AGT-005 · AGT-009 | 팔린 버전의 내용은 뒤에서 바뀌면 안 된다 |
| SEC-006 | 올린 파일은 형식 · 용량 검증을 거친다 |

계약은 `ai/docs/integration-guide.md` §5.2 · §7.1 이다.

---

## 1. 사용자 파일과 다른 것이다

| | 누가 언제 올리나 | 어디에 붙나 |
| --- | --- | --- |
| `file` | **수요자**가 실행할 때 | 실행 한 건 ([`file-upload.md`](file-upload.md)) |
| `ref_file_<node_id>_<n>` | **공급자**가 노드를 만들 때 | 노드 하나 |

둘은 성격이 반대다. 사용자 파일은 매번 새것이고 실행이 끝나면 쓸모가 없다. **참고 자료는 한 번 붙여
두면 그 노드가 도는 모든 실행에 따라간다.** 그래서 노드와 수명을 같이하고, 굳힌 버전에도 따라간다.

| 계약이 정한 것 | |
| --- | --- |
| 형식 | `pdf` · `txt` · `md` · `csv` (계약 v2.0 7.1. 이미지는 받지 않는다) |
| 크기 | **노드당 합계 10MB** (파일 하나가 아니라 합계다) |
| 어기면 | `REF_FILE_REJECTED` · **공급자 책임** |
| 파트 이름 | `ref_file_<node_id>_<n>` — 노드 정의의 `ref_files` 순서와 맞춘다 |

---

## 2. 굳힌 버전이 제 자료를 들고 있어야 한다

여기가 이 작업의 핵심이다.

`VersionNode.freeze` 가 이미 노드의 이름 · 모델 · 원가 · **프롬프트 원문을 버전에 복사해 박는다.**
공급자가 노드를 고쳐도 이미 판 에이전트는 판 시점의 프롬프트로 돈다.

**참고 자료를 여기 빠뜨리면 그 보장이 뚫린다.** 공급자가 채점 기준표만 조용히 바꿔 끼우면, 프롬프트는
그대로인데 팔린 에이전트의 결과가 달라진다.

### 파일을 덮어쓰지 않는다

버전이 파일을 복사해 갖게 하는 방법과, **파일을 한 번 쓰면 다시는 건드리지 않는 방법**이 있다.

**후자를 고른다.** 자료를 바꾸는 것은 새 키에 새로 쓰는 일이고, 노드 행만 새 키를 가리키게 바꾼다.
굳힌 버전은 옛 키를 그대로 들고 있으므로 아무것도 복사하지 않아도 내용이 고정된다.

| | 얻는 것 | 치르는 것 |
| --- | --- | --- |
| **덮어쓰지 않는다** | 굳히기가 문자열 복사로 끝난다. 실수로 팔린 물건이 바뀔 길이 없다 | 아무도 안 쓰는 파일이 남는다 |
| 버전마다 바이트를 복사한다 | 키가 단순하다 | 굳힐 때마다 디스크가 는다. 복사 중 실패를 다뤄야 한다 |

남는 파일은 **지우지 않는다.** 어느 버전이 아직 그 키를 보는지 세야 지울 수 있고, 잘못 세면 팔린
에이전트가 실행 중에 깨진다. 폐기는 보관 기간 정책이 정해질 때 한꺼번에 본다.

## 3. 무엇이 생기나

| 자리 | |
| --- | --- |
| `domain/node` | `RefFile` · `RefFileValidator` · 노드에 붙이고 떼는 유스케이스 |
| `domain/agent` | `VersionNode` 가 자료 목록까지 굳힌다 |
| `domain/execution` | `PlannedPrompt` 가 자료를 들고 다닌다 |
| `client:ai` | `RunRequest` 에 `ref_file_*` 파트 |
| `storage` | `node_ref_file` · `agent_version_node_ref_file` (V15) |
| `api` | `POST` · `DELETE /api/v1/nodes/{nodeId}/ref-files` |

저장은 [`file-upload.md`](file-upload.md) 에서 세운 것을 그대로 쓴다. **루트 · 볼륨 · 오류 코드가 이미
있으므로 새로 세울 것이 없다.**

## 4. 노드 저장 API 를 건드리지 않는다

**결정: 자료는 하위 자원으로 따로 올린다.**

| 안 | 왜 |
| --- | --- |
| **`POST /nodes/{nodeId}/ref-files`** | 노드 저장 API 가 JSON 그대로 남는다. FE 가 쓰던 화면이 안 깨진다 |
| `POST /nodes` 를 multipart 로 | 노드 만들 때마다 폼이 된다. 자료를 안 붙이는 노드가 대부분인데 전부 바뀐다 |

실행 요청은 반대로 골랐는데([`file-upload.md`](file-upload.md) 4장), 거기서는 **파일과 실행이 한
동작**이라 왕복을 나눌 이유가 없었다. 여기서는 자료를 붙였다 뗐다 하는 것이 노드 편집과 별개 동작이다.

| | |
| --- | --- |
| `POST /api/v1/nodes/{nodeId}/ref-files` | 파일 하나를 붙인다. 합계 10MB 를 넘기면 거부한다 |
| `DELETE /api/v1/nodes/{nodeId}/ref-files/{refFileId}` | 뗀다. **파일 자체는 지우지 않는다** (2장) |
| `GET /api/v1/nodes/{nodeId}` | 붙어 있는 자료 목록을 함께 준다 |

**남의 노드에는 못 붙인다.** 노드 수정과 같은 소유권 검사를 탄다.

## 5. 실행 때 어떻게 나가나

`RuntimeWorkflow` 가 지금 단계를 `n1` · `n2` … 로 다시 매기고 있다. 파트 이름은 **그 새 ID 를 따라야
한다** — 노드 정의 ID 가 아니다.

```
PlannedPrompt(자료 목록)  ──►  nodes[].ref_files 로 쓴다
                          └─►  ref_file_n1_0 · ref_file_n1_1 … 파트로 붙인다
```

에이전트를 펼쳐 보내고 있으므로 안쪽 노드도 `n3` 처럼 같은 번호 체계에 들어간다. 자료가 어느 단계에
붙은 것인지 잃지 않는다.

### 계약에 안 적힌 칸 하나

가이드는 노드 필드에 `ref_files` 가 있다고만 하고 **그 값의 모양을 적어 두지 않았다.** 이름 배열인지
객체 배열인지, `<n>` 이 0부터인지 1부터인지 알 수 없다.

**이름 배열 · 0부터로 가정하고 보낸다.** 한 메서드 안에 가둬 두어 답이 오면 한 줄로 바꾼다.
[`../ai-runtime-questions.md`](../ai-runtime-questions.md) 에 물어 둔다.

## 6. 검사

| 검사 | 값 | 왜 우리가 먼저 보나 |
| --- | --- | --- |
| 형식 | `pdf` · `txt` · `md` · `csv` | 붙일 때 막지 않으면 **실행할 때 터진다.** 그때는 수요자가 돈을 낸 뒤다 |
| 노드당 합계 | 10MB | 파일 하나씩 보면 통과하고 합쳐서 넘는 경우를 놓친다 |
| 빈 파일 | 거부 | |

`REF_FILE_REJECTED` 는 공급자 책임으로 집계된다. **공급자가 자기 노드를 저장하는 자리에서 막아 주는
것이 그에게도 이득이다.**

## 9. 구현하며 갈린 것

### 저장은 [`file-upload.md`](file-upload.md) 것과 한 클래스를 나눠 쓴다

디스크 입출력을 `domain/file/FileStore` 로 뽑았다. 실행 파일과 참고 자료가 키 모양과 수명은 다르지만
쓰고 찾고 지우는 일은 같다.

**`node` 가 `execution` 을 알게 둘 수는 없다.** 의존 방향이 `execution -> node` 라
(`../agent-pipeline.md` 9장) 실행 쪽 저장소를 노드가 가져다 쓰면 방향이 뒤집힌다.

| 자리 | 키 |
| --- | --- |
| `ExecutionFileStore` | `executions/{executionId}/input{확장자}` |
| `RefFileStore` | `nodes/{nodeId}/{refFileId}{확장자}` |

### 뗀 자료의 순번을 다시 매기지 않는다

`ordinal` 은 순서만 정하면 되고 빈틈이 없을 필요가 없다. 다시 매기면 지우기와 고치기가 같은 트랜잭션에
섞여 `(노드, 순번)` 유일 제약을 스치게 된다. **다음 순번은 개수가 아니라 최댓값 + 1 로 잡는다.**

### `<n>` 은 보낼 때 세고, 저장한 순번을 쓰지 않는다

파트 이름의 `<n>` 은 그 실행에서 보내는 목록의 위치다. 저장된 `ordinal` 에 빈틈이 있어도 나갈 때는
0 부터 촘촘하게 붙는다.
