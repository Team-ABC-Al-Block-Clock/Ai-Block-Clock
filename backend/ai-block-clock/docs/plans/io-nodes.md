# 시작 노드 · 끝 노드 — 설계

캔버스 양 끝에 두는 블록. 시작 노드는 사용자가 실행할 때 무엇을 넣을지 정하고, 끝 노드는 무엇을 받을지
정한다.

| 요구사항 | |
| --- | --- |
| WRK-008 · WRK-009 | 입출력 노드를 MVP 에 넣는다 |
| EXE-003 | H2A 노드는 실행 시점에 자연어와 파일을 입력받는다 |
| NOD-005 | 노드는 엑셀 · CSV 입력을 받도록 정의할 수 있다 |

계약은 `origin/develop-AI:ai/docs/integration-guide.md` (09-22 갱신본) §5.2 · §5.4 · §5.5 · §7.1 이다.

> **이 문서는 두 겹이다.**
>
> | | |
> | --- | --- |
> | **2 ~ 4장 — 지금 굳힌다** | FE 와 BE 가 무엇을 주고받아 어떻게 저장할지 |
> | **5 ~ 6장 — AI 답을 받고 정한다** | 저장한 것을 실행 요청으로 어떻게 번역할지 |
>
> 저장을 먼저 굳히는 이유는 1장에 적는다. [`file-upload.md`](file-upload.md) 10장이 미뤄 둔 `input`
> 자리는 6장에서 채운다.

---

## 1. 저장은 지금 정할 수 있다

**저장하는 값은 "사용자가 무엇을 넣고 무엇을 받나" 다.** 우리 화면의 문제라 AI 와 상의할 것이 없다.
AI 답에 걸린 것은 그다음 — 저장한 값을 실행 요청으로 어떻게 번역하느냐다.

번역하는 길은 둘로 보인다.

| | 어떻게 | 지금 판단 |
| --- | --- | --- |
| **갈래 A** | 변환용 `llm` 노드를 앞뒤에 하나씩 끼운다. 작업 노드는 손대지 않는다 | 유력하다 |
| **갈래 B** | 첫 노드에 `input_schema_id` 를, 마지막 노드에 `output_schema_id` 를 우리가 찍는다 | 위험하다 (6.2) |

**어느 쪽으로 가도 저장할 값은 같다.**

| 저장하는 값 | 갈래 A 에서 쓰임 | 갈래 B 에서 쓰임 |
| --- | --- | --- |
| 시작 노드의 입력 항목 | 실행 폼을 그리고, 변환 노드가 받을 payload 를 만든다 | 실행 폼을 그리고, 그대로 `input` 이 된다 |
| 끝 노드의 결과 모양 | 변환 노드의 `output_schema_id` 가 된다 | 마지막 작업 노드에 찍는 값이 된다 |

읽는 쪽이 다를 뿐 **저장소에 들어갈 칸과 FE 가 보낼 모양은 바뀌지 않는다.** 그래서 2 ~ 4장을 먼저
굳히고 FE 가 편집 화면을 끝낼 수 있게 한다.

## 2. 저장 틀

### 2.1 종류를 늘린다

```java
public enum SourceType { NODE, AGENT, CONTROL, IO }

public enum IoType { START, END }
```

`ControlType` 에 값을 더하지 않는다. 흐름을 제어하는 것이 아니라 경계에 서는 것이라 역할이 다르다.

**분기 노드와 같은 자리에 산다.** `node_definition` 행 없이 `graph_node` 에만 있고, 가리킬 원본이 없다.

### 2.2 시작 노드 — 입력 항목을 든다

```jsonc
{ "nodeKey": "s1", "sourceType": "IO", "ioType": "START",
  "fields": [
    { "key": "brand_name", "label": "브랜드명", "type": "TEXT",   "required": true },
    { "key": "price_tier", "label": "가격대",   "type": "CHOICE", "required": true,
      "choices": ["보급형", "중가", "프리미엄"] }
  ] }
```

| 타입 | 화면 | 값 |
| --- | --- | --- |
| `TEXT` · `LONG_TEXT` | 한 줄 · 여러 줄 입력란 | 문자열 |
| `NUMBER` | 숫자 입력란 | 숫자 |
| `CHOICE` | 선택 상자. `choices` 가 항목 | 문자열 |
| `BOOLEAN` | 체크 상자 | 참 · 거짓 |

| 한계 | |
| --- | --- |
| `key` | 영문 소문자 · 숫자 · 밑줄, 40자. 한 시작 노드 안에서 겹치지 않는다 |
| `label` | 40자 |
| 항목 수 | 10개 |
| `choices` | `CHOICE` 일 때 1 ~ 10개 |

**폼을 그리는 데 필요한 최소만 둔다.** 계약의 JSON Schema 를 흉내 내지 않는다 — 우리가 해석해 화면을
그리는 값이라 표현력이 늘수록 FE 와 BE 가 같은 해석을 유지해야 한다.

**`fields` 가 비면 자유 입력이다.** 실행 화면이 여러 줄 입력란 하나를 그린다. 폼은 사용자가 무엇을
써야 할지 알려 주려고 두는 것이라, 정의하지 않아도 실행은 된다.

**`comment` 는 `key` 로 쓸 수 없다.** 사용자 코멘트가 이미 별도 파트로 모든 노드에 따라가고 견본
프롬프트도 `{comment}` 를 그 뜻으로 쓴다. 이름이 겹치면 어느 쪽이 들어갈지 정해지지 않는다.

### 2.3 끝 노드 — 결과의 구조와 형식을 든다

```jsonc
{ "nodeKey": "e1", "sourceType": "IO", "ioType": "END",
  "resultShape": "DOCUMENT", "resultFormat": "PDF" }
```

**축이 둘이다.** 하나로 뭉치면 안 된다.

| | 무엇을 정하나 | 어디로 나가나 |
| --- | --- | --- |
| `resultShape` | LLM 이 **무엇을 만들지** — 글 · 문서 · 표 | `output.schema_id` |
| `resultFormat` | 그것을 **무엇으로 렌더할지** — pdf · md · xlsx · csv | `output` 의 형식 칸 (5장 4-1) |

```java
public enum ResultShape {
    TEXT,      // common.text@1      — 제목과 본문 한 덩어리
    DOCUMENT,  // common.document@1  — 제목 · 여러 절 · 요약
    TABLE      // common.table@1     — 열과 행
}

public enum ResultFormat { PDF, MD, XLSX, CSV }
```

`biz.*` 11종은 브랜드 시연 전용이라(`biz.brand_brief@1` 설명이 "사용자가 실행 화면에서 채우는 첫
입력(H2A 폼)" 이다) 일반 사용자가 고를 목록이 아니다. **우리 enum 으로 두고 카탈로그 ID 를 저장하지
않는다** — 사용자에게는 "글 · 문서 · 표" 셋이고, 어느 ID 로 나가는지는 실행할 때 정하면 된다.

**형식도 저장한다. 결과 화면에서 고르게 하지 않는다.** 렌더는 실행의 일부다 — 완료 응답이 `pdf_url` 을
이미 들고 있으니(계약 §7.2) 실행이 끝나는 시점에 이미 만들어져 있고, 그러려면 **무엇으로 렌더할지가
요청에 실려 있어야 한다.** 지금 PDF 하나뿐이라 물어볼 필요가 없었을 뿐이다.

**결과 JSON 은 형식과 무관하게 늘 보관한다.** `artifact_url` 은 항상 있다고 계약이 적는다.

### 2.4 `graph_node` 에 칸 넷

```sql
alter table graph_node
    add column io_type varchar(20) null after control_type;

alter table graph_node
    add column io_fields text null after io_type;

alter table graph_node
    add column result_shape varchar(20) null after io_fields;

alter table graph_node
    add column result_format varchar(20) null after result_shape;
```

`io_fields` 는 2.2 의 배열을 JSON 문자열로 담는다. **`branch_condition` 이 이미 같은 방식이다** — 모양이
바뀔 수 있는 값을 칼럼으로 펴지 않고 한 칸에 둔다. `reference_id` 는 V16 에서 이미 null 을 받게 열어
두었다.

**번호는 열린 MR 뒤로 민다.** 지금 `feat/execution-reserve` 가 V17 을, `feat/execution-refund` 가 V18 을
쥐고 있고 이 브랜치의 V18 과 부딪친다. 붙일 때 `develop-BE` 의 최신 번호를 다시 보고 그 뒤를 잡는다.

### 2.5 저장할 때 보는 것

| 보는 것 | 어기면 |
| --- | --- |
| 시작 · 끝은 각각 0개 또는 1개 | `WORKFLOW_IO_NODE_DUPLICATED` |
| 시작으로 들어오는 선이 없고, 나가는 선이 하나다 | `WORKFLOW_IO_NODE_EDGE_INVALID` |
| 끝에서 나가는 선이 없고, 들어오는 선이 하나다 | `WORKFLOW_IO_NODE_EDGE_INVALID` |
| `fields` 가 2.2 의 한계를 지킨다 | `WORKFLOW_IO_FIELD_INVALID` |
| 끝 노드는 `resultShape` · `resultFormat` 이 있고, 시작 노드는 없다 | `COMMON_001` |
| 시작 · 끝은 `sourceId` · `nodeType` · `controlType` · `condition` 을 싣지 않는다 | `COMMON_001` |

**구조와 형식의 조합은 막지 않는다.** 표를 마크다운으로 받는 것이 말이 되는지 같은 판정은 5장 4-2 의
답이 와야 표가 선다. 짐작으로 막으면 멀쩡한 저장을 거부하게 된다. 답이 오면 그때 한 줄 더한다.

세는 자리는 분기와 같다. **원가와 프롬프트 수에서 빠지고, 캔버스 노드 상한에는 든다.** 실행할 때 노드
수가 어떻게 세어질지는 번역 방식에 달렸으니 5장에서 묻는다.

## 3. FE 와 맞추는 것

| 언제 | 부르는 곳 | 주고받는 것 |
| --- | --- | --- |
| 워크플로우 저장 | `POST /api/v1/workflows` · `PUT …/{id}` | 배치에 `sourceType: "IO"` · `ioType` · `fields` · `resultShape` · `resultFormat` |
| 워크플로우 열기 | `GET /api/v1/workflows/{id}` | 응답의 노드에 같은 값이 실린다 |
| 실행 폼 그리기 | **없다** | 위 응답만으로 그린다. `fields` 가 비면 자유 입력란 하나 |

**추가 요청이 없다.** 시작 노드 정의가 워크플로우 상세에 실려 오므로 편집 화면에서도 실행 화면에서도
스키마 카탈로그를 불러오지 않는다.

**팔레트에는 싣지 않는다.** 팔레트는 `node_definition` 과 에이전트를 나열하는 자리이고, 시작 · 끝은
가리킬 원본이 없다. 분기와 같은 취급이다 — FE 가 고정 항목으로 들고 있는다.

실행 요청(`POST /api/v1/runs`)에 `input` 파트를 더하는 것은 **번역 방식이 정해진 뒤다.** 폼 값을 어떤
모양으로 묶어 보낼지가 갈래 A 와 B 에서 다르다.

## 4. 지금 굳히는 것 중 하나만 위험하다

| 칸 | AI 답에 흔들리나 |
| --- | --- |
| `io_type` | 아니다. 어느 갈래든 시작 · 끝을 가려야 한다 |
| `result_shape` · `result_format` | 아니다. 사용자가 고르는 값이다. 나가는 칸 이름만 4-1 의 답을 따른다 |
| `io_fields` | **역할이 줄 수 있다** |

노드마다 입출력 스키마를 갖게 되면 실행 폼을 **첫 작업 노드의 `input_schema_id` 로 그릴 수 있다.**
그때 `io_fields` 는 폼을 그리는 유일한 근거에서 "사용자가 따로 둔 입력란" 으로 역할이 준다.

**그래도 지금 둔다.** 스키마가 하나도 없는 지금 이 칸을 빼면 시작 노드가 할 수 있는 일이 없다. 그리고
없어질 칸이라고 보지도 않는다 — 제 워크플로우에 맞는 입력란을 직접 두고 싶은 것은 카탈로그 스키마와
별개다. 다만 **그때 폼을 무엇으로 그릴지 다시 정해야 한다**는 것만 여기 적어 둔다.

## 5. AI 에 물어야 정해지는 것

[`ai-runtime-questions.md`](ai-runtime-questions.md) 3 · 4장으로 보냈다.

| 물은 것 | 답에 걸린 우리 일 |
| --- | --- |
| 경계 형식을 변환 노드로 맞추나, 작업 노드에 찍나 (3-1) | 실행 조립 전체. 6장 |
| 플랫폼이 끼운 노드를 표시할 방법이 있나 (3-2) | 실패 책임 귀속. `fault: supplier` 로 오면 남의 것으로 읽힌다 |
| 단가 없는 노드를 견적에서 어떻게 세나 (3-3) | 견적 화면에 "단가 미정" 이 뜨는지 |
| 노드마다 스키마를 언제 갖게 되나 (3-4) | 4장의 `io_fields` 역할. 갈래 B 가 설 수 있는 시점 |
| md · xlsx 를 내려줄 수 있나 (4-1) | 결과 보관 구조. 안 된다고 하면 렌더를 우리가 맡아야 한다 |
| 결과 스키마마다 받을 수 있는 형식이 갈리나 (4-2) | 결과 화면에서 어떤 형식을 감출지 |
| `template_id` 목록을 어디서 받나 (4-3) | 끝 노드에 칸을 더 열지 |

**답을 기다리는 동안 2 ~ 4장은 막히지 않는다.** 저장 · 조회 · 편집 화면까지 끝낼 수 있다.

## 6. 답이 오면 정할 것 — 지금 기울어 있는 안

**확정이 아니다.** 5장의 답에 따라 뒤집힐 수 있다. 무엇을 왜 유력하게 보는지만 남긴다.

### 6.1 갈래 A — 변환 노드를 끼운다

시작 · 끝을 **평범한 `llm` 노드 하나씩**으로 번역해 보낸다. 프롬프트는 플랫폼이 들고 있고, 하는 일은
형식을 바꾸는 것이다.

> 시작 노드의 `output_schema_id` 는 다음 노드가 받는 형식이다. 다음 노드가 형식을 말하지 않으면
> `common.text@1` 이다. 끝 노드의 `output_schema_id` 는 `resultShape` 가 가리키는 값이고,
> `output.schema_id` 가 그것을 따라간다.

**변환기를 우리가 짜지 않는다.** `output_schema_id` 를 걸면 Runtime 이 LLM 출력에 그 형식을 강제하고
틀리면 2회까지 교정한다. 우리 일은 무엇으로 바꿀지 정해 노드를 끼우는 것뿐이다.

이 규칙이 **지금(노드에 스키마가 없다)과 나중(노드마다 스키마를 든다)에 똑같이 돈다.** 설계가 바뀌지
않고 값만 바뀐다.

### 6.2 갈래 B 를 꺼리는 이유

마지막 작업 노드에 `output_schema_id` 를 덮어쓰면, 그 노드가 **남이 만든 것일 때** 의도하지 않은 형식을
강요하게 된다. 실패하면 계약이 이렇게 처리한다.

| 오류 | 책임 | 성공률 |
| --- | --- | --- |
| `SCHEMA_VALIDATION_FAILED` (교정 2회 초과) | `supplier` | **반영된다** |

**남의 평판이 깎인다.** `repair_count` 도 판매자 품질 지표로 쓰인다. 우리가 덮어쓴 형식 때문에 남의
등급이 내려가는 구조는 둘 수 없다.

### 6.3 갈래 A 가 치러야 하는 값

| | |
| --- | --- |
| 원가 | 실행마다 LLM 호출이 2회 는다. 노드 1회 실측 3 ~ 5 ABC |
| 단가 · 정산 | 판매자가 없다. 5장 3-2 · 3-3 의 답에 걸려 있다 |
| 진행 화면 | `progress.total` 이 2 는다. "입력 정리" · "결과 정리" 로 보인다 |
| 실행 시간 | 최장 경로가 2 길어진다. PER-003 의 5분에 가까워진다 |
| 캔버스 상한 8 | 작업 노드만 셀지, 둘을 넣어 셀지 정해야 한다 |

### 6.4 결과를 내려주는 쪽

번역 방식과 무관하게 필요하다. `GET /v1/runs/{id}/pdf` 를 클라이언트에 더하고, 실행이 `succeeded` 가
되는 것을 본 자리에서 결과를 받아 보관한다. **Runtime 의 `out/` 은 임시 저장소라 컨테이너를 다시
올리면 사라진다**(계약 §7.4).

저장은 [`file-upload.md`](file-upload.md) 가 세운 `FileStore` 에 얹는다 — 그 문서 9장이 "저장소는
이번에 세우므로 얹기만 하면 된다" 고 적어 두었다.

**형식 변환은 AI 쪽 일이다. 우리는 골라 실어 보내고, 만들어진 것을 받아 보관한다.**

렌더는 이미 Runtime 이 한다 — `pdf_url` 을 그쪽이 만들고, 결과 봉투도 `"type": "pdf"` 로 **형식 이름을
칸으로 들고 있다.** 값이 늘어날 자리로 보인다. 같은 파이프라인에 형식을 더하는 것이, 우리가 payload 를
읽어 두 번째 렌더러를 세우는 것보다 싸다. **Apache POI 를 들이지 않는다.**

우리가 하는 일은 셋이다.

| | |
| --- | --- |
| 실을 때 | 끝 노드의 `resultFormat` 을 `output` 의 형식 칸에 넣어 보낸다. **칸 이름은 5장 4-1 의 답** |
| 받을 때 | 완료 응답의 `result` 에서 형식별 URL 을 읽어 내려받아 보관한다 |
| 내려줄 때 | `GET /api/v1/runs/{executionId}/result[?format=]` |

**보관 구조를 형식 하나로 굳히지 않는다.** `result_pdf_key` 한 칸이 아니라 형식별 행으로 둔다 —
워크플로우마다 고른 형식이 다르고, Runtime 이 형식을 늘리면 받는 자리만 늘어야 한다. 결과 JSON 은
형식과 무관하게 늘 보관한다.

---

## 7. 작업 순서

| | 무엇을 | 언제 |
| --- | --- | --- |
| 1 | 저장 — `SourceType.IO` · `IoType` · `InputField` · `ResultShape` · `ResultFormat` · 마이그레이션 · 그래프 규칙 | **지금** |
| 2 | 조회 — 상세 응답에 `ioType` · `fields` · `resultShape` · `resultFormat` | **지금.** FE 가 여기까지로 편집 화면을 끝낸다 |
| 3 | 번역 — 실행 조립, `output_schema_id` 규칙, `input` 파트 | 5장 3-1 의 답 뒤 |
| 4 | 결과 — `/pdf` 클라이언트 · 보관 · `GET …/result` | **지금.** 3 과 독립이고, 끝 노드가 없어도 이미 빠져 있는 기능이다 |
| 5 | 통합 — 폼 값을 실은 실행 한 건 | 마지막 |

**막히는 것은 3 과 5 뿐이다.** 1 · 2 · 4 는 답을 기다리지 않는다.

**md · xlsx 를 만드는 일은 목록에 없다.** AI 쪽이 렌더한다(6.4). 우리 몫은 4 에서 형식이 늘어날 수
있게 보관 구조를 열어 두는 것까지다.

다만 **1 ~ 2 까지 하면 화면이 완성되어 보이지만 `input` 은 여전히 비어 나간다.** FE 도 폼을 그리는
데까지가 한계다 — 그 값을 보낼 자리가 3 이다. 시연 순서를 짤 때 이 경계를 헷갈리지 않는다.
