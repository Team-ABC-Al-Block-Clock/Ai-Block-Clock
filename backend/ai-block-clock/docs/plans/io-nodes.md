# 시작 노드 · 끝 노드 — 설계

캔버스 양 끝에 두는 블록. 시작 노드는 사용자가 실행할 때 무엇을 넣을지 정하고, 끝 노드는 무엇을 받을지
정한다.

| 요구사항 | |
| --- | --- |
| WRK-008 · WRK-009 | 입출력 노드를 MVP 에 넣는다 |
| EXE-003 | H2A 노드는 실행 시점에 자연어와 파일을 입력받는다 |
| NOD-005 | 노드는 엑셀 · CSV 입력을 받도록 정의할 수 있다 |

계약은 `origin/develop-AI:ai/docs/integration-guide.md` 다. 아래 인용은 09-22 갱신본 §5.2 · §5.4 · §5.5 · §7.1 기준이다.

> 입력은 진입 노드의 `input.sample`(폼 견본), 출력은 종단 노드가 제 `output {kind, sample}` 로 낸 결과다.

## 1. 저장은 지금 정할 수 있다

**저장하는 값은 "사용자가 무엇을 넣고 무엇을 받나" 다.** 우리 화면의 문제라 AI 와 상의할 것이 없다.
AI 답에 걸린 것은 그다음 — 저장한 값을 실행 요청으로 어떻게 번역하느냐다.

번역하는 길은 둘로 보인다.

| | 어떻게 | 지금 판단 |
| --- | --- | --- |
| **갈래 A** | 변환용 `llm` 노드를 앞뒤에 하나씩 끼운다. 작업 노드는 손대지 않는다 | 유력하다 |
| **갈래 B** | 첫 노드에 `input_schema_id` 를, 마지막 노드에 `output_schema_id` 를 우리가 찍는다 | 위험하다 (6.2) |

**어느 쪽으로 가도 저장할 값은 같다.**

| 저장하는 값 | 갈래 A 에서 쓰임 | 갈래 B 에서 쓰임 |
| --- | --- | --- |
| 시작 노드의 입력 항목 | 실행 폼을 그리고, 변환 노드가 받을 payload 를 만든다 | 실행 폼을 그리고, 그대로 `input` 이 된다 |
| 끝 노드의 결과 모양 | 변환 노드의 `output_schema_id` 가 된다 | 마지막 작업 노드에 찍는 값이 된다 |

읽는 쪽이 다를 뿐 **저장소에 들어갈 칸과 FE 가 보낼 모양은 바뀌지 않는다.** 그래서 저장을 먼저
굳혔다 — 2 · 3장은 [`completed/io-nodes.md`](completed/io-nodes.md).

## 4. 굳힌 것 중 하나만 위험하다

| 칸 | AI 답에 흔들리나 |
| --- | --- |
| `io_type` | 아니다. 어느 갈래든 시작 · 끝을 가려야 한다 |
| `result_shape` · `result_format` | 아니다. 사용자가 고르는 값이다. 나가는 칸 이름만 4-1 의 답을 따른다 |
| `io_fields` | **역할이 줄 수 있다** |

노드마다 입출력 스키마를 갖게 되면 실행 폼을 **첫 작업 노드의 `input_schema_id` 로 그릴 수 있다.**
그때 `io_fields` 는 폼을 그리는 유일한 근거에서 "사용자가 따로 둔 입력란" 으로 역할이 준다.

**그래도 지금 둔다.** 스키마가 하나도 없는 지금 이 칸을 빼면 시작 노드가 할 수 있는 일이 없다. 그리고
없어질 칸이라고 보지도 않는다 — 제 워크플로우에 맞는 입력란을 직접 두고 싶은 것은 카탈로그 스키마와
별개다. 다만 **그때 폼을 무엇으로 그릴지 다시 정해야 한다**는 것만 여기 적어 둔다.

## 5. AI 에 물어야 정해지는 것

[`ai-runtime-questions.md`](ai-runtime-questions.md) 3 · 4장으로 보냈다.

| 물은 것 | 답에 걸린 우리 일 |
| --- | --- |
| 경계 형식을 변환 노드로 맞추나, 작업 노드에 찍나 (3-1) | 실행 조립 전체. 6장 |
| 플랫폼이 끼운 노드를 표시할 방법이 있나 (3-2) | 실패 책임 귀속. `fault: supplier` 로 오면 남의 것으로 읽힌다 |
| 단가 없는 노드를 견적에서 어떻게 세나 (3-3) | 견적 화면에 "단가 미정" 이 뜨는지 |
| 노드마다 스키마를 언제 갖게 되나 (3-4) | 4장의 `io_fields` 역할. 갈래 B 가 설 수 있는 시점 |
| md · xlsx 를 내려줄 수 있나 (4-1) | 결과 보관 구조. 안 된다고 하면 렌더를 우리가 맡아야 한다 |
| 결과 스키마마다 받을 수 있는 형식이 갈리나 (4-2) | 결과 화면에서 어떤 형식을 감출지 |
| `template_id` 목록을 어디서 받나 (4-3) | 끝 노드에 칸을 더 열지 |

v2.0 이 3-1 · 3-3 · 3-4 에 사실상 답했다(위 머리말). 3-2 · 4-1 · 4-2 는 아직 답이 없고, 4-3 은 "다음 버전, 지금은 기본 문서형" 이다.

## 6. 실행 요청으로 옮기기

### 6.0 정한 것 — 폼으로 받아 그대로 싣는다 (09-26, MR !125)

| 노드 | 실행할 때 |
| --- | --- |
| 시작 노드 | 실행 화면이 `fields` 로 폼을 그린다. 채운 값은 실행 요청의 `input`(JSON 문자열)으로 받고, 돈을 떼기 전에 `fields` 정의와 맞춰 본다 — 필수 누락 · 타입 · 선택지 · 정의하지 않은 항목이면 `EXECUTION_009`. 통과하면 엔진의 `input` 파트로 싣는다 |
| 끝 노드 | 마지막 결과를 받는 자리다. 엔진 결과(JSON · PDF)를 받아 보관하고 내려준다 |
| 둘 다 | 엔진은 입출력 노드를 단계로 받지 않는다. 작업 단계 목록과 견적에는 넣지 않고, 역할만 `input` 파트와 결과로 옮긴다. 에이전트 안에 놓인 것도 같다 |

**자연어를 폼 모양으로 바꾸는 변환 단계(6.1 갈래 A)는 넣지 않았다.** 변환 단계 자체는 평범한 `llm` 노드라 끼울 수
있지만, 엔진이 판매자 정의 필드로 출력을 강제하지 못한다(계약 §6.1 "다음 버전"). 모양을 보장하지 못하는데 실행마다
LLM 호출이 하나 늘고, 판매자 없는 단계라 실패하면 플랫폼 탓 전액 환불이다. **엔진이 판매자 정의 필드를 열면 다시 본다.**
자연어는 지금처럼 `comment` 로 모든 단계에 따라간다.

**FE 가 실행 화면에 폼을 그려야 한다.** 지금 실행 화면은 자연어 입력칸 하나뿐이다. BE 만 먼저 나가면 필수 항목이 있는
워크플로우는 `EXECUTION_009` 로 막히므로 폼과 함께 배포한다.

아래 6.1 ~ 6.3 은 v2.0 전에 갈래를 고르던 기록이다.

**확정이 아니다.** 5장의 답에 따라 뒤집힐 수 있다. 무엇을 왜 유력하게 보는지만 남긴다.

### 6.1 갈래 A — 변환 노드를 끼운다

시작 · 끝을 **평범한 `llm` 노드 하나씩**으로 번역해 보낸다. 프롬프트는 플랫폼이 들고 있고, 하는 일은
형식을 바꾸는 것이다.

> 시작 노드의 `output_schema_id` 는 다음 노드가 받는 형식이다. 다음 노드가 형식을 말하지 않으면
> `common.text@1` 이다. 끝 노드의 `output_schema_id` 는 `resultShape` 가 가리키는 값이고,
> `output.schema_id` 가 그것을 따라간다.

**변환기를 우리가 짜지 않는다.** `output_schema_id` 를 걸면 Runtime 이 LLM 출력에 그 형식을 강제하고
틀리면 2회까지 교정한다. 우리 일은 무엇으로 바꿀지 정해 노드를 끼우는 것뿐이다.

이 규칙이 **지금(노드에 스키마가 없다)과 나중(노드마다 스키마를 든다)에 똑같이 돈다.** 설계가 바뀌지
않고 값만 바뀐다.

### 6.2 갈래 B 를 꺼리는 이유

마지막 작업 노드에 `output_schema_id` 를 덮어쓰면, 그 노드가 **남이 만든 것일 때** 의도하지 않은 형식을
강요하게 된다. 실패하면 계약이 이렇게 처리한다.

| 오류 | 책임 | 성공률 |
| --- | --- | --- |
| `SCHEMA_VALIDATION_FAILED` (교정 2회 초과) | `supplier` | **반영된다** |

**남의 평판이 깎인다.** `repair_count` 도 판매자 품질 지표로 쓰인다. 우리가 덮어쓴 형식 때문에 남의
등급이 내려가는 구조는 둘 수 없다.

### 6.3 갈래 A 가 치러야 하는 값

| | |
| --- | --- |
| 원가 | 실행마다 LLM 호출이 2회 는다. 노드 1회 실측 3 ~ 5 ABC |
| 단가 · 정산 | 판매자가 없다. 5장 3-2 · 3-3 의 답에 걸려 있다 |
| 진행 화면 | `progress.total` 이 2 는다. "입력 정리" · "결과 정리" 로 보인다 |
| 실행 시간 | 최장 경로가 2 길어진다. PER-003 의 5분에 가까워진다 |
| 계약의 캔버스 상한 8 | 작업 노드만 셀지, 둘을 넣어 셀지 정해야 한다. 우리 `GraphLimits` 는 아직 20 이다 |

### 6.4 결과를 실을 때

받고 보관하고 내려주는 쪽은 들어갔다([`completed/io-nodes.md`](completed/io-nodes.md) 6.4). **남은 것은 실을 때
하나다** — 끝 노드의 `resultFormat` 을 요청의 형식 칸에 넣는다. 칸 이름은 5장 4-1 의 답을 기다린다. v2.0 은 아직
`result.type: "pdf"` 하나다.

## 7. 작업 순서

| | 무엇을 | 언제 |
| --- | --- | --- |
| ~~1~~ | 저장 — `SourceType.IO` · `IoType` · `InputField` · `ResultShape` · `ResultFormat` · 마이그레이션 · 그래프 규칙 | **들어갔다** (V20) |
| ~~2~~ | 조회 — 상세 응답에 `ioType` · `fields` · `resultShape` · `resultFormat` | **들어갔다** |
| 3 | 번역 — 실행 조립, `input` 파트 | **MR !125** (6.0). 종단 노드 `output` 은 노드별 출력 형식과 함께 ([`contract-v2.md`](contract-v2.md) 2장) |
| ~~4~~ | 결과 — `/pdf` 클라이언트 · 보관 · `GET …/result` | **들어갔다** (V21, !95) |
| 5 | 통합 — 폼 값을 실은 실행 한 건 | **MR !125** 의 `ExecutionControllerTest` 가 붙잡는다. 실제 엔진으로는 FE 폼이 붙은 뒤 |

**남은 것은 FE 폼과 실제 엔진으로 한 번 돌려 보는 일이다.**

**md · xlsx 를 만드는 일은 목록에 없다.** AI 쪽이 렌더한다(6.4). 우리 몫은 4 에서 형식이 늘어날 수
있게 보관 구조를 열어 두는 것까지다.

**!125 가 병합되기 전까지는 시작 · 끝 노드를 놓은 워크플로우가 실행되지 않는다.** 견적과 실행 조립이 `EXECUTION_005` 로
막는다. 병합 뒤에는 FE 폼이 없으면 필수 항목이 있는 워크플로우가 `EXECUTION_009` 로 막힌다. 시연 순서를 짤 때 이 경계를 헷갈리지 않는다.
